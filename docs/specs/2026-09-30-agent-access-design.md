## Рамка безопасности

Это **ограждение и учёт против ошибок агента, не изоляция**: тот же пользователь ОС может
запустить `kubectl`/`docker` с тем же kubeconfig. Поэтому граница — пользователь ОС (сокет 0600,
каталог 0700, плюс проверка `SO_PEERCRED` uid == свой — дешёвая страховка), права общие для
всех локальных агентов, имя агента — заявленное, в UI помечено «не проверено». Доступ к Docker
≈ root на хосте — это сказано в UI выдачи прав Compose.

## Допущения агента (пользователь может поправить)

1. Права выдаёт человек в UI Ocular; агент ничего не запрашивает и сам себе не выдаёт.
2. Права общие для всех агентов на машине (см. «Рамка»). Права по агенту/проекту — позже.
3. **Разрушающий план агента ждёт подтверждения в Ocular** (ключевой вопрос задан пользователю
   2026-09-30; до ответа — этот вариант, рекомендованный ревью): агент готовит план, Ocular
   показывает его в диалоге с именем агента, выполняется только после «Да». Флажок права «без
   подтверждения» снимает это для конкретной выдачи. Неразрушающие записи в пределах права
   идут без подтверждения. Если пользователь выберет «право = согласие», правило основной
   спецификации «разрушающее — с подтверждением» для агентов будет явно отменено здесь.
4. Сокет работает, пока запущено приложение (desktop или browser-режим).

## Архитектура

- **Транспорт.** HTTP/1.1 + JSON поверх unix-сокета `~/.spk/ocular/agent.sock`
  (`$SPK_OCULAR_HOME/agent.sock`). Отдельный `http.ServeMux` (`internal/agentapi`), не
  UI-транспорт: нет токена страницы, Origin/Host-стражей, SSE; наружу — только методы каталога.
  Никакие id UI (`viewId`, `terminalId`, `forwardId`) агенту не выдаются и не принимаются.
- **Один владелец сокета.** `flock` на `agent.sock.lock` держится всё время жизни процесса.
  Взял замок — старый файл сокета удаляется (только тогда), `Listen`, chmod 0600; при выходе
  сокет удаляется под замком. Не взял — сокетом владеет другой экземпляр (например, desktop и
  browser-режим одновременно на одной базе): агентский API в этом процессе не поднимается, UI
  показывает «доступ агентов обслуживает другой экземпляр Ocular».
- **Проверка прав — в `agentapi`, до вызова `api.Service`, по каталогу, не по запросу.**
  Namespaced вид или нет — из `KindDescriptor.Scoped` сессии; неизвестный/не обнаруженный вид —
  отказ. Для namespaced вида вниз передаётся только `ScopeOne`; «все выданные» — обход
  `ScopeOne` по каждому выданному namespace (не `ScopeAll` с фильтром — это ещё и не требует
  кластерных прав на list). Исключение — выдача «все namespace-ы»: там `ScopeAll` + фильтр
  означает ровно то же, а обход требовал бы списка namespace-ов и N информеров. Страховка —
  фильтр строк по `Row.Ref.Scope`. «Проблемы» при обходе: кластерные источники открываются
  один раз, строки со scope `""` — без повторов (и только при праве «кластер»).
- **Фильтрация того, что выходит.** Связи (relations) на объекты вне выданных scope-ов и
  кластерные без права «кластер» — убираются, взамен «скрыто: N». «Проблемы» со scope `""` —
  только при праве «кластер». Факты/YAML кластерного объекта при праве «кластер» могут называть
  имена из любых namespace-ов (pod-ы узла, `claimRef` PV, субъекты RBAC) — это принято и сказано
  в UI выдачи. Значения Secret никогда не выходят (YAML/детали Secret — с `data` скрытым, как в
  UI).
- **Сессии.** Вызов агента берёт сессию цели как отдельный владелец: `SelectTarget` в UI не
  закрывает сессию, пока ею пользуется агент (запись сессии хранит «агент до T» = последний
  вызов + 60 с; `closeOtherSessions` её пропускает); простаивающая — закрывается обычным
  сборщиком. События сессии не выбранной в UI цели UI не трогают. Одновременных снимков агента
  — не больше 4 на процесс (остальные ждут ≤ 10 с, затем `limit`).
- **Хранение.** Права — таблица SQLite `agent_grants`; журнал — `agent_audit`.

## Модель прав

Выдача = **(провайдер, цель + её опознание, scope, глагол, виды, без подтверждения?)**:
- *цель* — context kubeconfig / Docker-endpoint и его опознание: адрес сервера + хэш CA + имя
  пользователя (auth-info) context-а (для Docker — endpoint + id демона). Не совпало (context переуказан на другой кластер) — выдача
  «приостановлена: цель изменилась», в UI — «подтвердить заново».
- *scope* — namespace / проект Compose, либо «все namespace-ы (включая будущие, в т.ч.
  kube-system)» — отдельный явный выбор с предупреждением; по умолчанию новые namespace-ы не
  выданы. Псевдо-scope **«кластер»** — объекты без namespace (Kubernetes: узлы, namespace-ы,
  CRD, PV, …; Compose: список проектов, образы, сети и тома вне проекта — общие сети показывают
  контейнеры других проектов). В v1 «кластер» — **только `read`**.
- *виды* — перечисленные виды или «все виды»; «все виды» не включает Secret, ServiceAccount,
  Role/RoleBinding/ClusterRole/ClusterRoleBinding для `edit` — их выдают поимённо.
- *глаголы* (v1): `read` (виды, строки, детали, YAML без значений Secret, события, «Проблемы»,
  метрики); `logs`; `edit` (правка YAML, P9); `action:<id>` (restart, scale, suspend, resume,
  run, delete, … — у Compose start/stop/restart/remove).
- **Разрушающее — по плану, не по действию.** `plan.Destructive` (scale до 0, delete, …) и
  `EditPlan.Destructive` проверяются на Prepare и снова на Run: нужен глагол, выданный
  поимённо (не через «все виды»), и — если у выдачи нет «без подтверждения» —
  подтверждение в UI (допущение 3).
- **Записи, задевающие другие scope-ы, — не в v1.** Действия и правки кластерных объектов
  (drain, cordon, удаление namespace/CRD/PV, правка узла/ClusterRole) агенту недоступны. Сверх
  того, Run отказывает, если списки плана (`plan.Lists`) называют объекты вне выданных scope-ов.
- **Честное предупреждение в UI:** `edit` workload-ов вместе с `logs` ≈ доступ к Secret-ам и
  ServiceAccount-ам namespace-а (агент может смонтировать секрет и прочитать его в логах,
  сменить `serviceAccountName`). Поэтому «значения Secret — не в v1» — про прямое чтение, не
  гарантия. Так же `edit` namespaced-ресурсов, по которым действует оператор (ArgoCD
  Application, Flux Kustomization, …), может означать записи уровня кластера — предупреждение,
  не исключение по умолчанию.
- Отзыв и изменение прав действуют немедленно: права проверяются на каждом вызове, в том числе
  на Run после Prepare.

## Методы (v1)

`POST /v1/<Method>` с JSON-телом, кроме самоописания; политика совместимости: в `/v1` поля
только добавляются, несовместимое — `/v2`.
- `GET /v1` — кто это, версия, как пользоваться (коротко), ссылка на методы.
- `GET /v1/methods` — каталог: имя, описание, JSON-схемы запроса и ответа, нужное право, пишет
  ли метод. Схемы — `invopop/jsonschema` по тем же Go-структурам, что обслуживают вызов; тест:
  у каждого зарегистрированного обработчика есть запись каталога и право, и наоборот.
- `Access` — цели, scope-ы, виды, глаголы, флаги, состояние выдач (действует / приостановлена).
- `ListKinds` — только выданные виды и действия, с признаком «разрушающее».
- `ListObjects` — **снимок**: открыть представление → дождаться Ready/Error (таймаут 20 с) →
  строки → закрыть. Ответ: строки, `truncated`, статус (устаревшее, частичное покрытие, не
  покрыто). Фильтр по имени/метке, `limit` (≤ 500); курсоров в v1 нет.
- `GetObject` (детали, YAML — с фильтрацией выше), `Problems`, `GetMetrics` (по ссылкам на
  объекты, не по id представления).
- `GetLogs` — хвост N строк / с момента, без потока.
- `PrepareAction` → `RunAction`; `GetEditSource` → `PrepareEdit` → `RunEdit` (подписанная база
  P9) — контракт UI. Разрушающий план без «без подтверждения»: `RunAction`/`RunEdit` отвечают
  `{state: "awaiting_confirmation", id}` сразу; `GetRun(id)` ждёт решения до 25 с и отвечает
  итогом, `rejected` или тем же `awaiting_confirmation` (агент повторяет). Ожидание в UI живёт
  10 минут, затем `expired`; с выходом процесса ожидания пропадают — `GetRun` отвечает `gone`.
  После «Да» права и опознание цели проверяются снова в момент записи; план, устаревший за
  ожидание, кончается `conflict` через `Expect`/подписанную базу правки, не тихой записью.
  Ожидание видно человеку, даже если окно скрыто или страница не открыта: уведомление рабочего
  стола, значок/фокус окна, счётчик в списке целей; `GET /v1` и `Access` говорят, что
  подтверждение делает человек в UI Ocular (агент передаёт это своему пользователю).
- Ошибки — `{code, detail, why}` как у UI (P13): `forbidden` (что именно не выдано),
  `not_found`, `conflict`, `limit`, …

## Журнал

- До отправки записи — намерение: время, агент (заявленное имя), метод, цель, scope, объект,
  `Destructive`, хэш `Expect`; после — итог (done / refused / unknown / сводка частей /
  rejected). Неизвестный итог оставляет след. Чтения — одной записью на метод и цель в минуту
  (счётчик). Без тел запросов и без значений секретов; ротация по объёму.
- В UI — журнал с фильтром по агенту и цели.

## Инструкция для агента

Одна строка для общих инструкций агента (UI даёт кнопку «Скопировать»):

> SPK Ocular (Kubernetes/Docker): `curl -s --unix-socket ~/.spk/ocular/agent.sock http://ocular/v1`
> — описание и список методов; доступ к namespace-ам выдаёт пользователь в Ocular.

## UI

Раздел «Доступ агентов»: по цели — scope-ы (включая «все namespace-ы» и «кластер» с
предупреждениями) с глаголами, видами/действиями и флагом «без подтверждения»; по умолчанию
пусто; «Отозвать всё»; предупреждения из «Модели прав». Диалог подтверждения разрушающего плана
агента (план как в ActionDialog/EditDialog + имя агента «не проверено»). Журнал. Статус сокета
(работает / обслуживает другой экземпляр).

## Проверка

- Go: таблица «метод × право есть/нет»; обход через `ScopeNone`/`ScopeAll`/пустой scope у
  namespaced видов (Secret, pod) — отказ; фильтр связей и «Проблем»; кластерные записи (drain,
  удаление namespace) — отказ; scale→0 при «все виды» — требует поимённого и подтверждения;
  списки плана вне scope — отказ на Run; отзыв между Prepare и Run; `SelectTarget` во время
  вызова агента; два экземпляра одновременно (замок); сокет 0600 и чужой uid; журнал без
  секретов; каталог методов ↔ обработчики.
- kind: агент по сокету читает выданный namespace, не видит невыданный, restart по праву,
  `forbidden` без него, delete ждёт подтверждения.
- Desktop: раздел прав и диалог подтверждения в русской раскладке.
