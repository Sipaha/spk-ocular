## Замечания и исправления

1. **P2 — сохранялся промежуточный снимок вместо текущего.** В `pageMemoPersist.ts`
   `note()` выходил по `json === last` или превышению лимита, оставляя старый `pending`.
   Сценарий: A сохранён → пользователь вводит B → возвращает A до таймера → в SQLite
   записывается B. При слишком длинном фильтре тоже записывался уже неактуальный снимок.
   Теперь каждое уведомление замещает либо отменяет ожидающую запись.
2. **P2 — записи могли завершаться в обратном порядке.** Fire-and-forget запросы
   `SetTargetState` отправлялись независимо, в том числе после ухода с цели и возврата.
   Медленная старая запись могла затереть новую. Теперь один writer на client/target:
   один запрос в полёте, только последний ожидающий снимок, порядок сохраняется и через
   размонтирование Workspace. Неограниченной очереди запросов нет.
3. **P2 — ошибка записи считалась успехом.** `last` обновлялся до ответа сервера,
   rejection полностью игнорировался. Повторное уведомление с тем же состоянием уже не
   могло его сохранить. Теперь подтверждённое значение обновляется после успеха;
   при отказе следующее уведомление допускает повтор. Бесконечных фоновых повторов нет.
4. **P3 — debounce не соответствовал плану.** Таймер отсчитывался от первого изменения,
   а не последнего: фактически throttling. Теперь интервал 1 с начинается заново после
   изменения, как указано в P19; уход с цели по-прежнему вызывает flush.
5. **P3 — несколько тестов давали ложную уверенность.**
   - «does not write content it has already written» вызывал `note()` один раз:
     удаление проверки дедупликации не ломало тест. Добавлено второе уведомление.
   - Workspace «marks are never in it» сначала отмечал `api-1`, затем фильтровал по
     `db`, что снимало отметку до сериализации. Теперь строка остаётся отмеченной,
     это явно проверяется перед проверкой сохранённого JSON.
   - Oversize-тест требовал наличия записи малого снимка после ввода большого —
     закреплял ошибку из п. 1. Теперь ожидает отмену этой записи.
   - Тест изоляции synthetic-потоков запускал две горутины с `context.Background()`
     без завершения; отрицательные проверки опирались на sleep 100 мс, потом повторно
     читали срезы без замка. Теперь есть отмена/ожидание завершения, конечные события
     для обоих потоков и проверки под замком; sleep и дубли удалены.
6. **P3 — хрупкий жизненный цикл restart-e2e.** Был sleep 1600 мс вместо ожидания
   записи, потеря дочернего процесса при ошибке старта, игнорирование `signalCode`
   при остановке, отсутствие ожидания выхода после SIGKILL. Теперь проверяется реальный
   `GetTargetState`, процессы завершаются и при неудачном старте, stderr попадает в
   ошибку, ресурсы теста создаются внутри теста в solution `.agents/tmp`. Сценарий
   дополнен быстрым изменением/возвратом фильтра и переключением целей перед рестартом.
7. **Старая проблема, не Kimi.** Повтор `go test -race -count=10` поймал
   `TestEchoTerminal`: результат отдавался в канал раньше `h.Close()`, хотя тест уже
   ожидал ноль handles. Исправлен порядок в `runTerm` (`live_test.go`, существовал до
   передачи Kimi). После исправления весь synthetic-пакет прошёл 30 повторов с race.

Убран устаревший комментарий Workspace о закрытии логов при переключении. Тестовый
reset-route оставлен: он ограждён test-api/token и решает реальную изоляцию сценариев;
это не бесполезное расширение production API. Удалять целые тестовые файлы оснований нет.

## Качество тестов и отчётности

P18 имеет содержательные проверки: транспортные счётчики учитывают и LIST, и
WatchList (`sendInitialEvents`), второй synthetic-target использует те же имена
объектов, что позволяет выявлять смешение потоков. Реальные kind-тесты проверяют
обновление credentials и отказ фонового плагина. E2E warm-return допускает 1500 мс,
поэтому сам по себе не доказывает бюджет 150 мс; для этого нужны отдельные замеры,
которые Kimi записал в P18. Старые замеры памяти и desktop здесь повторно не заявляются.

Слабое место — запись в итогах P19 «мутации подтверждены» со способом
«отсутствие символов → красные». Удаление целого модуля доказывает зависимость тестов
от модуля, но не чувствительность к ошибкам дедупликации, порядка и отказов записи.
Наши шесть новых регрессий падают на исходном `pageMemoPersist.ts` и проходят на
исправленном. Удаление target-предиката ломает исправленный тест потоков.

## Оценка Kimi как инструмента в этой работе

**Справился с продолжением проекта, но результат требовал инженерного ревью.**
P18 завершён с учётом существующей архитектуры; P19 работает в обычном сценарии,
но содержит реальные ошибки асинхронного сохранения. Исправления локальны:
переписывать подсистему или откатывать этапы не нужно.

Сильные стороны:
- восстановил контекст после другой модели, сохранил соглашения проекта;
- использовал готовый target_state, не изобретал новый слой хранения;
- проверял приложение не только моками: kind, e2e, desktop, замеры;
- обнаружил реальную межтестовую утечку состояния и исправил изоляцию;
- исправил собственную устаревшую рекомендацию restart-workload, сверившись с кодом;
- отсутствие независимого ревью обозначил явно; автономное продолжение разрешил пользователь.

Слабые стороны:
- хорошо покрывает прямой сценарий, хуже — смену состояния во время ожидания,
  обратный порядок ответов, повтор после неудачи и завершение ресурсов теста;
- принимает зелёные проверки и грубые мутации за более сильное доказательство,
  чем они дают; отдельные названия тестов превосходят фактические проверки;
- переносит знакомый шаблон `.catch(() => {})` без проверки его взаимодействия
  с дедупликацией и очередью;
- документы подробные, но оставались противоречия («сервер не меняется» при новом
  test-route, старый комментарий о вкладках), часть уверенных выводов требует аудита.

Практический вывод именно из этой сессии: Kimi пригоден для реализации ограниченных
этапов и подхвата работ в зрелом репозитории. Принимать асинхронную логику только по
его «все тесты зелёные» нельзя; полезнее независимое ревью переходов состояний и
поведенческие мутации, чем наращивание числа похожих проверок. Данных для честного
сравнения стоимости, скорости и общей надёжности с Claude/Codex здесь недостаточно.
