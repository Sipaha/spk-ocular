# Спайк: fetch-стрим из desktop-окна к loopback-серверу (P2 Task 1)

> Итог: работает с CORS и «толчком» после каждого всплеска — см. «Второй заход».

Дата: 2026-09-29. Wails v3 beta.26, WebKitGTK (Ubuntu, Xvfb, без GPU).

## Вопрос

Можно ли в desktop-сборке читать лог-поток обычным `fetch` + `ReadableStream` со страницы
`wails://` к `http://127.0.0.1:<port>`: приходят ли данные по мере записи, нужен ли CORS,
не обрезается ли всплеск с последующей паузой (грабли launcher-а с `wails://`-мостом),
доходит ли отмена до сервера.

## Как проверяли

Временный код (не в репозитории): в desktop-сборке loopback-сервер на фиксированном порту с
ответами `stream` (строка NDJSON каждые 100 мс, `Flush` после каждой), `burst` (5000 строк по
~120 байт одним махом, пауза 3 с, ещё строка, пауза 2 с) и `report` (страница присылает
результаты). Страница при загрузке прогоняла сценарии и отчитывалась; запуск под
`xvfb-run`, итог — журнал сервера.

## Результат

| Сценарий | Итог |
|---|---|
| Origin страницы | `wails://localhost` (не `wails://wails`), `Host` — `127.0.0.1:<port>` |
| GET без `Access-Control-Allow-Origin` | `TypeError: Load failed` — CORS обязателен |
| GET с `Access-Control-Allow-Origin: wails://localhost`, простой запрос (без своих заголовков) | preflight нет; 20 чтений по одному кадру с шагом ~100 мс — поток живой, не буферизуется до конца |
| Всплеск 5000 строк → пауза 3 с → строка | все 5001 строки, последняя пришла через 3,0 с — обрезки нет |
| `AbortController.abort()` посреди потока | сервер видит `r.Context().Done()` сразу |

## Второй заход (после ревью Codex): всплеск, затем тишина без закрытия

Codex указал, что грабля launcher-а — это «всплеск, потом полная тишина при открытом
соединении», а первый заход проверял всплеск с последующей строкой. Проверили отдельно
(соединение не закрывается, страница считает строки через 1,5–3 с и отменяет запрос):

| Сценарий | Итог |
|---|---|
| 20 000 строк × ~120 Б, затем тишина | в ~1 из 4 запросов **хвост 20–60 КБ не доходит**, пока не придут новые байты (19 026 / 19 523 / 19 800 из 20 000; 2 978–2 996 из 3 000; 49 966 из 50 000). Не зависит от `Content-Type` (ndjson / text/plain / octet-stream). Недетерминированно: в другом прогоне все 9 из 9 полные |
| 1 маленький кадр, затем тишина | доходит |
| Всплеск + ping каждые 200 мс / 1 с | всё доходит |
| Всплеск + **один** маленький кадр через 100 мс, затем тишина | 72 из 72 запросов полные (3 прогона × 24: 3 000 / 20 000 / 50 000 строк) |
| 200 000 строк (24 МБ) | доходит за 1,6 с |

То есть WebKitGTK (NetworkProcess → WebProcess) придерживает хвост пачки и отдаёт его только
со следующими байтами — это свойство WebKit, а не `wails://`: на loopback HTTP оно тоже есть,
просто реже.

## Выводы для P2

- Поток логов — один запрос (backlog и follow в одном ответе), но писатель потока после
  каждого сброса, за которым наступила тишина, через 100 мс шлёт маленький кадр `ping`
  («толчок»), плюс редкий heartbeat. Без этого конец backlog-а (самые свежие строки!)
  иногда не виден, пока pod не напишет что-нибудь ещё.
- CORS: `Access-Control-Allow-Origin` ровно для origin страницы desktop (`wails://localhost`);
  токен в пути, запрос «простой» — preflight не нужен.
- Закрытие вкладки = `abort` → запрос kube отменяется по контексту HTTP-запроса.
- Не проверено: поведение скрытого/свёрнутого окна (нет xdotool в окружении). Чтение идёт
  промисами `reader.read()`, не через rAF, поэтому остановки чтения не ожидается; обратное
  давление при остановке — предмет теста Task 2 на стороне сервера.

## Дополнение: поведение `pods/log` на kind (v1.3x, containerd)

- Метки `timestamps=true` — RFC3339 с наносекундами (`2026-09-29T10:43:41.711250730Z text`).
- `sinceTime` с долями секунды **обрезается до секунды**: запрос с `…:41.711Z` вернул строки
  с `…:41.106Z`. Шов при продолжении обязателен.
- `limitBytes` режет посреди строки (30 байт — одна метка без текста): последняя неполная
  строка ответа с `limitBytes` отбрасывается.
- Ошибки — 400 с понятным текстом: `container nope is not valid for pod ticker`,
  `previous terminated container "ticker" in pod "ticker" not found`.
- Pod в CrashLoopBackOff: обычный запрос отдаёт логи последнего завершившегося запуска.
