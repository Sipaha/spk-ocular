# P14 — доступ агентов (Claude/Codex) к целям Ocular через unix-сокет

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`. Каждая задача — отдельные
> коммиты `area: summary`, `make check` зелёный перед коммитом. Каждое исправление и каждая
> возможность начинаются с теста, который падает без них (проверка мутацией на старом коде).

**Цель:** локальный агент (Claude Code, Codex) по unix-сокету узнаёт, что ему выдал человек
(цели, namespace-ы/проекты, глаголы, виды), и в этих пределах читает объекты, детали, «Проблемы»,
метрики, логи, готовит и выполняет действия и правки YAML. Права выдаёт человек в UI Ocular; без
выдачи список пуст. Разрушающий план ждёт «Да» в UI, если у выдачи нет флажка «без
подтверждения». Всё записывается в журнал.

**Спецификация:** `docs/specs/2026-09-30-agent-access-design.md` (закрыта ревью `ggyxmbt4`,
`c9f60ef`). План её не пересказывает: ниже — как она ложится на код, и решения, которых в ней
нет.

**Архитектура (слои):**
- `internal/agentgrant` — модель прав и чистые функции решения (`Allows`, `Readable`,
  `ScopesFor`), без ввода-вывода; ей пользуются и `agentapi`, и `api` (UI-методы).
- `internal/store` — таблицы `agent_targets`, `agent_grants`, `agent_audit` (миграция
  `0003_agent_access.sql`), CRUD и журнал с агрегацией чтений и ротацией.
- `internal/api` — то, что нужно агентскому слою от сервиса и чего нет в API UI: снимок строк без
  представления UI, хвост логов без потока, метрики по ссылкам, опознание цели, пощада сессий
  агента; UI-методы управления доступом (выдачи, ожидания подтверждения, журнал, статус сокета)
  — в интерфейсе `API` и обоих транспортах, реализация делегируется `AgentControl`, который
  ставит проводка.
- `internal/agentapi` — сокет (`flock`, 0600, `SO_PEERCRED`), `http.ServeMux` `/v1`, каталог
  методов (`invopop/jsonschema`), проверка прав до вызова `api.Service`, обход scope-ов, фильтры
  ответа, реестр планов агента, ожидания подтверждения, журнал; реализует `api.AgentControl`.
- `cmd/spk-ocular` — поднимает `agentapi` после `newCore` в browser- и desktop-режиме, закрывает
  до `c.Close()`; `internal/desktop` — уведомление рабочего стола и заголовок окна при ожидании.
- `web/src/agents` — раздел «Доступ агентов» (выдачи, журнал, статус, строка инструкции),
  глобальный диалог подтверждения, индикатор в строке состояния, счётчик у цели в списке.

## Глобальные ограничения

- Всё из P0–P13 (AGENTS.md «Правила»). UI-поведение без выдач не меняется; сокет — только
  локальный, наружу ничего нового не слушает.
- Проверка прав — в `agentapi` **до** вызова `api.Service`, по каталогу сессии
  (`KindDescriptor.Scoped`), на каждом вызове, включая Run после Prepare и запись после «Да».
- Агенту не выдаются и от него не принимаются id UI (`viewId`, `terminalId`, `forwardId`,
  `configRev`, `expect`, `base`/`token` правки): их держит `agentapi` за своим `planId`.
- Значения Secret не выходят никогда (YAML/детали — как в UI, `data` скрыт; `GetValues`,
  `RevealValue`, exec, проброс портов, потоки — не методы v1).
- Тексты UI — через `t()`/ключи, русский и английский; ответы сокета — английский (агенту),
  ошибки в форме `{code, detail, why?}` (P13).
- Память: новое держится только пока идёт вызов (снимок, хвост логов) или ограничено
  (реестр планов ≤ 200, ожиданий ≤ 20, журнал в SQLite с ротацией). Private_Dirty без агента не
  растёт — замер до/после в Task 7.

## Решения P14 (агент, 2026-09-30)

1. **Права — строки `(цель, scope, глагол, виды, без подтверждения)`.** Одна строка
   `agent_grants` — один глагол в одном scope одной цели: `verb` ∈ `read`, `logs`, `edit`,
   `action:<id>`; `kinds` — JSON-список id видов или `NULL` = «все виды»; `no_confirm`. Scope:
   `mode` ∈ `one` (`name` = namespace/проект), `all` («все namespace-ы, включая будущие»),
   `cluster` (псевдо-scope объектов без namespace; допускает только `read` — проверка в модели
   и в store). UI группирует строки по цели → scope. Так любой набор из спецификации выражается
   без особых случаев, а решение «разрешено ли» — чистая функция над списком строк.
2. **Опознание цели — отдельно от выдачи.** `agent_targets(provider, target, title, identity,
   shown, observed)`: `identity` — хэш на момент выдачи, `shown` — человеческое «сервер · CA ·
   пользователь» / «endpoint · id демона», `observed` — иное опознание, увиденное на вызове (не
   пусто = все выдачи цели «приостановлены: цель изменилась»). «Подтвердить заново» в UI
   переносит `observed` в `identity`. Выдача без строки цели не создаётся (UI создаёт обе в одной
   транзакции).
   - Kubernetes: `core.Target.Identity` (`json:"-"`) — читаемая строка «server | ca:<первые 8
     байт sha256 CA — `certificate-authority-data` или содержимого файла `certificate-authority`
     (≤ 1 MiB); `insecure`; `system`> | tls-server-name | proxy-url | user:<имя auth-info>».
     Считается в `describe` без сети; токены и exec в неё не входят (их ротация не
     приостанавливает выдачи — в отличие от `ConfigHash`). `tls-server-name` и `proxy-url`
     входят: они меняют, куда реально идёт запрос, при прежнем `server` (ревью P3-5).
     Строка не секретна, она же показывается в UI («было … стало …»).
   - Docker: `Target.Identity` = endpoint из Discover; id демона — только по сети, поэтому
     сессия compose реализует новый `provider.Identifier{ Identity(ctx) (string, error) }`:
     `engine.Info().ID`, один раз на сессию (кэш, повтор после ошибки). `api.Service.
     TargetIdentity(ctx, provider, target)` = `Target.Identity` + (если сессия — `Identifier`)
     id демона. Не удалось узнать id демона — вызов агента `unavailable`, выдачи не
     приостанавливаются (недоступность ≠ другая цель).
3. **«Все виды» не включает чувствительные для `edit`, а разрушающее — только поимённо.** Новое
   `core.KindDescriptor.Sensitive` (провайдер): kubernetes — `secrets`, `serviceaccounts`,
   RBAC (`roles`, `rolebindings`, `clusterroles`, `clusterrolebindings` группы
   `rbac.authorization.k8s.io`, и описанные, и обнаруженные). `edit` вида `Sensitive` требует
   строку, где вид назван явно. Разрушающий план (`ActionPlan.Destructive`,
   `EditPlan.Destructive`) требует строку глагола, где вид назван явно (не `NULL`), — иначе
   `forbidden` с объяснением «разрушающее выдаётся поимённо».
4. **Планы агента — за `planId`.** `PrepareAction`/`PrepareEdit` агента зовут сервис, кладут
   полный запрос Run (`ActionRunRequest` с `Expect` и `ConfigRev`; `EditRunRequest` с `Base`,
   текстами и `Token`) и сводку плана (цель, ref, `Destructive`, списки, глагол) в реестр
   `agentapi` (TTL 10 мин, ≤ 200, самые старые вытесняются) и отдают агенту план без этих полей
   и `planId`. `RunAction`/`RunEdit` принимают только `planId`: судить о разрушительности по
   плану, который видел агент, а не по тому, что он прислал; подделать `Expect`/токен нельзя.
   Устаревший план по-прежнему ловит провайдер (`Expect`, подписанная база) — `conflict`.
5. **Списки плана — с `Ref`.** `core.ActionItem` получает `Ref *core.Ref` (`omitempty`):
   drain (pod-ы) заполняет. Синтетический провайдер — нет: его список (evacuate) у несcoped-вида,
   агенту недоступен; «элемент без `Ref` = вне выдачи» проверяется на фейковом провайдере тестов
   `agentapi`. Run агента отказывает (`forbidden`), если
   элемент списка без `Ref` или его scope/вид вне выданного этому глаголу. Сегодня списки есть
   только у drain (кластерное действие — агенту недоступно), правило — на будущее.
6. **Кластерные записи — отказ по каталогу.** Действие/правка вида с `Scoped == false` агенту
   `forbidden` всегда (drain, cordon, правка узла/namespace/CRD/ClusterRole); `read` такого вида
   — при scope `cluster`.
7. **Снимок строк — не представление UI, но с теми же шагами до `views.Open`.**
   `api.Service.Snapshot(ctx, SnapshotRequest)` повторяет `OpenView` (ревью P2-1): вид ищется в
   `sess.Kinds()`, исчезнувший (`KindRemoved`) — `removed`, неизвестный — `unsupported`;
   `ViewDescriber.DescribeView` даёт колонки ответа и `Query` со `Schema` (обнаруженные виды —
   колонки серверной таблицы). Затем `sess.Watch` напрямую со своим собирающим `Sink` (без
   `views.Manager`: ни событий `view_changed` в UI, ни id). `Sink.Apply` не блокирует и
   применяет `Delta` по контракту: `Reset` (замена всех строк) или `Upserts`, затем `Deletes`,
   затем `Status`. Ждём `Ready`/`Error`; `schema_changed` во время снимка — один повтор с новым
   `DescribeView`, второй — ошибка. Строки — `core.Row` без изменений, колонки рядом.
   Семафор — на каждый `Watch` (4 на процесс, ожидание в пределах срока вызова). Срок одного
   `Watch` — 20 с, **общий срок вызова агента — 30 с** (ревью P3-3): при обходе scope-ов
   (решение 11) идут не больше 4 одновременно, не успевшие к сроку — в `scopes[]` с `state:
   timeout`, ответ собирается из успевших. `limit` ≤ 500 (по умолчанию 200) — по сумме обхода,
   `truncated` — если строк было больше.
8. **Пощада сессий агента — любому вызову.** `sessionEntry.agentUntil` = последний вызов
   агента + 60 с (`sessionIdle`) и `agentCalls` — вызовы агента в работе (снимок, хвост логов,
   метрики, `GetObject`, Prepare/Run, запись после «Да»; ревью P3-1). Вызов агента берёт сессию
   через `Service.agentCall(ctx, provider, target) (entry, ctx, done)`: регистрирует свою
   отмену в записи сессии и продлевает `agentUntil`; `done` снимает регистрацию.
   `closeOtherSessions` (выбор цели в UI) пропускает сессию, у которой `agentUntil` в будущем или
   `agentCalls` не пуст; сборщик считает её занятой так же. `closeSessionLocked` (смена
   конфигурации, выход) отменяет контексты идущих вызовов — они кончаются `gone`.
9. **Метрики — по ссылкам.** `GetMetrics{refs ≤ 100}`: ссылки группируются по (вид, scope);
   на группу — один снимок вида в этом scope (решение 7), строки выбираются по `Ref.Name` (и
   `UID`, если дан), затем `MetricsSource.Metrics(ctx, q, rowIDs)` с таймаутом 10 с (как у UI).
   Ссылка без строки — `missing` в ответе. `GetMetrics` UI не меняется.
10. **Логи — хвост без потока.** `api.Service.TailLogs(ctx, ref, TailRequest{Channel,
    Previous, TailLines ≤ 5000 (по умолчанию 200), SinceTime})`: `LogSource.StreamLogs` с
    `Follow: false` в собирающий `LogSink` с потолком 1 MiB текста (сверх — `truncated`,
    прерывание), таймаут 20 с; ответ — строки (время, текст, источник) и состояния
    источников. Слоты логов провайдера те же, что у UI.
11. **Обход и фильтры ответа.** Без scope в запросе `ListObjects`/`Problems` обходят
    namespace-ы из выдач `read` этого вида **по их именам** (`ScopeOne` на каждый) — `ListScopes`
    и кластерные права на list не нужны. Выдача `all` → один `ScopeAll`; если сервер отказал
    (403: нет кластерного `list`) — `forbidden` с подсказкой «выдайте namespace-ы поимённо».
    `GetObject`: связи на объекты, которые агенту не читать (scope или вид вне `read`,
    кластерные без `cluster`), убираются, взамен `hiddenRelations: N`. «Проблемы»: строки по
    `Row.Ref` — только читаемые (scope **и** вид, ревью P3-6); строки со scope `""` — только
    при `cluster`; при обходе дубли (узлы) — по `Row.ID`. `ListObjects` при обходе и при
    `ScopeAll` — строки только читаемых scope-ов (страховка).
12. **Подтверждение в UI (вариант A, пока пользователь не ответил иначе).** Разрушающий план
    без `no_confirm`: `RunAction`/`RunEdit` сразу отвечают `{state: "awaiting_confirmation",
    id}`, ожидание в памяти `agentapi` (≤ 20; сверх — `limit`), событие `agent_pending_changed`.
    UI показывает глобальный диалог (план как в `ActionDialog`/`EditDialog`, имя агента «не
    проверено», цель). «Да» → права и опознание проверяются заново, затем Run сервиса на
    **своём контексте** `agentapi` (не на контексте HTTP-запроса агента — он давно закрыт;
    ревью P3-2): срок как у Run из UI (у drain — `drainRunTimeout`, иначе 60 с), отменяется
    закрытием `agentapi`; прерванная выходом запись — в журнал `unknown`. `DecideAgentPending`
    отвечает сразу, итог — в `GetRun` и событием. «Нет» → `rejected`; 10 мин без решения →
    `expired`.
    Самоподтверждение (ревью P3-4): в desktop-режиме решение принимается только через Wails
    (в процессе); в browser-режиме токен страницы отдаётся `GET /` любому локальному процессу
    (так с P0: страница получает его из `index.html`), поэтому агент, **намеренно** читающий
    страницу UI, может подтвердить себе сам. По «Рамке» это принято: подтверждение — ограждение
    от ошибки агента, не изоляция. Токен не пишется ни в лог запуска, ни в журнал, ни в файл
    (тест). Сказано в документации browser-режима. `GetRun{id}` ждёт до 25 с изменения и отвечает
    итогом, `rejected`, `expired` или `awaiting_confirmation`; неизвестный id (в т.ч. после
    перезапуска) — `gone`. Решённые хранятся 10 мин для `GetRun`. Если пользователь выберет B
    (право = согласие), меняется только это решение: ожиданий нет, разрушающее поимённо —
    остаётся.
13. **Видимость ожидания.** Событие → UI: диалог поверх всего, счётчик у цели в списке целей и в
    строке состояния, `document.title` с «(N)». Desktop: `internal/desktop` подписан на событие,
    ставит заголовок окна «SPK Ocular — ждёт подтверждения (N)» и шлёт уведомление рабочего
    стола через D-Bus `org.freedesktop.Notifications` (если шина жива — проба уже есть;
    окно не выдёргивается). `GET /v1` и `Access` говорят: подтверждение делает человек в UI.
14. **Имя агента — заявленное.** Заголовок `X-Agent-Name` (≤ 64 печатных символа, иначе
    обрезка/замена), без него — `unknown`. В журнале и диалоге — с пометкой «не проверено».
15. **Журнал.** `agent_audit(id, at, agent, method, provider, target, scope, object, verb,
    destructive, expect_hash, phase, outcome, detail, count)`. Записи агента: `intent` до
    отправки (Run, запись после «Да») и `outcome` после (`done`/`refused`/`unknown`/сводка
    частей/`rejected`/`expired`/`forbidden`); отказ в правах — тоже запись. Чтения — одна запись
    на (минута, агент, метод, цель) с `count`. Без тел запросов и значений; `detail` ≤ 500
    символов. Ротация: при вставке раз в 100 — удалить всё сверх 20 000 последних.
16. **Каталог методов — из тех же структур.** Обработчик регистрируется одной записью
    `method{Name, Doc, Verb, Writes, Req, Resp, handle}`; `/v1/methods` строит схемы
    `invopop/jsonschema` по `Req`/`Resp`; тест: каждый маршрут mux-а — запись каталога и
    наоборот, у каждой записи непустые описание и глагол (или `none` для `Access`/самоописания).
17. **Сокет.** `paths.Paths.AgentSocket` = `DataDir/agent.sock`, `AgentLock` =
    `DataDir/agent.sock.lock`. `unix.Flock(LOCK_EX|LOCK_NB)` на открытом lock-файле на всё
    время процесса; взял — удалить старый сокет, `Listen("unix")`, `chmod 0600`; не взял —
    состояние `other_instance`, сервер не поднимается. На каждое соединение `SO_PEERCRED`
    (`unix.GetsockoptUcred`) — uid ≠ свой → соединение закрывается (и запись в журнал без
    агента). Закрытие: `Shutdown` (≤ 3 с), удалить сокет, снять замок. HTTP-сервер с
    `ReadHeaderTimeout` 5 с, тело запроса ≤ 4 MiB (правка YAML ≤ 3 MiB, P9).
18. **Поверхность UI-API.** Новые методы `API` (оба транспорта, `client.ts`, тест маршрутов):
    `AgentAccessStatus`, `ListAgentGrants`, `SaveAgentGrants{provider, target, grants}`
    (заменяет выдачи цели целиком, в одной транзакции; пустой список = отозвать цель),
    `RevokeAllAgentGrants`, `ReconfirmAgentTarget`, `ListAgentPending`, `DecideAgentPending{id,
    approve}`, `ListAgentAudit{agent?, provider?, target?, before?, limit ≤ 500}`. События:
    `agent_grants_changed`, `agent_pending_changed`, `agent_audit_changed` (сведены, ≤ 1/с).
    Без `AgentControl` (тесты сервиса без сокета) методы отвечают `unsupported`.

## Методы сокета (v1)

Все — `POST /v1/<Method>` с JSON, кроме `GET /v1` и `GET /v1/methods`. Цель — `{provider,
target}` (id цели как в UI, плюс её заголовок в `Access`).

| Метод | Глагол | Что |
|---|---|---|
| `GET /v1` | — | кто, версия, как пользоваться, где методы, что подтверждает человек в UI |
| `GET /v1/methods` | — | каталог: имя, описание, схемы запроса/ответа, глагол, пишет ли |
| `Access` | — | выдачи по целям: scope-ы, глаголы, виды, `noConfirm`, состояние (`active`/`suspended`) |
| `ListKinds` | `read` | выданные виды цели (id, заголовок, `scoped`, колонки) и выданные действия (`destructive`) |
| `ListObjects` | `read` | снимок: `{target, kind, scope?, name?, limit?}`; без scope — все выданные |
| `GetObject` | `read` | детали и YAML (фильтр связей), `hiddenRelations` |
| `Problems` | `read` | «Проблемы» выданных scope-ов (+ кластерные при `cluster`) |
| `GetMetrics` | `read` | `{refs ≤ 100}` → использование |
| `GetLogs` | `logs` | хвост: `{ref, channel?, previous?, tailLines?, sinceTime?}` |
| `PrepareAction` | `action:<id>` | план + `planId` |
| `RunAction` | `action:<id>` | `{planId}` → итог или `awaiting_confirmation` |
| `GetEditSource` | `edit` | текст для правки (+ `sourceId` за базой) |
| `PrepareEdit` | `edit` | `{sourceId, edited}` → план (Before/After) + `planId` |
| `RunEdit` | `edit` | `{planId}` → итог или `awaiting_confirmation` |
| `GetRun` | — | `{id}` → ждёт ≤ 25 с: итог / `rejected` / `expired` / `awaiting_confirmation` / `gone` |

Расхождение со спецификацией: фильтр `ListObjects` — только `name` (подстрока имени); фильтра по
метке в v1 нет — в строках (`core.Row`) меток нет, а обещать то, чего не проверить, хуже. Ответ
`ListObjects`: `{columns, rows[{ref, cells, health}], truncated, status{state, coverage},
scopes[{name, state, class?}]}` — при обходе у каждого scope своё состояние.
