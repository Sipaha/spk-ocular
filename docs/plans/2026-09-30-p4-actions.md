# P4 — действия: restart, scale, delete

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`; каждая задача —
> отдельные коммиты `area: summary`, `make check` зелёный перед коммитом; каждое исправление и
> каждая возможность начинаются с теста, который падает без них.

**Цель:** из деталей объекта или прямо из таблицы пользователь перезапускает workload (как
`kubectl rollout restart`), меняет число реплик (scale) и удаляет объект (в том числе pod — ради
пересоздания контроллером). Перед выполнением — подтверждение, в котором явно видно, **где** и
**над чем** действие (context и сервер, namespace, вид, имя) и **что** произойдёт — ровно
настолько, насколько провайдер это знает: стратегия обновления, политика хранения PVC у
StatefulSet, автоскейлер, контроллер pod-а. Проверенные права, непроверенные права и отказ —
три разных состояния. Результат — «запрошено», а не «сделано»; ход виден через существующий
watch. Неизвестный исход (сеть оборвалась после отправки) так и называется.

**Архитектура:** provider-агностичная возможность сессии `Actioner`, протокол без серверного
состояния: `PrepareAction` (только чтение: план — последствия, права, **ожидание** — отпечаток
состояния, от которого зависят последствия) → подтверждение в общем UI → `RunAction` (перечитать
объект, сверить UID и ожидание, записать с предусловием `resourceVersion`). Действия вида —
статически в `KindDescriptor.Actions`. Kubernetes: restart — merge patch аннотации
`kubectl.kubernetes.io/restartedAt`, scale — patch subresource `scale`, delete — `Delete` с
`Preconditions{UID, ResourceVersion}` и фоновым каскадом; права — `SelfSubjectAccessReview`.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` («Kubernetes MVP — функции»:
действия с подтверждением с явным context/namespace/объектом; «Ключевые технические решения» п. 8;
«Принципы»: все contexts RW, отдельной read-only/protected-пометки нет).

## Глобальные ограничения

- Всё из P0–P3 (AGENTS.md «Правила»).
- `internal/core`, `internal/api` и общий UI действий не знают deployment/pod/namespace/PVC:
  действие — `ActionDescriptor`, последствия и предупреждения — строки провайдера, опасность —
  флаг плана. Docker Compose ляжет на тот же контракт (restart, stop/start, rm).
- Все contexts работают в RW-режиме: никакой read-only/protected-пометки (решение пользователя
  2026-09-29, повторено 2026-09-30). Защита — только UX подтверждения.
- Действие выполняется над подтверждённым объектом: `RunAction` требует непустые UID и
  `ConfigRev`, объект читается строго с UID; заменённый одноимённым — `gone`, никогда не «то, что
  сейчас так называется».
- Никаких автоматических повторов изменяющих запросов, кроме повтора после отказа предусловия
  `resourceVersion` (409 — запись не произошла) при неизменном ожидании, ≤ 3 раз.
- Никаких опросов: план читается один раз; ход rollout-а — через существующие виды.
- У каждого запроса к кластеру — контекст и таймаут; у подготовки — общий дедлайн, необязательные
  части (права, HPA, счёт pod-ов) не блокируют план и не роняют его.
- Тесты действий против кластера — **только kind `ocular-dev`**: kind-тесты и скрипты явно берут
  сгенерированный kubeconfig и проверяют, что это он (context `kind-ocular-dev`, сервер на
  loopback), прежде чем что-либо создавать или удалять. Реальные кластеры из kubeconfig
  пользователя не трогаются ни тестами, ни ручными проверками.

## Решения P4 (агент, 2026-09-30; уточнены ревью Codex)

### Какие действия у каких видов

| Вид | restart | scale | delete |
|---|---|---|---|
| Deployments | ✓ (нет, если `spec.paused` — как kubectl) | ✓ | ✓ (каскадно) |
| StatefulSets | ✓ | ✓ (scale down — политика PVC `whenScaled`) | ✓ (каскадно; политика PVC `whenDeleted`) |
| DaemonSets | ✓ | — | ✓ (каскадно) |
| ReplicaSets (скрытый вид) | — | — | ✓ |
| Pods | — | — | ✓ («удалить», контроллер может пересоздать) |
| Services, Ingresses, ConfigMaps, Secrets | — | — | ✓ |
| Namespaces, Nodes, Events | — | — | — |

- Namespaces и Nodes в P4 не удаляются: удаление namespace уничтожает всё внутри, удаление Node ≠
  drain. В бэклог: удаление namespace с вводом имени, cordon/drain. Events не удаляются.
- Scale ReplicaSet-а под Deployment-ом не предлагается (контроллер вернёт).
- Отдельного restart pod-а нет: «удалить» + честное последствие про контроллер.
- Force-delete, массовые действия, журнал действий — в бэклог.

### Контракт

```go
// core
type ActionDescriptor struct {
    ID          string       // "restart" | "scale" | "delete" (Compose: "stop", "start", …)
    Title       string       // подпись провайдера; UI переводит известные ID
    Destructive bool         // базовая опасность (delete); план может её поднять
    Param       *ActionParam // scale: число
}
type ActionParam struct { Kind string /* "count" */; Min, Max int }

type ActionPlan struct {        // ответ PrepareAction
    Ref         Ref             // с UID, прочитанным сейчас (подготовка может закрепить ссылку без UID)
    Action      ActionDescriptor
    Params      ActionParams    // с какими параметрами план посчитан (scale: предлагаемое M)
    Current     *int            // scale: текущее spec.replicas
    Destructive bool            // для этих параметров: delete; scale down с удалением PVC; scale в 0
    Effects     []string        // что произойдёт — только обоснованное
    Warnings    []string        // что может вмешаться (HPA, PDB не учитывается, …)
    Rights      Rights          // {State: allowed|denied|unknown, Reason}
    Unavailable string          // нельзя по состоянию (paused, уже удаляется)
    Expect      string          // непрозрачный отпечаток значимого состояния; уходит в RunAction
}
type ActionResult struct { Message string } // «запрошено»

// provider
type Actioner interface {
    PrepareAction(ctx, ref Ref, action string, p ActionParams) (core.ActionPlan, error)
    RunAction(ctx, ActionRun) (core.ActionResult, error) // Ref(UID), Action, Params, Expect
}
type ActionParams struct { Count *int `json:"count,omitempty"` }
```

- **Ожидание (`Expect`).** Провайдер кладёт в план канонический отпечаток **действия, его
  параметров** (план «M = 3» не подходит к выполнению «M = 0») и полей, от которых
  зависят показанные последствия (k8s: UID, `spec.replicas`, `spec.paused`, `deletionTimestamp`,
  стратегия обновления и partition, политика PVC и наличие `volumeClaimTemplates`, контроллер
  pod-а). `RunAction` перечитывает объект (строго с UID), считает отпечаток заново: не совпал →
  `conflict` «объект изменился после проверки: …» — пользователь смотрит план заново; старое
  обещание не используется молча. Шум status (число готовых pod-ов и т.п.) в отпечаток не входит.
  Клиент может подделать `Expect` — это меняет только его собственное подтверждение.
- **Сессия.** `PrepareAction` берёт **одну** запись сессии и из неё же — план, подпись context-а,
  сервер и `ConfigRev`. `RunAction`: под `sessMu` найти текущую запись target-а, сверить
  `ConfigRev` (не совпал/нет — `conflict` «конфигурация context-а изменилась — проверьте действие
  заново»), взять её сессию, отпустить блокировку и выполнять **на этой** сессии; смена
  конфигурации после начала выполнения его не перенаправляет и не превращает удачный результат
  в конфликт. Сессия, закрытая reaper-ом и открытая заново с той же конфигурацией, даёт тот же
  `ConfigRev` — план остаётся действителен; перезапуск приложения меняет ключ HMAC — старые
  планы недействительны. `ConfigRev` отражает настройки context-а, а не обновления токенов/
  exec-плагинов — так и документируется.
- **Проверка запроса в `RunAction`** (без доверия клиенту): провайдер/target/scope/kind/name/UID
  непустые и согласованные; действие есть в `KindDescriptor.Actions` вида; параметры — только
  нужные действию (у restart/delete параметров нет — лишние → `bad_request`), count целый в
  `[Min, Max]` (k8s: 0…10 000); `Expect` непустой. Невалидный запрос — ноль изменяющих вызовов.
  `Denied`/`Unavailable`/последствия от клиента не принимаются — провайдер проверяет состояние
  заново (paused, удаляется).
- **Параметры и двухшаговый scale.** Последствия scale зависят от M, поэтому диалог scale —
  «ввод → просмотр»: шаг 1 — поле числа (Enter/«Далее» → `PrepareAction` с M), шаг 2 — план для
  M (N → M, PVC, 0, HPA) и «Подтвердить». Смена M возвращает к шагу 1. restart/delete — сразу
  просмотр.

### Kubernetes: выполнение

- Общая схема `RunAction`: GET (строго UID) → проверка состояния и `Expect` → запись с
  предусловием `resourceVersion` из этого GET → отказ предусловия версии (delete/restart: 409;
  scale: 422 провала `test`) повторяется с начала, ≤ 3 раз, **только когда доказано, что записи
  не было и изменилась лишь версия**: перечитанный объект — тот же UID, тот же `Expect`, другой
  `resourceVersion`. Иначе — `gone` / `conflict` / исходная ошибка. Любые другие 422/409 не
  повторяются.
- **restart**: JSON merge patch `{"metadata":{"uid":U,"resourceVersion":RV},"spec":{"template":
  {"metadata":{"annotations":{"kubectl.kubernetes.io/restartedAt":<RFC3339Nano>}}}}}`. Merge patch
  сливает map-ы — чужие аннотации не стираются. `RFC3339Nano` (совместим с RFC3339) — два
  restart в одну секунду не склеиваются в один. Запасной путь через JSON Patch не нужен (спайк).
- **scale**: JSON Patch на subresource `scale`: `test /metadata/uid`, `test /metadata/resourceVersion`,
  `test /spec/replicas = Current`, `replace /spec/replicas = M` (Scale несёт метаданные
  родителя — `scaleFromDeployment`). Провал `test` у replicas/RV — `conflict`, не `gone`.
- **delete**: `Delete(name, {Preconditions: {UID, ResourceVersion}, PropagationPolicy: Background})`.
  Результат — «удаление запрошено» (финализаторы, grace-период и контроллеры могут держать
  объект — это видно в таблице).
- **Классификация ошибок записи**: 403 → `forbidden` (с правом); 404 → `gone` («уже удалён»);
  409 → повтор по схеме выше, иначе `conflict` (сохраняя причину); 422 → один GET: объекта нет
  или UID другой → `gone`, иначе исходная ошибка с причиной (`bad_request`/валидация/admission).
  Таймаут и обрыв после отправки — `unknown` («результат неизвестен — проверьте объект, прежде чем
  повторять»); никаких автоматических повторов.
- **Последствия — только обоснованные** (формулировки «запрошено», «может»):
  - restart Deployment: RollingUpdate — «pod-ы будут заменены постепенно (maxUnavailable …)»;
    Recreate — «все pod-ы остановятся, затем запустятся новые»; `replicas = 0` — «запущенных pod-ов
    нет: изменится только шаблон».
  - restart StatefulSet: RollingUpdate — «pod-ы заменяются по одному, от старшего номера»;
    с partition P — «только pod-ы с номером ≥ P»; OnDelete — «существующие pod-ы не перезапустятся,
    пока их не удалят». DaemonSet: RollingUpdate / OnDelete так же.
  - scale: «N → M реплик»; M = 0 — план опасный, «все pod-ы будут остановлены»; StatefulSet при
    M < N и `whenScaled=Delete` — «PVC pod-ов с номерами M…N-1 будут удалены (судьба данных — по
    reclaim policy тома)», опасный; при `Retain` — «PVC останутся», а если `whenDeleted=Delete` —
    «останутся до удаления StatefulSet (тогда удалятся вместе с ним)»: kind показал, что
    сохранённые при scale down PVC сохраняют ownerReference на StatefulSet и уходят при его delete.
  - delete StatefulSet: `whenDeleted=Delete` — «PVC шаблонов будут удалены (…reclaim policy)»;
    `Retain` или политики нет — «PVC останутся»; нет `volumeClaimTemplates` — о PVC ни слова.
  - delete workload: «pod-ы будут удалены (сейчас их N)» — N из ограниченного LIST по UID
    контроллера, без него — без числа.
  - delete pod: контроллер ReplicaSet/StatefulSet/DaemonSet, существующий и не удаляемый, —
    «<Kind> <имя> обычно создаёт замену»; Job — «Job может создать новый pod, если не завершён»;
    незнакомый владелец — «принадлежит <Kind> <имя>: пересоздание зависит от него»; без владельца —
    «pod не будет пересоздан». Всегда: «это не eviction — PodDisruptionBudget не учитывается».
  - delete ReplicaSet с владельцем — «Deployment <имя> может создать его заново».
- **HPA**: при подготовке scale и restart — LIST `autoscaling/v2 horizontalpodautoscalers` в
  namespace по страницам (≤ 5 × 500, в пределах дедлайна); совпадение по `scaleTargetRef`
  (group из apiVersion + kind + name). Найден — «HPA <имя> может перезаписать число реплик
  (min–max)»; LIST запрещён/неполон — предупреждение «проверить автоскейлеры не удалось»
  (не «автоскейлеров нет»).
- **Права**: SSAR `ResourceAttributes{Verb, Group, Resource, Subresource, Namespace, Name}` —
  restart: patch deployments; scale: patch deployments + subresource scale; delete: delete. Итог —
  `allowed` / `denied` (+ причина, кнопка неактивна) / `unknown` (SSAR не удался — выполнить можно,
  UI не говорит «права проверены»). SSAR не гарантирует admission/квоты, права могут измениться
  до выполнения — ошибка выполнения всё равно показывается.
- **Дедлайн подготовки**: GET — обязательный (его ошибка — ошибка плана); SSAR, HPA, счёт pod-ов
  — параллельно в пределах 5 с, опоздавшие — «неизвестно».

### Спайк предусловий на kind (2026-09-30)

- Merge patch с `metadata.uid` старого объекта на одноимённую замену: `422 Invalid — metadata.uid:
  field is immutable`, новый объект не изменён; с верным UID — проходит.
- JSON Patch на `deployments/<name>/scale` с `test /metadata/uid` старого UID: `422` «the server
  rejected our request due to an error in our request» (без причины), с верным — проходит.
- Отсюда: 422 после записи различается одним GET (см. классификацию), запасной путь restart
  не нужен.

### UI

- **Меню «Действия»** в заголовке деталей — пункты из `KindDescriptor.Actions`; цель — **текущий**
  объект деталей (после перехода по связям — он, а не исходный).
- **Контекстное меню строки** (правый клик, `ContextMenu`/`Shift+F10`): цель — строка, по которой
  кликнули (не ранее выбранная); `Ref` с UID фиксируется в момент открытия. Пункты: «Детали»,
  «Логи», «Терминал», затем действия. Клавиша `Delete` — только при фокусе в теле таблицы (не в
  полях ввода, терминале, CodeMirror, диалогах) → подтверждение удаления выбранной строки.
  Остальные горячие клавиши и палитра — P5.
- **Диалог** (модальный, ловушка фокуса, Esc — отмена, пока не идёт выполнение):
  - блок «где»: context, сервер, namespace, вид, имя — моноширинно; «что»: последствия,
    предупреждения; права: «проверены» / «нет права …» / «не удалось проверить»;
  - опасный план (`plan.Destructive`) — красная кнопка, фокус на «Отмена»; иначе — фокус на кнопке;
    Enter, пришедший из открывшего меню нажатия (повтор клавиши), не подтверждает;
  - поздний ответ подготовки не подменяет объект уже открытого диалога (поколение);
  - выполнение: синхронный замок на клиенте (ref, не только disabled-кнопка) — один `RunAction`
    на подтверждение; диалог не закрывается, пока ответ не пришёл (ограничено таймаутом);
    ошибка — в диалоге; `unknown` — «результат неизвестен…» и «Закрыть»; `conflict` по
    ожиданию/конфигурации — «Проверить заново» (новая подготовка).
- **Результат**: уведомление в строке состояния (~5 с): «Deployment web: restart requested»,
  «Pod web-…: deletion requested». Детали удалённого объекта — проверить нынешнее поведение
  (Terminating виден; исчезнувший — явное «объект удалён», а не ошибка).
- Меню и диалог не знают Kubernetes: подписи действий по ID (i18n ru/en, иначе `Title`), вид —
  `KindDescriptor.Title`.

  подменён; reaper + повторное открытие с той же конфигурацией → действителен; target удалён →

## Ревью плана (Codex, 2026-09-30)

Девять замечаний к первой версии (26fcebc), все приняты по существу и внесены выше:
1. P1 — «PVC останутся» ложно при `persistentVolumeClaimRetentionPolicy` `Delete` (и scale down
   при `whenScaled=Delete`) → политика читается, последствия для delete и scale down, отпечаток в
   `Expect`, kind-тест жизненного цикла PVC.
2. P1 — выполнение без UID превратилось бы в «действие над тем, что сейчас так называется» →
   `RunAction` требует UID/`ConfigRev`/`Expect`, строгое чтение, полная проверка запроса, ноль
   вызовов на невалидном.
3. P1/P2 — план и `ConfigRev` из одной записи сессии; выполнение на захваченной сессии, граница
   гонки определена; `ConfigRev` не обещает отслеживать обновления токенов.
4. P2 — «N → M» мог стать «100 → M» → `test /spec/replicas` + отпечаток; провал — `conflict`.
5. P2 — последствия были сильнее правды (OnDelete, partition, replicas 0, контроллер pod-а,
   фоновое удаление, PDB) → формулировки по стратегии, «запрошено», «может».
6. P2 — не сводить 422/409/`test` к «заменён» → классификация через GET; повтор только после
   отказа предусловия версии; `RFC3339Nano` против склейки двух restart в одну секунду.
7. P2 — неизвестный исход и повторная отправка → класс `unknown` без повторов, синхронный замок
   клиента, диалог держится до ответа.
8. P2 — «права неизвестны» ≠ «разрешено»; атрибуты SSAR раздельно; HPA по страницам и «проверить
   не удалось»; дедлайн подготовки.
9. P2 — последствия зависят от параметра → двухшаговый scale с подготовкой под M, опасность —
   у плана; цель меню — строка под курсором / текущий объект деталей; `Delete` не всплывает из
   полей и терминала.
