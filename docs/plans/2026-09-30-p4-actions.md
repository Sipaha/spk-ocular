# P4 — действия: restart, scale, delete

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`; каждая задача —
> отдельные коммиты `area: summary`, `make check` зелёный перед коммитом; каждое исправление и
> каждая возможность начинаются с теста, который падает без них.

**Цель:** из деталей объекта или прямо из таблицы пользователь перезапускает workload (как
`kubectl rollout restart`), меняет число реплик (scale) и удаляет объект (в том числе pod — ради
пересоздания контроллером). Перед выполнением — подтверждение, в котором явно видно, **где** и
**над чем** действие: context (и сервер), namespace, вид, имя, а также что произойдёт
(«ReplicaSet web-… создаст новый pod», «HPA web управляет репликами 2–10 — ручной scale будет
перезаписан», «pod-ы будут пересозданы по стратегии rollout-а»). Нет прав — видно до
подтверждения. Результат и ошибки видны по-человечески; таблица и детали отражают изменения
через уже существующий watch.

**Архитектура:** provider-агностичная возможность сессии `Actioner` с двухшаговым протоколом:
`PrepareAction` (ничего не меняет: текущее состояние, последствия, права) → подтверждение в
общем UI → `RunAction` (выполнение с предусловием «тот же объект» по UID). Какие действия есть у
вида — статически в `KindDescriptor.Actions` (UI рисует меню без запросов). Kubernetes: restart —
merge-patch аннотации `kubectl.kubernetes.io/restartedAt` в шаблоне pod-а, scale — patch
subresource `scale`, delete — `Delete` с `Preconditions{UID}` и фоновым каскадом; права —
`SelfSubjectAccessReview`.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` («Kubernetes MVP — функции»:
действия с подтверждением с явным context/namespace/объектом; «Ключевые технические решения» п. 8;
«Принципы»: все contexts RW, отдельной read-only/protected-пометки нет).

## Глобальные ограничения

- Всё из P0–P3 (AGENTS.md «Правила»).
- `internal/core`, `internal/api` и общий UI действий не знают deployment/pod/namespace: действие —
  `ActionDescriptor{ID, Title, Destructive, Param}`, последствия — строки провайдера, scope —
  подпись из `Ref.Scope`. Docker Compose ляжет на тот же контракт (restart, stop/start, rm).
- Все contexts работают в RW-режиме: никакой read-only/protected-пометки, никаких «опасных»
  context-ов (решение пользователя 2026-09-29, повторено 2026-09-30). Защита — только UX
  подтверждения.
- Действие выполняется по явной паре (сессия target-а, `Ref` с UID), никогда через «текущий
  выбор» (спецификация «Живые таблицы»). Объект, заменённый одноимённым, — `gone`, а не действие
  над новым.
- Никаких опросов: последствия и права читаются один раз при подготовке; ход rollout-а виден через
  существующие виды (health `progressing`), отдельного «ожидания завершения» нет.
- У каждого запроса к кластеру — контекст и таймаут (`getTimeout`).
- Тесты действий против кластера — **только kind `ocular-dev`**; реальные кластеры из kubeconfig
  пользователя не трогаются ни тестами, ни ручными проверками.

## Решения P4 (агент, 2026-09-30)

### Какие действия у каких видов

| Вид | restart | scale | delete |
|---|---|---|---|
| Deployments | ✓ (нет, если `spec.paused` — как kubectl) | ✓ | ✓ (каскадно) |
| StatefulSets | ✓ | ✓ | ✓ (каскадно; PVC остаются — сказано в последствиях) |
| DaemonSets | ✓ | — | ✓ (каскадно) |
| ReplicaSets (скрытый вид) | — | — | ✓ (если есть владелец — «Deployment создаст заново») |
| Pods | — | — | ✓ («удалить и пересоздать», если есть контроллер; иначе «не вернётся») |
| Services, Ingresses, ConfigMaps, Secrets | — | — | ✓ |
| Namespaces, Nodes, Events | — | — | — |

- Namespaces и Nodes в P4 не удаляются: удаление namespace уничтожает всё внутри (радиус
  несопоставим с остальными действиями), удаление Node ≠ drain (pod-ы остаются работать без
  учёта). В бэклог: удаление namespace с вводом имени, cordon/drain. Events не удаляются (служебные
  объекты, истекают сами).
- Scale ReplicaSet-а под Deployment-ом бессмыслен (контроллер вернёт) — не предлагается.
- restart pod-а как отдельного действия нет: у pod-а «удалить» и есть пересоздание; диалог говорит,
  кто его пересоздаст (контроллер по `ownerReferences`), или что bare pod не вернётся.
- Force-delete (grace 0) застрявших в Terminating pod-ов, массовые действия по выделению — в
  бэклог.

### Provider API

```go
// core
type ActionDescriptor struct {
    ID          string       // "restart" | "scale" | "delete" (Compose: "stop", "start", …)
    Title       string       // подпись провайдера; UI переводит известные ID
    Destructive bool         // подтверждение с опасной кнопкой, фокус на «Отмена»
    Param       *ActionParam // scale: число
}
type ActionParam struct { Kind string /* "count" */; Min, Max int }
type ActionPlan struct {       // ответ PrepareAction
    Ref        Ref             // с UID, прочитанным сейчас
    Action     ActionDescriptor
    Current    *int            // scale: текущее spec.replicas
    Effects    []string        // последствия, по строке
    Warnings   []string        // например, HPA перезапишет scale
    Denied     string          // права: почему нельзя (RBAC); "" — можно или неизвестно
    Unavailable string         // нельзя по состоянию (paused, удаляется)
}
type ActionResult struct { Message string }

// provider
type Actioner interface {
    PrepareAction(ctx, ref Ref, action string) (core.ActionPlan, error)
    RunAction(ctx, ref Ref, action string, params ActionParams) (core.ActionResult, error)
}
type ActionParams struct { Count *int }
```

- `KindDescriptor.Actions []ActionDescriptor` — статический список; UI не показывает меню у вида
  без действий.
- API: `PrepareAction(ActionRequest{Ref, Action})` → `ActionPlan` + сведения о target-е
  (подпись context-а, сервер/endpoint, `configRev`); `RunAction(ActionRun{Ref, Action, Params,
  ConfigRev})`. Сервис сверяет `ConfigRev` с текущей сессией target-а: конфигурация сменилась
  между подтверждением и выполнением → `conflict` «конфигурация context-а изменилась — проверьте
  действие заново» (пользователь подтверждал другой сервер/учётку). Без серверного состояния
  (токенов/хэндлов): подготовка ничего не резервирует, выполнение самодостаточно.
- Параметры проверяются в API и в провайдере: count — целое в `[Min, Max]` (k8s: 0…10 000;
  больше — почти наверняка опечатка).

### Kubernetes: выполнение и предусловия

- **restart** (Deployment/StatefulSet/DaemonSet): JSON merge patch
  `{"metadata":{"uid":U},"spec":{"template":{"metadata":{"annotations":{"kubectl.kubernetes.io/restartedAt":<RFC3339>}}}}}`.
  Merge patch сливает map-ы — чужие аннотации не стираются (в отличие от JSON Patch `add` на
  отсутствующий родитель). `metadata.uid` в патче — предусловие: у заменённого объекта UID другой,
  apiserver отвергает изменение неизменяемого поля (422) → `gone`. **Проверяется на kind в Task 3**;
  если apiserver не отвергает — запасной путь: JSON Patch `[test /metadata/uid, add …]` с двумя
  вариантами (аннотации есть / нет) и повтором при расхождении. Paused Deployment → `Unavailable`
  (kubectl тоже отказывает).
- **scale**: JSON Patch на subresource `scale`: `[{"op":"test","path":"/metadata/uid","value":U},
  {"op":"replace","path":"/spec/replicas","value":N}]`. `test` сверяет UID самого объекта (Scale
  несёт метаданные родителя) без `resourceVersion` — частые изменения status не дают ложных
  конфликтов. Проверяется на kind. `Current` — из `spec.replicas` объекта (GET).
  Последствия: «N → M реплик»; M = 0 — предупреждение «все pod-ы будут остановлены».
- **delete**: `Delete(name, {Preconditions: {UID}, PropagationPolicy: Background})` — как kubectl
  по умолчанию. Последствия: pod с контроллером — «<Kind> <name> создаст новый pod»; bare pod —
  «pod не будет пересоздан»; workload — «удалит N pod-ов» (N — из уже известных связей, без
  отдельного LIST, если не дорого: один LIST по UID контроллера, ограниченный); StatefulSet —
  «PersistentVolumeClaim-ы останутся»; объект уже удаляется (`deletionTimestamp`) — `Unavailable`.
- **HPA**: при подготовке scale — один LIST `autoscaling/v2 horizontalpodautoscalers` в namespace
  (≤ 1 страницы, таймаут); HPA с `scaleTargetRef` на объект → предупреждение «HPA <имя> управляет
  репликами (min–max): ручной scale будет перезаписан». Нет прав на LIST HPA — предупреждения нет
  (не ошибка).
- **Права**: `SelfSubjectAccessReview` (verb/resource/subresource/namespace/name) при подготовке:
  restart → `patch` на ресурс; scale → `patch` на `<ресурс>/scale`; delete → `delete`. Отказ →
  `Denied` («нет права delete на pods в ocular-demo»), кнопка подтверждения неактивна. Ошибка
  самого SSAR → права «неизвестны», выполнение разрешено (ошибка придёт от выполнения).
- **Ошибки выполнения**: 403 → `forbidden` с тем же текстом о праве; 404 → `not_found`
  («уже удалён»); предусловие UID / `test` → `gone` («объект заменён новым с тем же именем»);
  409 → `conflict`; прочее — `classify`.

### UI

- **Меню «Действия»** в заголовке деталей (кнопка с подписью, не «…»: «…» уже у терминала)
  — пункты из `KindDescriptor.Actions`; destructive — красным.
- **Контекстное меню строки таблицы** (правый клик, клавиша `ContextMenu`/`Shift+F10`): «Детали»,
  «Логи», «Терминал», затем действия. Клавиша `Delete` на выбранной строке → подтверждение удаления.
  Остальные горячие клавиши и команды палитры — P5.
- **Диалог подтверждения** (общий для всех действий): заголовок «Delete pod web-…?» / «Restart
  deployment web?» / «Scale deployment web»; блок «где»: context (+ сервер), namespace, вид, имя —
  крупно и моноширинно; последствия и предупреждения; для scale — числовое поле (по умолчанию
  текущее значение, Enter подтверждает), «N → M»; `Denied`/`Unavailable` — сообщение и неактивная
  кнопка. Фокус: у destructive — на «Отмена» (Enter не удаляет случайно), у остальных — на кнопке
  действия/поле. Esc закрывает. Во время выполнения кнопка занята, повторный клик невозможен.
  Ошибка выполнения — в диалоге (он остаётся открытым; `gone`/`not_found` — «Закрыть»).
- **Результат**: уведомление в строке состояния (`role=status`, ~5 с): «Deployment web: restart
  requested», «Pod web-…: deleted». Детали удалённого объекта: объект в Terminating виден как
  есть; после исчезновения детали показывают «объект удалён» (проверить нынешнее поведение, при
  необходимости — явное состояние вместо ошибки).
- Меню и диалог не знают Kubernetes: подписи действий — по ID (i18n ru/en, иначе `Title`
  провайдера), вид — `KindDescriptor.Title` в единственном числе (поле `Singular`, если нужно).

- [ ] `internal/api`: `PrepareAction`, `RunAction` (сверка `ConfigRev`, проверка параметров,

- [ ] Тесты (фейковый провайдер): подготовка отдаёт план с target-ом; выполнение с устаревшим

  неизвестное действие → `unsupported`; действие по ref другого target-а — в своей сессии.

### Task 2. Kubernetes: restart, scale, delete
- [ ] `actions.go`: дескрипторы в `kindDef`, `PrepareAction` (GET с UID, `Current`, последствия,
  HPA, SSAR, `Unavailable`), `RunAction` (patch/scale/delete с предусловиями), классификация
  ошибок.
- [ ] Тесты на dynamic fake (+ reactor-ы для subresource scale и SSAR): тела патчей (аннотация,

### Task 3. kind
- [ ] `TestKindAction*` на `ocular-dev`, объекты создаются тестом в своём namespace и удаляются:
  restart Deployment → новая ReplicaSet, pod-ы заменены, аннотация одна; restart StatefulSet и
  DaemonSet; scale Deployment 1 → 3 → 0 и StatefulSet; delete pod под ReplicaSet → новый pod,
  bare pod → не вернулся; delete Deployment каскадно; **замена одноимённым объектом**: действие со
  старым UID → `gone`, новый объект не изменён (restart, scale, delete) — здесь же решается
  судьба запасного пути restart; HPA → предупреждение; paused Deployment → `Unavailable`.
- [ ] RBAC: пользователь `ocular-viewer` (`kind-rbac.sh`) — `Denied` при подготовке и `forbidden`
