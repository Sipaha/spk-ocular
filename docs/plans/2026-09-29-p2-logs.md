# P2 — логи контейнеров

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`; каждая задача —
> отдельные коммиты `area: summary`, `make check` зелёный перед коммитом.

**Цель:** из таблицы или деталей pod-а / workload-а пользователь открывает логи во вкладке
нижней панели: последние N строк, затем живой follow; выбор контейнера (или все), previous,
since, агрегация всех pod-ов workload-а в один поток с цветным префиксом источника, метки
времени, поиск и фильтр, уровни, ANSI-цвета, копирование и сохранение. Поток переживает
рестарт контейнера и rollout (новые pods подхватываются), ошибки (нет прав, контейнер ещё не
стартовал, previous нет) показываются по-человечески, а не пустым окном.

**Архитектура:** provider-агностичная возможность `LogSource` + общий слой потоков
`internal/streams` (loopback HTTP с токеном, NDJSON-кадры, сброс с коалесцированием).
Kubernetes-адаптер реализует `LogSource` поверх `pods/log` (REST-клиент, без typed clientset).
UI — порт пайплайна логов SPK-launcher (код пользователя, переносится как есть и
адаптируется): `useLogStream`, `useLogFilter`, `LogViewport`, `logSelection`, `LogViewer`.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` (разделы «Потоки», «Provider API»).

## Глобальные ограничения

- Всё из P0/P1 (AGENTS.md «Правила»).
- `internal/core`, `internal/streams`, общий UI логов не знают про pod/container/namespace:
  источник логов — непрозрачный `key` + человекочитаемая `label`, выбор «контейнера» —
  список `LogChannel` от провайдера.
- Потоки — только через loopback-сервер с токеном, никогда через `wails://` (WebKitGTK:
  Blob-тела и буферизация стримов; см. AGENTS.md).
- Никаких опросов кластера: смена контейнера/pod-ов узнаётся из informer-кэша pods (аренда),
  а не периодическим GET.
- У каждого запроса к кластеру — контекст; у открытия лог-потока — дедлайн на заголовки (как у
  watch), у самого потока клиентского таймаута нет (`rest.Config.Timeout` не ставится).
- Ограничения памяти не ухудшают UX, но худший случай ограничен: клиентский буфер ≤ 50k строк
  **и** ≤ 64 МБ текста (старые строки уходят первыми, в статусе видно «обрезано»); строка
  длиннее 1 МиБ обрезается с пометкой.

## Решения P2 (агент, 2026-09-29)

- **Один запрос вместо «backlog + follow».** Launcher делил поток на два запроса из-за
  `wails://`-моста, который обрезал поток, выдавший backlog и замолчавший. У нас поток идёт по
  loopback HTTP, где этой проблемы нет; поэтому клиент открывает один поток, а шов «backlog →
  живой хвост» закрывает backend (ниже). Порт `useLogStream` упрощается: без hold/overlap.
- **Backend владеет жизнью источников.** Разрыв потока kube (рестарт контейнера, таймаут
  apiserver, сетевой сбой) backend переоткрывает сам — с `sinceTime` = последняя метка
  источника и отбрасыванием уже отданных строк (метки у kube с наносекундами, а `sinceTime` —
  до секунды: отбрасываются строки с меткой < последней и уже виденные строки с равной
  меткой). Клиент переподключается только при обрыве самого loopback-потока (закрытие
  сессии — `gone`, выход приложения), и тоже с «продолжить с метки».
- **Метки времени запрашиваются всегда** (`timestamps=true`): они нужны для шва, слияния
  источников и переключателя «время» в UI; в кадре метка отделена от текста.
- **Агрегация на backend-е.** Backlog всех источников читается параллельно (ограниченный пул)
  без follow, сливается по метке времени (k-way merge) и обрезается до последних N строк в
  сумме (запрос — N на источник, поэтому результат точный); затем follow каждого источника с
  его последней метки. Порядок живых строк разных источников — порядок прихода (как stern).
- **Источники workload-а — живые.** Pods workload-а — по UID контроллера (Deployment → RS →
  Pod, как в связях P1) из informer-кэшей pods/replicasets (аренды на время потока). Новый
  pod (rollout, scale) — новый источник с `sinceTime` = момент его появления; удалённый —
  источник завершается с понятным статусом. Лимит одновременных источников — 20
  (`kubectl --max-log-requests` по умолчанию 5; у нас больше, потому что UI агрегирует) — при
  превышении статус потока говорит «показаны 20 из K», выбор — по свежести pod-ов.
- **Контейнер.** Выбор: конкретный контейнер (по умолчанию — аннотация
  `kubectl.kubernetes.io/default-container`, иначе первый обычный) или «все контейнеры»
  (агрегация контейнеров pod-а тем же механизмом). Init- и ephemeral-контейнеры — в списке с
  пометкой. Для workload-а список контейнеров — из шаблона pod-а.
- **Previous** — только для одного pod-а и конкретного контейнера (как kubectl); без follow.
  «Нет предыдущего контейнера» — понятный статус, не ошибка-стена.
- **Рестарт контейнера во время follow.** Поток kube кончается, когда контейнер завершился;
  источник переходит в `waiting` («контейнер завершился (exit 1), ждём рестарта») и
  переоткрывается, когда кэш pods покажет новый запуск (`restartCount`/`state.running`).
  CrashLoopBackOff так и выглядит: строки запуска, статус ожидания, снова строки.
- **Классы ошибок источника:** `forbidden` (нет `pods/log`), `waiting` (ContainerCreating /
  образ не скачан — 400 «is waiting to start»), `not_found` (pod удалён), `unavailable`
  (сеть), `bad_request` (previous нет и пр.). Запрет не выглядит пустым окном.
- **Протокол потока — NDJSON по chunked HTTP**, кадры батчатся (сброс не чаще ~50 мс или по
  32 КБ): `source` (id, key, label), `lines` (id источника + массив [метка, текст]), `state`
  (источник или поток целиком: streaming/waiting/ended/error + класс + сообщение), `ready`
  (backlog выдан — дальше живые строки), `end`. Текст — как есть, с ANSI; невалидный UTF-8
  заменяется на U+FFFD (JSON).
- **Открытие потока — через API**, а не параметрами URL: `OpenLogStream(ref, query)` проверяет
  запрос, привязывает поток к инкарнации сессии и возвращает одноразовый id (подключиться за
  30 с); UI делает `GET <streamBase>/logs/<id>`. Закрытие сессии (смена конфигурации,
  выбор другого target-а) завершает её потоки кадром `end{gone}`.
- **Loopback-сервер** (модель `internal/media/loopback.go` spk-mm-client): в desktop —
  `127.0.0.1:<случайный порт>`, стартует при первом `StreamBase`, токен 32 байта в пути
  (сравнение за постоянное время), проверка `Host`, только GET (+ POST сохранения), `no-store`,
  CORS только для origin страницы desktop (`wails://wails`) — токен в пути, поэтому запросы
  «простые», без preflight. В browser-режиме — тот же обработчик под `/streams/<token>` на
  основном сервере (тот же origin). Код клиента один: `fetch(streamBase + '/logs/' + id)`.
  Работу fetch-стрима из `wails://` к `http://127.0.0.1` в WebKitGTK проверяет спайк Task 1
  до остального кода.
- **UI — нижняя панель вкладок** (как в Lens; её же займут терминалы P3): вкладка на поток,
  заголовок «pod/контейнер» или «deploy/имя», высота панели запоминается (`ui_prefs`).
  Точки входа: в деталях pod-а — контейнеры с кнопкой «Логи», у workload-а — «Логи»;
  клавиша `L` на выбранной строке pods/workloads. Вкладки живут, пока открыты (поток
  продолжает идти и во вкладке в фоне; буфер ограничен).
- **ANSI** — свой маленький разборщик SGR (16/256/truecolor, bold/dim/italic/underline/
  inverse) в сегменты; прочие CSI, OSC (в т.ч. гиперссылки) и одиночные ESC вырезаются.
  Поиск, фильтр, уровни и копирование работают по тексту без ANSI; разбор в сегменты — только
  для отрисованных строк. `\r\n` → `\n`, одиночный `\r` в строке — как есть (без эмуляции
  терминала).
- **Сохранение в файл:** в browser-режиме — Blob-скачивание; в desktop (у WebKitGTK нет
  менеджера загрузок) — `POST <streamBase>/save` со строковым телом, backend пишет в каталог
  загрузок (XDG `DOWNLOAD`, иначе `~/Downloads`), UI показывает путь.
- **Синтетический провайдер для герметичного e2e.** Только с `--test-api`: provider `synthetic`
  с одним target-ом и объектами, у которых есть детерминированные логи (ANSI, уровни, длинные
  строки, «рестарт», агрегат из трёх источников). Так `make check` проверяет лог-вьюер без
  кластера — и заодно доказывает, что UI логов не знает про Kubernetes.

## Provider API (дополнение)

```go
// core
type LogChannel struct { // что можно выбрать в «контейнере»
    ID, Title string
    Note  string // "init", "ephemeral", ""
}
type LogInfo struct {
    Channels       []LogChannel
    DefaultChannel string
    Aggregate      bool // объект — группа источников (workload)
    Previous       bool // поддерживается previous
}

// provider
type LogQuery struct {
    Channel   string    // "" = по умолчанию, "*" = все
    Previous  bool
    Follow    bool
    TailLines int       // 0 = все (ограничено 50k)
    Since     time.Duration
    SinceTime time.Time // продолжение после обрыва (перекрывает Since)
}
type LogSink interface { // вызывается из одной горутины потока, может блокировать (обратное давление)
    Source(id int, key, label string) error
    Lines(id int, lines []LogLine) error
    State(id int, st LogState) error // id 0 = поток целиком
    Ready() error
}
type LogSource interface {
    LogInfo(ctx context.Context, ref core.Ref) (core.LogInfo, error)
    StreamLogs(ctx context.Context, ref core.Ref, q LogQuery, sink LogSink) error // до ctx или конца
}
```

## Задачи

### Task 1: спайк — fetch-стрим из desktop к loopback

      под Xvfb в desktop: fetch из `wails://` к `http://127.0.0.1:<port>/<token>/…` читается
      потоково (строки приходят по одной, не пачкой в конце), CORS-заголовок нужен/достаточен,
      скрытое окно не копит данные бесконечно. Итог — `docs/spikes/2026-09-29-log-stream-desktop.md`.
      Если не работает — альтернатива (WebSocket на тот же loopback) до продолжения.

- [ ] `internal/streams`: реестр потоков (одноразовый id, TTL подключения 30 с, привязка к

## Review Focus

1. Шов backlog → follow и переоткрытия: ни потерь, ни дублей (равные метки, рестарт, обрыв).
2. Жизнь потоков: закрытие вкладки/сессии/приложения освобождает всё (запросы kube, аренды
   кэшей, горутины), одноразовые id, лимиты.
3. Безопасность loopback-сервера: токен, Host, CORS, отсутствие токена в логах.
4. Обратное давление: медленный/скрытый UI не раздувает память backend-а.
5. Агрегация: порядок backlog-а, живой набор pods, лимит источников и честный статус.
6. UI: follow/отрыв, выделение и копирование при идущем потоке, производительность на 50k строк.
