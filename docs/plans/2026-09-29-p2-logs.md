# P2 — логи контейнеров

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`; каждая задача —
> отдельные коммиты `area: summary`, `make check` зелёный перед коммитом.

**Цель:** из таблицы или деталей pod-а / workload-а пользователь открывает логи во вкладке
нижней панели: последние N строк, затем живой follow; выбор контейнера (или все), previous,
since, агрегация всех pod-ов workload-а в один поток с цветным префиксом источника, метки
времени, поиск и фильтр, уровни, ANSI-цвета, копирование и сохранение. Поток переживает
рестарт контейнера и rollout (новые pods подхватываются), ошибки (нет прав, контейнер ещё не
стартовал, previous нет) показываются по-человечески, а не пустым окном.

**Архитектура:** provider-агностичная возможность `LogSource` + общий слой потоков
`internal/streams` (loopback HTTP с токеном, NDJSON-кадры, коалесцирующий сброс с «толчком»).
Kubernetes-адаптер реализует `LogSource` поверх `pods/log` (REST-клиент, без typed clientset).
UI — порт пайплайна логов SPK-launcher (код пользователя, переносится и адаптируется):
`useLogStream`, `useLogFilter`, `LogViewport`, `logSelection`, `LogViewer`.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` (разделы «Потоки», «Provider API»).
**Спайк:** `docs/spikes/2026-09-29-log-stream-desktop.md` (WebKitGTK, поведение `pods/log`).

## Глобальные ограничения

- Всё из P0/P1 (AGENTS.md «Правила»).
- `internal/core`, `internal/streams`, общий UI логов не знают про pod/container/namespace:
  источник — непрозрачный `key` + `label`, выбор «контейнера» — список `LogChannel` провайдера.
- Потоки — только через loopback-сервер с токеном, никогда через `wails://`.
- Никаких опросов кластера: смена контейнера/pod-ов узнаётся из informer-кэшей (аренды).
- У каждого запроса к кластеру — контекст; у открытия лог-потока — дедлайн на заголовки,
  у backlog-фазы — общий дедлайн; у живого потока клиентского таймаута нет.
- Все слои ограничены по **байтам**, а не только по строкам (бюджеты ниже); любое срабатывание
  ограничения видно пользователю («обрезано», «пропуск»), молча ничего не теряется.

## Гарантии (честно)

- В пределах одной инкарнации контейнера и без ротации лог-файла на узле: переподключение к
  kube не теряет и не дублирует строк (курсор ниже).
- Ротация файла kubelet-ом во время разрыва может безвозвратно унести строки (Kubernetes отдаёт
  только сохранённые файлы) — тогда источник показывает «возможен пропуск», если курсор не
  сошёлся.
- Разрыв самого loopback-потока (выход приложения, медленный читатель отключён) и `gone`
  (сессия закрыта) — **терминальны**: история во вкладке остаётся до явной кнопки «Открыть
  заново», которая начинает новый поток с чистого буфера (он приходит со своим backlog-ом;
  склейка со старой историей дала бы дубли — решение после ревью). Автоматического
  восстановления на уровне loopback нет — он локальный, и рвётся только по этим причинам.
- Порядок строк разных источников в backlog-е — по метке времени (при неубывающих метках внутри
  источника, как их пишет runtime); живые строки — в порядке прихода.

## Решения P2 (агент, 2026-09-29; уточнены ревью Codex и спайком)

**Поток и транспорт**
- **Один HTTP-запрос на вкладку** (backlog + follow): спайк показал, что loopback HTTP в
  WebKitGTK стримит. Но WebKitGTK иногда придерживает хвост пачки (20–60 КБ), пока не придут
  новые байты — поэтому писатель после сброса, за которым тишина, через 100 мс шлёт кадр `ping`
  (72/72 полных прогонов против ~1/4 неполных без него) и heartbeat раз в 20 с. Разделение
  launcher-а на два запроса не переносим.
- **Открытие:** `OpenLogStream(ref, query)` проверяет запрос и регистрирует поток под
  одноразовым id (TTL подключения 30 с, работа — только после подключения); UI делает
  `GET <streamBase>/logs/<id>`. Регистрация и `CloseOwner` сериализованы блокировкой сессий:
  поток не переживает закрытую инкарнацию. `CloseOwner` отменяет и неподключённые id.
- **Жизнь:** потоки считаются использованием сессии (reaper не закрывает сессию с открытой
  вкладкой логов); закрытие сессии → `end{gone}` по возможности (доставка best effort, очистка
  не ждёт читателя); закрытие вкладки → `abort` → отмена запросов kube. Запись с дедлайном
  (60 с на сброс): не читающий страницу поток отключается, а не копит память.
- **Протокол NDJSON:** `source{id,key,label,channel}`, `lines{s, l:[[ts, text, flags?]...]}`
  (ts — строка RFC3339Nano как у kube, без потери наносекунд; `flags`: обрезана/без метки),
  `state{s, state, class, msg}` (s=0 — поток целиком; state: streaming, waiting, ended, error,
  gap, truncated, limited), `ready` (backlog выдан), `ping`, `end{reason: done|gone|error}`.
- **Loopback-сервер** (модель spk-mm-client): `127.0.0.1:<случайный порт>`, ленивый старт,
  токен 32 байта в пути (постоянное время), точная проверка `Host`, только GET `logs/<id>` и POST
  `save`, `no-store`/`no-referrer`/`nosniff`, без редиректов; Origin проверяется **до**
  потребления id или записи файла: desktop — ровно `wails://localhost` (установлено спайком),
  browser — свой origin; ACAO — только для desktop-origin. Browser-режим: тот же обработчик под
  `/streams/<token>/` основного сервера.
- **Сохранение:** browser — Blob-скачивание; desktop — `POST save` со строковым телом
  (`text/plain`, без preflight; обязателен разрешённый Origin), лимит тела и времени чтения,
  имя очищается, файл не перезаписывается (`name (1).log`), права 0600, каталог — XDG
  `DOWNLOAD` (иначе `~/Downloads`). Тесты подменяют HOME/XDG.

**Запрос (`LogQuery`)**
- `TailLines`: N > 0 или `-1` = «все» (не kube-шный 0 = «ничего»); «все» ограничено байтовым
  бюджетом с честным статусом `limited`.
- `Since` (относительное) превращается в абсолютный `SinceTime` **один раз при открытии** — все
  источники и переоткрытия используют тот же порог (окно не «ползёт»).
- `Previous` — продуктовое решение: только для одного pod-а и конкретного контейнера, без
  follow (kube отдаёт лишь последний завершённый экземпляр).
- `limitBytes` у kube режет посреди строки и может остановиться раньше свежих строк: поэтому
  «последние N» считаются от `tailLines`, а `limitBytes` — только страховка; неполная
  последняя строка ответа с достигнутым лимитом отбрасывается и источник помечается
  `truncated`. На переоткрытиях начальные tail/limit не повторяются.

**Разбор (Go)**
- Свой ограниченный построчный читатель (не `bufio.Scanner`): метка — в начале логической
  строки (kubelet пишет одну метку на логическую строку; продолжения частичных CRI-записей идут
  без метки внутри той же строки). Строка > 256 КиБ: сохраняется префикс + пометка, остаток до
  `\n` отбрасывается. Строка без метки (начало ответа посреди частичной записи, битый формат)
  сохраняется с флагом «без метки» и не двигает курсор. Последняя строка без `\n` при чистом EOF
  без follow — отдаётся; при обрыве/лимите — отбрасывается (придёт при переоткрытии).

**Курсор и переоткрытие (Kubernetes)**
- Источник = (pod UID, контейнер); **инкарнация** = `containerID` (+`restartCount`). Курсор —
  на инкарнацию: последняя метка + кольцо меток последних строк (≤ 10k).
- Переоткрытие той же инкарнации: `sinceTime` = секунда последней метки (kube округляет вниз),
  ответ kubelet-а — строки файла по порядку с меткой ≥ порога, поэтому пропускаются первые K
  строк, где K — число уже отданных строк с меткой ≥ порога (по кольцу); первые пропущенные
  метки сверяются. Несовпадение или кольцо не покрывает порог → статус `gap` («возможен
  пропуск/повтор»), дубли предпочтительнее потерь. Равные метки и одинаковый текст —
  нормальные разные строки (считаются, а не сравниваются по тексту).
- Новая инкарнация (рестарт) или новый pod: kube отдаёт файл текущего экземпляра, поэтому
  запрос без `sinceTime` (кроме замороженного пользовательского порога), со «стартовым»
  хвостом ≤ 5000 строк / 4 МиБ и статусом `truncated`, если больше. Время обнаружения pod-а
  informer-ом курсором не служит (стартовые логи короткоживущего контейнера не теряются).
- **Машина состояний источника** (одна горутина на источник): наблюдения pod-а из кэша
  приходят в почтовый ящик «последнее значение» (обработчик informer-а не блокируется). На
  EOF/обрыве источник **атомарно смотрит последнее наблюдение**: уже есть более новая
  инкарнация → открыть её сразу; та же инкарнация running → повтор с джиттер-backoff 1–10 с
  (обрыв сети/прокси); завершена и рестарт ожидается (restartPolicy, не завершённый init,
  sidecar-init с `restartPolicy: Always`) → `waiting`, ждать наблюдения; завершена окончательно
  (Never/OnFailure-успех, завершённый init, ephemeral, pod удалён или заменён одноимённым с
  другим UID) → `ended`. Отмена — по контексту в любом ожидании.
- UID: `pods/log` адресуется по имени; перед каждым (пере)открытием наблюдаемый UID сверяется
  с UID источника, одноимённая замена — `ended` («pod заменён»). Узкая гонка
  удаление/создание между проверкой и запросом не закрывается API — задокументировано.
- Нет прав на list/watch pods, но есть на `pods/log` (один pod): follow работает, автоматическое
  отслеживание рестартов — нет (статус «отслеживание рестартов недоступно: нет прав на
  watch pods» + ручное «Переподключить»); запрет inventory не выдаётся за запрет логов.

**Агрегация**
- Набор pods workload-а — по UID контроллера (Deployment → RS → Pod) из кэшей pods и
  replicasets; ready набора — после синхронизации **обоих**; pod раньше своего RS и изменения
  любого из кэшей переоцениваются. Workload с 0 реплик остаётся подписанным (scale up → новые
  источники).
- Лимит — **20 потоков-контейнеров** на вкладку (не pods: «все контейнеры» × pods); выбор
  детерминированный (свежие pods первыми), допущенный источник не вытесняется, освободившиеся
  места заполняются; статус «показаны 20 из K».
- Backlog: параллельно ≤ 4 запроса, общий дедлайн backlog-фазы 30 с — не успевший источник
  получает статус и продолжает follow-ом, остальные не ждут; k-way merge по метке; обрезка до
  последних N в сумме (точно при полных ответах без `truncated`).
- Контейнеры для выбора: из текущего шаблона + фактические контейнеры pods (при rollout старые
  pods могут иметь другие имена); выбранного контейнера нет в pod-е — статус источника.

**Бюджеты**
- Go: строка ≤ 256 КиБ; backlog-бюджет вкладки 16 МиБ, делится между источниками
  (`limitBytes` ≥ 512 КиБ каждому); очередь источника → писатель ограничена (≤ 1 МиБ, иначе
  источник ждёт = обратное давление, не память); вкладок (потоков) ≤ 8 на приложение, запросов
  логов к кластеру ≤ 64 одновременно на приложение (сверх — `waiting` «лимит соединений»).
- Web: вкладка ≤ 50k строк **и** ≤ 16 М символов (старые уходят первыми, счётчик «вытеснено»);
  пока пользователь читает (не follow), окно может растянуться до ×1,2, чтобы текст не
  «уезжал» под ним (осознанная политика, как в launcher); кадр NDJSON ≤ 8 М символов (сервер
  режет пачки по 64 КБ); очередь на время выделения мышью ограничена тем же бюджетом;
  метаданные завершённых источников удаляются вместе с их последней строкой. Бюджет — на
  вкладку, не глобальный: худший случай ~8 вкладок × 19 М символов — редкость, типичный —
  единицы МБ; замеры — в итогах.

**UI**
- **Нижняя панель вкладок** (её же займут терминалы P3): вкладка на поток, splitter, высота в
  `ui_prefs`. Точки входа: детали pod-а (контейнеры с «Логи»), детали workload-а («Логи»),
  клавиша `L` на выбранной строке.
- Follow потока (upstream идёт всегда) отделён от автопрокрутки: прокрутка вверх замораживает
  вид (без обрезки под читателем, только потолок бюджета, при котором видно «вытеснено N
  строк»), кнопка «К концу» возвращает.
- Поиск: plain — `indexOf`; фильтр с `*` — последовательный `indexOf` частей (линейно); regex —
  в Web Worker с бюджетом времени (300 мс на проход; превышение — «слишком медленное выражение»,
  поиск выключается), главный поток не блокируется. Эвристика launcher-а `isRegexSafe` не
  используется как защита.
- Уровни: определяются по тексту без ANSI; строки-продолжения наследуют уровень **своего
  источника**.
- ANSI: свой разборщик SGR (16/256/truecolor, bold/dim/italic/underline/inverse); прочие CSI,
  OSC (гиперссылки как текст не интерпретируются), одиночные ESC вырезаются. Состояние стиля
  **на источник** переносится между строками: при приёме у строки хранится стиль на её начале
  (только если не по умолчанию), спаны строятся при отрисовке. `\r\n` → `\n`.
- Копирование/сохранение — текст без ANSI в пределах того, что видно (фильтр), с префиксом
  источника и временем, если они показаны.

**Проверка**
- Герметично: `internal/providers/synthetic` (только `--test-api`) для Playwright UI и
  управляемый **фейковый kube-сервер логов** (httptest: `pods/log` с timestamps/sinceTime/
  tailLines/limitBytes/follow/previous, частичные записи, обрывы, ротация) для Go-тестов
  разбора, курсора и переоткрытий.
- Порядок: сначала один источник (tail/follow/переоткрытие) и smoke на kind, потом агрегация.

## Provider API (дополнение)

```go
// core
type LogChannel struct{ ID, Title, Note string } // Note: "init", "sidecar", "ephemeral"
type LogInfo struct {
    Channels       []LogChannel
    DefaultChannel string
    Aggregate      bool // объект — группа источников (workload)
    Previous       bool // previous поддерживается (один pod)
}

// provider
type LogQuery struct {
    Channel   string    // "" = по умолчанию, "*" = все
    Previous  bool
    Follow    bool
    TailLines int       // N > 0, -1 = все (в пределах бюджета)
    SinceTime time.Time // абсолютный порог (UI Since переводится при открытии), zero = нет
}
type LogLine struct { TS string; Text string; Flags LineFlags }
type LogState struct { State, Class, Message string }
type LogSink interface { // из горутин потока; может блокировать (обратное давление)
    Source(id int, key, label, channel string) error
    Lines(id int, lines []LogLine) error
    State(id int, st LogState) error // id 0 = поток целиком
    Ready() error
}
type LogSource interface {
    LogInfo(ctx context.Context, ref core.Ref) (core.LogInfo, error)
    StreamLogs(ctx context.Context, ref core.Ref, q LogQuery, sink LogSink) error
}
```

## Задачи

### Task 1: спайк — fetch-стрим из desktop к loopback
- [x] Под Xvfb: fetch из `wails://localhost` к `http://127.0.0.1:<port>` стримит, CORS
      обязателен и достаточен, abort доходит до сервера; «всплеск, затем тишина» иногда теряет
      хвост до следующих байтов — лечится кадром-толчком через 100 мс (72/72). Скрытое окно не
      проверено (нет xdotool) — страхует дедлайн записи. Поведение `pods/log` на kind записано.

### Task 2: контракт и слой потоков
- [x] `core`/`provider`: типы выше; JSON-формы стабильны (тест).
- [x] `internal/streams`: реестр (одноразовые id, TTL 30 с, owner, ≤ 8 потоков, `CloseOwner`
      отменяет и неподключённые), писатель (коалесцирование 50 мс/32 КБ, толчок 100 мс,
      heartbeat 20 с, дедлайн записи 60 с), обработчик (токен, Host, Origin до потребления id,
      CORS только desktop), loopback-сервер, сохранение, `LogSink` → кадры.
- [x] API: `LogInfo(ref)`, `OpenLogStream(ref, query)` (регистрация под блокировкой сессий),
      `StreamBase()`; reaper считает потоки; `closeSessionLocked` закрывает потоки. HTTP +
      Wails + client.ts.
- [x] Тесты: неверный токен/Host/Origin → отказ без потребления id и без токена в логе; id
      одноразовый, истекает; подключение наперегонки с `CloseOwner`; сессия с одной вкладкой
      логов переживает TTL reaper-а; закрытие сессии → `gone`, без автопереоткрытия;

## Ревью реализации (Codex, 2026-09-29) — исправлено

Все 11 замечаний подтверждены и исправлены, к каждому — регрессионный тест (Go —
`logs_review_test.go`, web — `LogViewer.test.tsx`, `match.test.ts`, `ndjson.test.ts`,
`buffer.test.ts`, `row.test.tsx`):

1. Группа ждала свои источники раньше, чем отменяла их (порядок `defer`) — выход при ошибке
   анонса источника висел; теперь один defer «отменить → дождаться».
2. Пачки backlog-а группы резались только по строкам (40 × 250 КиБ = кадр > 10 МБ) — теперь и
   по байтам; клиент проверяет размер и у завершённых кадров (одинаково при любой нарезке TCP).
3. Pod, появившийся во время backlog-а, не допускался до следующего события набора; новый
   контейнер pod-а (ephemeral) не будил допуск — теперь сверка и подписка из одного снимка,
   изменение списка контейнеров — событие набора.
4. Явный канал (UI шлёт его всегда) обходил проверку UID — previous/текущие логи одноимённой
   замены; теперь GET с проверкой UID перед любым запросом (без права get — только для follow,
   где UID держит наблюдение), и backlog группы не читает ушедший pod по имени.
5. Оборванный не-follow ответ выдавался за полный; частичный backlog группы переигрывался
   follow-ом — теперь ошибка «ответ оборвался после N строк», а показанное входит в курсор.
6. Нативный sidecar (`initContainers[].restartPolicy: Always`) при pod-политике Never/OnFailure
   считался завершённым — теперь ждёт рестарта, пока pod жив.
7. UI: поздние кадры заменённого потока попадали в новый буфер; битый кадр оставлял запрос
   открытым — теперь «ворота» поколения на каждом шаге и `abort` при битом кадре и после `end`.
8. Regex-поиск ломался после смены канала/tail/reopen (id строк начинались заново; поздний
   ответ воркера возвращал удалённые совпадения) — id монотонны на всю жизнь вкладки, у поиска
   нижняя граница живых id. Решение: «Открыть заново» начинает с чистого буфера (без склейки).
9. Невидимые сигналы потерь: маркер обрезанной строки (на экране и в копии), gap/truncated
   «липкие» (не затираются следующим streaming), перенос стиля/уровня не теряется при сбросе
   очереди во время выделения и сбрасывается на границе (рестарт, переподключение);
   префиксы не перестраиваются под активным выделением.
10. Удержание памяти: backlog источников освобождается после отправки, ключи `finished` ушедших
    pod-ов забываются, в UI завершённые источники без строк удаляются; «все контейнеры»
    удалённого pod-а завершают поток; потеря watch у группы видна («новые pods не появятся»).
    Бюджет UI — на вкладку (не глобальный), ×1,2 при чтении — записано в «Бюджеты».
11. Дедлайны: тело ответа-ошибки (10 с), не-follow ответ (2 мин), тело `POST save` (60 с).

Безопасность потокового сервера замечаний не получила. После исправлений: `make check`,
`make test-kind`, `make e2e-kind` зелёные.
