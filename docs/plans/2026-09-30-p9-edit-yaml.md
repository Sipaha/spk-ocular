# P9 — редактирование YAML объекта Kubernetes

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`. Каждая задача — отдельные
> коммиты `area: summary`, `make check` зелёный перед коммитом. Каждое исправление и каждая
> возможность начинаются с теста, который падает без них.

**Цель:** пользователь правит YAML существующего объекта прямо в деталях (как `kubectl edit`
или «Edit» в Lens). Перед записью он видит **что именно изменится**: разницу между объектом
сейчас и тем, каким его сделает сервер. Разница считается server-side dry-run-ом, поэтому
видны defaulting и мутации admission, а ошибки валидации приходят до подтверждения. Видны и
**где** (context, сервер, namespace, вид, имя), права и предупреждения. Запись идёт только
после подтверждения, над подтверждённым объектом (UID) и его версией (`resourceVersion`).
Если объект изменился с момента открытия редактора, правки пользователя накладываются на
текущую версию, и это явно сказано в просмотре. Если он изменился после просмотра, запись
отказывает (`conflict`) и предлагает посмотреть заново. Молча ничего не перезаписывается.

**Архитектура:** provider-агностичная возможность сессии `Editor` с протоколом без серверного
состояния, как у действий P4:
1. `EditSource` — текст для редактора и база (версия, от которой он).
2. `PrepareEdit` — только чтение: разбор, проверка идентичности, патч, dry-run, разница, права,
   предупреждения, `Expect`.
3. Подтверждение в общем UI.
4. `RunEdit` — тот же патч с предусловиями UID и `resourceVersion`, без повторов.

Kubernetes: патч — JSON merge patch от **показанного** документа к отредактированному. Поля,
которые не показаны (status, managedFields, last-applied), не трогаются. Маскированные значения
Secret, оставленные как есть, в патч не попадают. Вид редактируем по флагу
`KindDescriptor.Editable`.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md`. «Не делаем в MVP» называл
редактирование/apply YAML; MVP завершён (P0–P8), пункт взят из `docs/backlog.md`. «Принципы»:
Read-first, destructive — с подтверждением, все contexts RW без read-only-пометок.

## Глобальные ограничения

- Всё из P0–P8 (AGENTS.md «Правила»). `internal/core`, `internal/api` и общий UI не знают
  Kubernetes: документ — текст, разница — строки до/после, предупреждения — `Message`
  провайдера, опасность — флаг плана.
- Все contexts работают в RW-режиме. Защита — только UX подтверждения.
- Ни одной записи без подтверждённого просмотра: `RunEdit` требует `Expect` из `PrepareEdit`.
  Сервер не держит состояния, поэтому клиент присылает текст заново, и провайдер проверяет, что
  патч тот же (хэш в `Expect`).
- Никаких автоматических повторов записи. Правка — содержимое пользователя: на 409 он смотрит
  разницу заново.
- Никаких опросов. Изменение объекта во время редактирования видно по уже существующей
  ревизии деталей (`useObjectRevision`).
- У каждого запроса к кластеру свои контекст и таймаут. Необязательные части просмотра (права)
  не блокируют план и не роняют его: дедлайн 5 с, как в P4.
- Тесты записи против кластера — только kind `ocular-dev`, с той же проверкой kubeconfig, что
  в P4. Реальные кластеры не трогаются.
- CodeMirror остаётся ленивым чанком. Разница считается своей функцией построчного diff, без
  новой зависимости.

## Решения P9 (агент, 2026-09-30)

1. **Объём.** Правка одного существующего объекта из деталей. В бэклог:
   - создание объектов и `apply -f` многодокументного YAML;
   - раскрытие значений Secret;
   - редактирование Compose — его объекты неизменяемы, а compose-файлы уже в бэклоге.
2. **Что редактируемо.** `KindDescriptor.Editable`:
   - описанные виды Kubernetes — все, кроме Events и синтетических (Problems);
   - обнаруженные — если discovery даёт глагол `patch`.

   Глагол говорит, что обслуживается, а не что разрешено: права проверяет SSAR в просмотре.
3. **Показанный документ.** Объект как прочитан, без:
   - `metadata.managedFields`;
   - аннотации `kubectl.kubernetes.io/last-applied-configuration`;
   - `status`.

   Над YAML — комментарий: «status, managedFields и last-applied не показаны и не меняются».
   Порядок ключей тот же, что во вьюере (`sigs.k8s.io/yaml`). Secret — `data` с маской
   `<N bytes>`, как во вьюере.
4. **База.** `EditSource` возвращает текст и `Base`: непрозрачный отпечаток (HMAC) маршрута
   (GVR + scope, как `sameRoute` P8), UID и `resourceVersion` прочитанного объекта. Сервер
   ничего не хранит, а точную старую версию Kubernetes не отдаёт (GET с `resourceVersion` —
   «не старше»). Поэтому исходный текст присылает клиент: `PrepareEdit` принимает `{ref,
   base, original, edited}`. Провайдер сверяет `original` с `Base`: `metadata.uid` и
   `resourceVersion` в нём те же, HMAC совпал. Иначе — `bad_request`. Подделка исходного
   текста меняет только собственный просмотр пользователя: запись всё равно идёт после
   dry-run и с предусловиями.
5. **Патч.** Считается так: `CreateMergePatch(original, edited)` (JSON merge patch,
   `evanphx/json-patch`, уже в зависимостях), затем:
   - Изменение идентичности — `apiVersion`, `kind`, `metadata.name`, `namespace`, `uid` —
     отказ `invalid` с понятной причиной: «это другой объект». Правка `resourceVersion` в
     тексте игнорируется — версию ставит провайдер.
   - Пустой патч — план «изменений нет», «Применить» недоступна.
   - Массивы merge patch заменяет целиком. Против конкурентных правок защищает предусловие
     версии: запись идёт при версии, против которой сделан просмотр.
   - `null` в тексте удаляет ключ — так работает merge patch; это сказано в подсказке редактора.
6. **Наложение на текущую версию.** `PrepareEdit` читает объект сейчас, строго с UID. Замена
   одноимённым объектом — `gone`, а маршрут сверяется, как в P8. Патч применяется к
   **текущему** объекту: `dryRun=All`, в патч добавлены `metadata.uid` и `resourceVersion`
   текущего объекта.
   - Если версия базы ≠ текущей, в плане предупреждение: «объект изменился после открытия
     редактора (кем-то ещё или контроллером); ваши правки наложены на текущую версию —
     проверьте разницу».
   - Разница — «текущий показанный документ» против «результата dry-run», нормализованных
     одинаково (п. 3).
7. **Dry-run.**
   - 422 (валидация, неизменяемые поля pod-а) или отказ webhook-а — план `Unavailable` с
     сообщением сервера, «Применить» недоступна, пользователь возвращается к тексту.
   - Webhook с побочными эффектами отказывает в dry-run. Тогда в плане предупреждение
     «сервер не смог проверить без записи: <сообщение>», разница — локальное наложение патча
     (помечено «без проверки сервером»), план опасный. Применить можно.
   - 403 на dry-run — права `denied`.
8. **Предупреждения:**
   - У объекта есть `ownerReferences` с `controller: true`: «управляется <Kind> <имя>:
     контроллер может вернуть изменения».
   - Есть метка `app.kubernetes.io/managed-by` или аннотации Helm/Argo CD: «управляется <кем>:
     изменения могут быть перезаписаны при следующем деплое».
   - Изменение `spec` workload-а со стратегией обновления: «изменение шаблона pod-ов запустит
     rollout». Определяется, когда патч трогает `spec.template`.
   - Всё это строки провайдера, обоснованные прочитанным.
9. **Права.** SSAR `patch` на ресурс (namespace, name). `allowed` / `denied` / `unknown`, как в
   P4.
10. **`Expect`.** HMAC, как у действий, от:
    - маршрута;
    - UID;
    - `resourceVersion` текущего объекта;
    - хэша канонического патча;
    - `ConfigRev` сессии.

    Отказ сервера показывают как есть, без повторов:
    - `RunEdit`: пересчитать патч из присланных `original`/`edited`; хэш не совпал —
      `bad_request`; маршрут не совпал — `conflict`;
    - запись — PATCH (merge) с `metadata.uid` и `resourceVersion` из `Expect` (не
      перечитывая: версия и есть предусловие);
    - 409 → `conflict` «объект изменился после просмотра — посмотрите разницу заново»;
    - 422 → `invalid` с сообщением;
    - 403 → `forbidden`;
    - 404 → `gone`;
    - обрыв после отправки → `unknown`.

    Результат — «изменения записаны» и новая версия объекта.
11. **UI.**
    - Вкладка YAML получает кнопку «Изменить» (`E` на вкладке YAML, по `KeyboardEvent.code`).
      Редактор — тот же ленивый CodeMirror без `readOnly`, с подсказками `null` и маски
      Secret.
    - Панель редактора: «Просмотреть изменения» (`Ctrl+Enter`) и «Отмена».
    - Живые обновления объекта текст редактора не заменяют. Если ревизия объекта сменилась,
      появляется полоса «объект изменился на сервере — ваши правки будут наложены на текущую
      версию при просмотре».
    - Просмотр — модальный диалог, как у действий:
      - где и что;
      - предупреждения и права;
      - разница: унифицированный построчный diff с контекстом 3 строки, +/−, свёрнутые
        неизменённые участки;
      - кнопки «Применить» и «Назад к тексту».

      Опасный план — красная кнопка, фокус на «Назад». `conflict` при записи — в диалоге,
      с кнопкой «Посмотреть заново».
    - Успех — уведомление в строке состояния. Редактор закрывается, детали перечитываются.
    - Несохранённые правки не теряются молча. Esc (вне панели поиска), закрытие деталей, переход
      по связям, смена вкладки, смена вида или target-а — подтверждение «Отбросить правки?».
      Фокус по умолчанию — «Продолжить правку».
12. **Что показывает dry-run.** Разница включает поля, заполненные сервером: defaulting и
    мутации webhook-ов. Это и есть результат. Нормализация (п. 3) убирает только managedFields,
    status и last-applied. `resourceVersion`, `generation` и `managedFields` в разнице не
    показываются: они меняются всегда.

### Спайк на kind (2026-09-30)

- Merge patch `--dry-run=server` с `metadata.uid` и верным `resourceVersion` возвращает
  результат (`null` удалил ключ), объект не изменён, версия в ответе прежняя.
- С устаревшим `resourceVersion` — 409 Conflict и в dry-run: конфликт виден уже в просмотре.
- С чужим UID — 422 `metadata.uid: field is immutable`, как в P4.

## Контракт

```go
// core
type EditDoc struct {
    Ref  Ref    // с UID прочитанного объекта
    Text string // показанный документ (п. 3), с комментарием-заголовком
    Base string // непрозрачно: маршрут + UID + resourceVersion
}
type EditPlan struct {
    Where       LiveTarget // как ActionPlan.Where
    Before      string     // текущий объект (п. 3)
    After       string     // результат dry-run (или локальное наложение, Checked=false)
    Checked     bool       // After — от сервера (dry-run)
    Changed     bool       // патч не пустой
    Rebased     bool       // версия базы ≠ текущей
    Destructive bool
    Warnings    []Message
    Rights      Rights
    Unavailable *Message   // dry-run отказал (валидация, webhook)
    Expect      string
}
type EditResult struct { Message string; Version string }

// provider
type Editor interface {
    EditSource(ctx, ref core.Ref) (core.EditDoc, error)
    PrepareEdit(ctx, EditRequest) (core.EditPlan, error) // Ref, Base, Original, Edited
    RunEdit(ctx, EditRun) (core.EditResult, error)       // + Expect
}
```

API: `GetEditSource`, `PrepareEdit`, `RunEdit`, с сессией и `ConfigRev`, как у действий. Оба
транспорта (Wails и HTTP) и `web/src/api/client.ts`. Предел текста — 3 МБ (`bad_request`
сверх него; объект etcd ≤ 1,5 МБ).
