# P12 — CronJob: приостановить, возобновить, запустить сейчас

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`. Каждая задача — отдельные
> коммиты `area: summary`, `make check` зелёный перед коммитом. Каждое исправление и каждая
> возможность начинаются с теста, который падает без них.

**Цель:** у CronJob появляются действия **Suspend** (новые запуски по расписанию не
начинаются), **Resume** (начинаются снова) и **Run now** (создать Job из шаблона CronJob
сейчас — как `kubectl create job --from=cronjob/<имя>` и «Trigger» в Lens). Сейчас CronJob —
обнаруженный вид (P8: колонки сервера, в разделе Workloads) с единственным действием Delete.

**Архитектура:** контракт действий P4 (`PrepareAction` → просмотр → один `RunAction`) без
новых методов API и без изменений `internal/core`/общего UI. Обнаруженный вид получает
действия по точному `GroupResource` (`batch/cronjobs`) рядом с `delete`; колонки остаются
серверными (Table: Schedule, Suspend, Active, Last Schedule — меняются вживую). Все подписи —
ключи сообщений провайдера.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md`; пункт — из `docs/backlog.md`
(«CronJob: действия (suspend/resume, запустить Job) — отдельный этап», решение 148 P11).
Принципы: Read-first, destructive — с подтверждением, все contexts RW без read-only-пометок.

## Глобальные ограничения

- Всё из P0–P11 (AGENTS.md «Правила»), особенно правила действий: `RunAction` читает строго по
  UID, `Expect` связывает всё, что прочитали эффекты плана, несовпадение — `conflict` без
  записи; каждая запись — один HTTP-запрос (`restWriter`, `MaxRetries(0)`), неоднозначный ответ
  (5xx, таймаут, обрыв) — `unknown`, без повторов; повтор — только при провале предусловия,
  когда перечтение доказывает, что записи не было (≤ 3). Маршрут (GVR + scope) — в `Expect` и
  на весь прогон (P8).
- Никаких опросов: «Run now» не ждёт завершения Job — таблица Jobs/Pods показывает это вживую.
- Все contexts RW. Тесты записи — только kind `ocular-dev`, в собственном namespace теста.

## Решения P12 (агент, 2026-09-30)

1. **Объём.** `batch/v1` CronJob: `suspend`, `resume`, `run` (Run now) + существующий `delete`.
   Действия привязаны к точному GR `batch/cronjobs` и только когда discovery даёт версию `v1`
   (иной версии нет с Kubernetes 1.25; другая — действий нет, только delete) и глаголы
   `patch` (suspend/resume), `get` (все). Не делаем: suspend/resume Job, выбор имени Job,
   изменение шаблона перед запуском, переход к созданной Job (бэклог).
2. **Suspend / Resume.** Merge patch `spec.suspend: true|false` с `metadata.uid` и
   `metadata.resourceVersion` (как cordon P11, повтор по 409 — общее правило). Недоступно,
   если CronJob уже в нужном состоянии (`suspend` отсутствует = `false`). Оба не опасные.
   Эффекты:
   - suspend: «новые запуски по расписанию не начнутся; уже идущие Job продолжаются» (+ «на
     момент просмотра шло N запусков по расписанию» из `status.active` — наблюдение, не в
     `Expect`);
   - resume: «запуски по расписанию возобновятся»; «время запуска, пропущенное за
     приостановку, может начать один запуск сразу: без `startingDeadlineSeconds` — если
     пропусков не слишком много; с ним — если пропуск был не раньше N с назад» (формулировка
     «может»: решает контроллер; поведение по документации Kubernetes, CronJob «Schedule
     suspension»).
   `effectState` — `spec.suspend` (для resume ещё `startingDeadlineSeconds`, по нему текст).
   Права — SSAR `patch cronjobs` (группа `batch`) с namespace и именем.
3. **Run now: что создаётся.** То, что делает `kubectl create job --from=cronjob` (kubectl
   `createJobFromCronJob`, master 2026-09): `batch/v1` Job в namespace CronJob-а;
   `metadata.labels` — из `spec.jobTemplate.metadata.labels`; `metadata.annotations` — сначала
   `cronjob.kubernetes.io/instantiate: manual`, затем аннотации шаблона поверх (как у kubectl:
   ключ из шаблона побеждает); `ownerReferences` — один: `{apiVersion: batch/v1, kind: CronJob,
   name, uid, controller: true}` (без `blockOwnerDeletion`, как kubectl); `spec` —
   `spec.jobTemplate.spec` как есть (шаблон с `suspend: true` или `parallelism: 0` не
   переопределяется — просмотр предупреждает, что Job будет создана, но работать не начнёт).
   Запуск не зависит от расписания и от `suspend` CronJob-а.
4. **Run now: имя.** `<база>-manual-<5 символов [a-z0-9]>`, всё имя ≤ 63 (имя Job — значение
   меток её pod-ов `job-name`). База — имя CronJob-а (DNS subdomain, ≤ 52), усечённое до 50 и
   затем без хвостовых `.` и `-` (иначе `a….` + `-manual-…` — недопустимое имя, ревью плана).
   Итоговое имя проверяется `validation.IsDNS1123Subdomain` и `IsValidLabelValue`; не прошло —
   план `Unavailable` (не должно случаться; тест на границах). Суффикс — `crypto/rand`. Имя
   выбирается **в плане** и показывается в просмотре («будет создана Job <имя>»).
5. **Run now: грант, один просмотр — одна отправка.** Имя не может жить в редактируемом
   суффиксе `Expect`. `Expect` run = `<маршрут>-<грант>`, грант — HMAC ключом процесса
   (`printKey`, P10) над каноническим набором: действие, маршрут, namespace, имя и UID
   CronJob-а, хэш состояния (решение 6), имя Job, срок годности (план + 10 мин), id инкарнации
   сессии (случайный при создании сессии: грант не переживает пересоздание сессии), и сами
   эти поля в открытом виде (base64url JSON) рядом с подписью. `RunAction`: проверяет подпись
   (подмена имени, срока, объекта — `invalid`, ни одной записи), срок (истёк — `conflict`
   «посмотрите снова»), инкарнацию, затем **расходует** грант: под мьютексом сессии id гранта
   заносится в набор израсходованных до отправки POST (в том числе когда итог потом
   `unknown`); повторное или одновременное использование — `conflict` «этот просмотр уже
   выполнен — посмотрите снова», ни одной записи. Набор ограничен сроком гранта (записи старше
   срока удаляются при каждом расходе; больше 1000 неистёкших — отказ `unavailable`, не рост
   без предела). Так «один просмотр — одна отправка» держится и после удаления созданной Job
   (TTL, пределы истории), а не только пока Job с этим именем существует. `ConfigRev` сверяет
   API-слой, как для всех действий.
6. **Run now: состояние, просмотр и слова.** Хэш состояния в гранте: UID CronJob-а,
   `deletionTimestamp`, канонический `spec.jobTemplate` (метаданные и spec), `spec.suspend`,
   `spec.concurrencyPolicy`, `successfulJobsHistoryLimit`, `failedJobsHistoryLimit` — всё, по
   чему выбраны тексты; изменилось между просмотром и записью — `conflict`, ни одной записи.
   `status.active` — **наблюдение на момент просмотра** («на момент просмотра шло N запусков
   по расписанию»), не обещание о записи и не в хэше: изменения статуса прогон не
   останавливают; и `status.active` перечисляет только запуски самого контроллера (ручные туда
   не входят — проверено на kind). Не опасный (создаёт, не удаляет). Эффекты — проверены на
   kind 1.37 (2026-09-30, namespace-ы `ocular-p12-probe*`, удалены):
   - «будет создана Job <имя> из шаблона CronJob-а сейчас, вне расписания»;
   - «Job принадлежит CronJob-у: удаление CronJob удалит её; после завершения её удаляют
     пределы истории CronJob-а» (с числами лимитов; проверено: `successfulJobsHistoryLimit: 1`
     удалил более старую завершённую ручную Job);
   - «к ней не применяется `concurrencyPolicy`: запуск по расписанию начнётся и пока она идёт
     (`Forbid` его не остановит, `Replace` её не заменит)» (проверено: при идущей ручной Job
     оба CronJob-а по расписанию создали свою Job, ручные продолжили работу);
   - «пока она идёт, Kubernetes отмечает CronJob событием Warning `UnexpectedJob` (так же с
     kubectl) — оно будет в «Проблемах»» (проверено: событие повторяется, пока Job идёт).
   Предупреждения: CronJob приостановлен («запуск всё равно будет»); шаблон приостановлен или
   `parallelism: 0` (Job создастся, но не начнёт работу); наблюдение `status.active` выше.
   Права — SSAR `create jobs` (группа `batch`) в namespace CronJob-а.
7. **Run now: запись и ответы.** Один `POST jobs` (`restWriter`, `MaxRetries(0)`), без
   предусловий на CronJob (у create их нет): перед записью одно чтение CronJob-а по UID и
   сверка хэша состояния — окно между ним и созданием остаётся и названо в правилах. Ответы:
   201 — «Job <имя> создана» (имя в сообщении); 409 AlreadyExists — `refused` «Job с таким
   именем уже есть — посмотрите снова»; 403 — `forbidden`; 400/422 — `refused` с текстом
   сервера (квоты, admission); 5xx/таймаут/обрыв/нет статуса — `unknown` «проверьте, есть ли
   Job <имя>, прежде чем повторять». Повторов нет никогда (create не идемпотентен). Своя ветка
   классификации (`failedWrite` — про объект действия: 404/409 там значат другое).
8. **Где живёт код.** `internal/providers/kubernetes/cronjob.go`: дескрипторы
   `actSuspend`/`actResume`/`actRunNow`, привязка к обнаруженному виду (из `catalog.go`, по
   GR и версии), эффекты, недоступность, грант run (подпись, срок, расход), построение Job и
   имени, классификация ответа create (решение 7). `actionWriter.create` (restWriter: `POST` коллекции, `MaxRetries(0)`;
   dynWriter: `Create`). `RunAction` отправляет `run` в свою ветку (как drain), suspend/resume —
   общий путь `write`.
9. **Тестовые фикстуры.** kind: CronJob в namespace теста (не `ocular-crd` — там фикстура P8
   `yearly`, на которую смотрят другие тесты), расписание раз в год, `suspend: true`, шаблон —
   `busybox:1.36` `true` (образ уже на узлах, сидится P8); Job заканчивается за секунды.
   Очистка — удаление namespace.

## Ревью плана

Ревью Codex ревизии 1 (`28ed1f0`) — 3 × P2 + P3, все приняты (ревизия 2):
- P2 — суффикс имени в `Expect` не был подписан (подмена `.abc12` → `.xyz34` создала бы не ту
  Job), а «один просмотр — одна Job» держалось только пока Job существует (TTL, пределы истории
  её удаляют) → решение 5: подписанный грант с именем, сроком и инкарнацией сессии,
  расходуется до отправки; тесты подмены, повтора, одновременного использования.
- P2 — усечение оставляло `.` на границе (`a…a.` + `-manual-…` — недопустимое имя) →
  решение 4: снимать хвостовые `.`/`-`, проверять итог функциями apimachinery.
- P2 — поля, по которым выбраны тексты (`suspend`, `concurrencyPolicy`, лимиты), не входили в
  `Expect` → решение 6: в хэше состояния; `status.active` — наблюдение на момент просмотра.
- P3 — приоритет аннотаций не как у kubectl → решение 3: `instantiate: manual` первым, шаблон
  поверх (как kubectl).
Принятые без изменений замечания: шаблон с `suspend`/`parallelism: 0` — предупреждение, не
переопределение (решение 3); проверка контроллера на kind — и `Forbid`, и `Replace` при идущей
ручной Job, отдельно `status.active` и очистка истории (Task 4, сделано до реализации).

Перепроверка ревизии 2 (`cb23656`): **план закрыт**. Напоминания к реализации (план не
переоткрывают): id гранта — из подписанного неизменного содержимого (подпись/nonce), не из
байтов кодировки; свой доменный тег HMAC при общем `printKey`; каждое подписанное поле
сверяется с запросом и сессией; декодирование ограничено; в гранте — хэш состояния, не шаблон.
Проверка срока (текущим временем), чистка, проверка повтора и резерв — одно атомарное решение;
тест на границе срока (запрос, проверенный до срока и задержанный чтением); отмена вызывающего
проверяется до отправки; отправленное/неизвестное не «разрасходуется». Слова о контроллере —
условные: ручная Job сама не мешает и не заменяется через `concurrencyPolicy`, но это не
обещание запуска по расписанию; пределы истории удаляют завершённые Job, когда этого требуют
пределы, не обязательно сразу.
