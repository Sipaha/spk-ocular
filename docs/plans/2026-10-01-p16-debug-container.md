# P16 — отладочный контейнер в pod-е (ephemeral container) с терминалом

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`. Каждая задача — отдельные
> коммиты `area: summary`, `make check` зелёный перед коммитом (коммит — только по его коду
> выхода). Каждое исправление и каждая возможность начинаются с теста, который падает без них
> (проверка мутацией на старом коде).

**Цель:** у pod-а появляется действие **Отладить…** — как `kubectl debug -it <pod>
--image=<образ> --target=<контейнер>`: в pod добавляется ephemeral-контейнер с выбранным образом
(по умолчанию `busybox:1.36`), видящий процессы выбранного контейнера, и сразу открывается
терминал в нём. Сейчас в pod без shell (distroless, scratch) терминал Ocular не зайти — остаётся
kubectl.

**Почему этот этап (выбор агента, 2026-10-01; пользователь просил не ждать его выбора):** на
живых кластерах всё больше образов без shell; «зайти посмотреть» в такой pod — ежедневная
задача, и сейчас она выводит из Ocular. Прочее в бэклоге реже (удаление namespace по имени,
compose-файлы, SS/DS undo) или полировка (английские тексты в RU UI, подписи).

**Архитектура:** контракт действий P4 (`PrepareAction` → просмотр → один `RunAction`) с одним
расширением `core` — **текстовое значение** рядом с параметром (`ActionDescriptor.Text`,
`ActionParams.Text`): образ вводится, цель выбирается (`choice`, P15). Имя контейнера — в
подписанном гранте `Expect`, как имя Job у «Запустить сейчас» (P12). Итог действия может
попросить UI открыть терминал (`ActionResult.Terminal`). Терминал в отладочный контейнер —
**attach** к его процессу (как `kubectl debug -it`): выход из shell завершает контейнер, лишних
процессов в pod-е не остаётся. Контейнер, ещё не запущенный (образ скачивается), терминал ждёт
по watch pod-а, с пояснением в вкладке.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` (бэклог P3: «ephemeral
debug-контейнеры (`kubectl debug`) и attach без exec»). Принципы: Read-first, запись — с
просмотром, все contexts RW без read-only-пометок.

## Глобальные ограничения

- Всё из P0–P15 (AGENTS.md «Правила»): `RunAction` читает строго по UID, несовпавший `Expect` —
  `conflict` без записи; запись — один HTTP-запрос (`restWriter`, `MaxRetries(0)`),
  неоднозначный ответ — `unknown` без повторов; повтор — только при 409 и доказанном отсутствии
  записи (≤ 3).
- Никаких опросов: ожидание запуска контейнера — watch одного pod-а с дедлайном.
- Все contexts RW. Тесты записи — только kind `ocular-dev`, собственный namespace теста
  (удаляется); образ — уже загруженный на узлы (`busybox:1.36`).
- Агенты (P14) отладочные контейнеры не получают (это exec-уровень доступа, exec агентам не
  выдаётся).
- Ручные запуски — изолированные HOME/DOCKER_CONFIG/SPK_OCULAR_HOME, цель по точному имени.

## Решения P16 (агент, 2026-10-01)

1. **Объём.** Pod (`v1` pods): действие `debug` рядом с delete. Не делаем в v1: копия pod-а
   (`kubectl debug --copy-to`), отладка узла (`kubectl debug node/…`), профили securityContext
   (`--profile`), свои команда и переменные контейнера — бэклог. Workload-и — через их pod (как
   терминал: сначала выбирается pod).
2. **Текстовое значение в `core`.** `ActionDescriptor.Text *ActionText{Title Message, Default
   string, Max int}` — второе поле действия рядом с `Param`; `ActionParams.Text *string`.
   `CheckParams`: у действия без `Text` — отказ; у действия с `Text` пустое/длиннее `Max` —
   отказ; при Run обязательно. Почему не `Params []ActionParam`: одно необязательное поле не
   ломает P4–P15 (дескрипторы, диалог, агентов); выбор «список параметров» — когда понадобится
   третий. Провайдер проверяет смысл (ссылка на образ).
3. **Образ.** По умолчанию `busybox:1.36`; последний использованный для цели запоминается в
   `target_state` (`debugImage`) и подставляется. Проверка формы — как у kubelet: непустой, без
   пробелов, ≤ 512; остальное — отказ API сервера (виден в итоге). Предупреждение в плане:
   «образ скачивается из реестра узлом — в закрытой сети нужен доступный образ».
4. **Цель** (`choice`): контейнеры pod-а (обычные и sidecar-ы, запущенные), по умолчанию —
   контейнер по умолчанию (аннотация `kubectl.kubernetes.io/default-container`, иначе первый);
   вариант «без цели» (общее пространство процессов только если оно уже включено в pod-е,
   `shareProcessNamespace`). Детали варианта — образ контейнера и состояние.
5. **План.** Эффекты: «в pod <имя> добавится отладочный контейнер <debugger-xxxxx> с образом
   <образ>; он видит процессы контейнера <цель>»; «убрать его нельзя: он останется в описании
   pod-а до пересоздания pod-а; после выхода из shell он завершится»; «откроется терминал».
   Предупреждения: реестр (решение 3); у pod-а с политикой PodSecurity `restricted`/`baseline`
   namespace-а (метка `pod-security.kubernetes.io/enforce`) — «может быть отклонён: контейнер без
   securityContext» (профилей в v1 нет). Unavailable: удаляется; не `Running`
   (`Succeeded`/`Failed`/`Pending` без запущенных контейнеров); mirror/static pod (аннотация
   `kubernetes.io/config.mirror`) — «статический pod: kubelet не добавляет ему контейнеры». Не
   destructive (ничего не теряется), но необратимо — сказано эффектом. Права: `patch
   pods/ephemeralcontainers` и `create pods/attach` (оба SSAR; худший итог).
6. **Имя и одна запись.** Имя `debugger-<5 [a-z0-9]>` выбирается при просмотре и едет в
   подписанном гранте `Expect` (механизм `runGrant` P12, свой доменный тег: действие, маршрут,
   pod, хэш состояния, имя, образ, цель, срок 10 мин, инкарнация сессии, nonce); грант
   расходуется до записи — один просмотр не больше одного контейнера. Состояние в гранте: uid,
   deleting, phase, имена контейнеров и ephemeral-контейнеров, `shareProcessNamespace`, состояние
   цели (запущена). Изменилось — `conflict`.
7. **Запись.** `PATCH pods/<name>/ephemeralcontainers`, strategic merge patch:
   `{"metadata":{"uid":…,"resourceVersion":…},"spec":{"ephemeralContainers":[{"name","image",
   "targetContainerName"?,"stdin":true,"tty":true,"imagePullPolicy":"IfNotPresent"}]}}` — список
   сливается по имени (как `kubectl debug`), существующие не трогаются. Один запрос. 409
   (версия сдвинулась статусом — pod-ы меняют статус часто) — перечтение: тот же грант-state и
   нет контейнера с этим именем → повтор (≤ 3; грант уже израсходован — повторы в рамках одного
   прогона); контейнер с этим именем уже есть — `done` (запись дошла раньше). 422/403 — отказ
   с текстом сервера; 5xx/обрыв — `unknown` с именем контейнера. **Проверено на kind
   2026-10-01** (`kubectl patch --subresource=ephemeralcontainers --type=strategic`): устаревшая
   `resourceVersion` — 409; тот же контейнер тем же телом ещё раз — 200 без изменений; то же имя с
   другим образом — 422 (ephemeral-контейнеры неизменяемы); чужой `uid` — 422 (перечтение по UID →
   «заменён тем временем», как у отката P15). Статус pod-а, запускающего отладчик, меняется
   несколько раз в секунду — повтор после 409 нужен на деле.
8. **Терминал после.** `ActionResult.Terminal *TerminalOpen{Ref, Instance, Channel, Attach
   bool}` — UI открывает вкладку терминала сразу после итога «запрошено». `ExecRequest.Attach`:
   Run подключается к `pods/<name>/attach` (stdin, stdout, tty; без command), не `exec`.
   Контейнер ещё не запущен — Run ждёт watch-ем pod-а (дедлайн 120 с, `Notice`: «контейнер
   запускается: <reason>»); `ErrImagePull`/`ImagePullBackOff`/завершился — ошибка вкладки с
   причиной. Выход из shell — процесс завершился: код — из
   `ephemeralContainerStatuses[].state.terminated.exitCode` (attach кода не сообщает; нет —
   «неизвестен»). «Подключиться заново» к завершившемуся — ошибка «контейнер завершился»
   (перезапустить ephemeral нельзя). `ExecInfo`/`TerminalDialog` уже показывают запущенные
   ephemeral-контейнеры: к живому отладочному можно вернуться обычным терминалом (exec) —
   attach только из итога действия.
9. **Детали pod-а.** Факты «container <имя>: образ» дополняются init- и ephemeral-контейнерами
   (помечены), иначе добавленный отладчик не виден в деталях.
10. **Агенты (P14).** `debug` — не выдаётся: `agentgrant`/редактор грантов исключают его, как
    exec; `PrepareAction` агента с `debug` — `forbidden` без обращения к провайдеру; тест.
11. **UI.** `ActionDialog`: поле текста (образ) над выбором цели; как у числа — Enter в поле и
    «Просмотреть» пересобирают план, «Выполнить» — только с планом этих значений; выбор цели —
    сразу пересборка (P15). После `done` с `Terminal` — вкладка терминала (как из
    `TerminalDialog.onOpen`), заголовок «debugger-xxxxx · <pod>».
12. **Синтетика и тесты.** Синтетический «Pod»-вид не заводим: синтетические Workloads получают
    `debug` с echo-терминалом attach (для e2e диалога и открытия вкладки). Unit (fake dynamic
    client): план (эффекты, Unavailable, права), тело patch, грант (одна запись, подмена,
    срок), 409 → повтор, «уже есть» → done, 422/5xx; attach URL (без command), ожидание запуска
    (fake watch), код выхода из статуса. kind: отладчик в pod-е `nginx:1.27-alpine`,
    `ps` видит процессы цели, выход завершает контейнер; e2e synth + kind (из UI).
