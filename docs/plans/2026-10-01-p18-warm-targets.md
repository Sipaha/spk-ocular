# P18 — Переключение между целями без потерь: недавние цели остаются открытыми

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`. Каждая задача — отдельные
> коммиты `area: summary`, `make check` зелёный перед коммитом (коммит — только по его коду
> выхода). Каждое исправление и каждая возможность начинаются с теста, который падает без них
> (проверка мутацией на старом коде).

**Цель:** переход prod → stage → prod не стоит ничего. Сейчас выбор другой цели сразу закрывает
сессию прежней (`closeOtherSessions`): её кэши, открытые вкладки логов (`dock.keepLogsOf`),
а страница цели начинается заново — вид и scope восстанавливаются из `target_state`, но фильтр,
сортировка, выбранная строка и открытые детали теряются, таблица грузится с нуля (list + watch
каждого вида). После P18:
- две последние покинутые цели остаются **открытыми** (сессия, её кэши и watch-и) до 10 минут —
  возврат показывает таблицу сразу, из тёплого кэша;
- страница цели при возврате — та же: вид, scope, фильтр, сортировка по видам, строка курсора,
  открытые детали и их вкладка;
- вкладки логов другой цели **не закрываются** и продолжают идти (как уже терминалы и туннели),
  помечены как чужие;
- в списке целей видно, какие открыты, и открытую можно закрыть.

**Почему этот этап (выбор агента, 2026-10-01; пользователь просил не ждать его выбора):** на
живых кластерах переключение контекстов — самое частое действие дня: сравнить prod и stage,
посмотреть логи в одном, пока чинишь другой, вернуться к инциденту. Сейчас каждое переключение
— потеря контекста работы (открытые логи закрываются, фильтр и детали сбрасываются) и полная
перезагрузка таблиц. Lens держит кластеры подключёнными. Из бэклога это «несколько активных
кластеров одновременно» в экономной форме: одно окно, одна видимая цель, но недавние — тёплые.
Прочее из бэклога — реже в день (удаление namespace, журнал действий, undo StatefulSet) или
крупнее без такой же отдачи (создание объектов/apply — в ежедневной работе с GitOps-кластерами
редко; несколько окон). «Несколько окон» — остаётся в бэклоге.

**Архитектура:** жизнь сессии перестаёт зависеть от выбора цели мгновенно. `Service` помнит
порядок выбора целей; выбор другой цели закрывает сессии только сверх предела недавних; простой
недавней сессии — 10 мин вместо 60 с. Провайдер узнаёт, что его сессия в фоне (новый
необязательный интерфейс), — Kubernetes держит простаивающие кэши фоновой сессии, пока она
открыта (в пределе `maxIdleCaches`). UI хранит в памяти снимок страницы каждой цели и
восстанавливает его при возврате. Контракт `Watch`/views не меняется.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` — ключевое решение 1 («при смене
context старые кэши освобождаются сразу») и «Не делаем в MVP: несколько активных кластеров
одновременно» уточняются этим этапом (правка спецификации — в Task 5). Бэклог: «Несколько
активных кластеров одновременно / несколько окон».

## Глобальные ограничения

- Всё из P0–P17 (AGENTS.md «Правила»). Никаких опросов: фоновая сессия живёт на тех же watch-ах,
  таймеры — только локальные (жизнь сессии, кэша).
- Все contexts RW. Тесты — kind `ocular-dev` (две цели на один кластер: второй context в
  изолированном `~/.kube`) и dind `ocular-dind`; синтетика — вторая цель только в тестовом режиме.
- Ручные запуски — изолированные HOME/DOCKER_CONFIG/SPK_OCULAR_HOME, цель по точному имени.
- UX важнее памяти; меряется только Private_Dirty (процесс приложения и WebProcess).

## Решения P18 (агент, 2026-10-01)

1. **Недавние цели.** `Service` ведёт список выбранных целей по времени выбора. Выбор цели X:
   X — текущая; сессии **двух** последних покинутых целей (`recentTargets = 2`) остаются; прочие
   закрываются, **кроме** занятых: с открытыми потоками (вкладка логов), с вызовом агента
   (`spared`, как сейчас). Почему 2: prod/stage/dev — типичная тройка; больше — лишние watch-и
   на кластеры, к которым не вернутся (предел — константа, не настройка; настройка — бэклог).
   Недавняя сессия без views и потоков закрывается через **10 мин** (`recentIdle`) после ухода с
   неё, текущая и прочие — через 60 с, как сейчас (`sessionIdle`). Смена конфигурации цели,
   исчезновение цели — закрытие, как сейчас (`revalidateSessions`).
2. **Фон у провайдера.** Необязательный интерфейс `provider.Backgrounder { SetBackground(on bool,
   lost func()) }`: `Service` зовёт его с `true` для каждой сессии не выбранной цели (покинутой
   пользователем и открытой агентом) и с `false` при выборе цели. Kubernetes: в фоне
   простаивающие кэши не вытесняются по `cacheGrace` (только сверх `maxIdleCaches = 8`, самые
   старые); при возврате отсчёт `cacheGrace` начинается заново с момента возврата.
   **Фон не входит в кластер (ревью P2-1).** Реальные kubeconfig-и — exec-плагины (kubelogin/
   oidc-login, aws, gke, `tsh`, `yc`): истёкший токен client-go обновляет плагином перед
   следующим запросом, а фоновая сессия делает запросы сама (повторный watch по таймауту,
   relist). Без правила через 10 минут после ухода с prod мог бы открыться браузерный OIDC-вход
   или MFA prod-а «из ниоткуда», а фоновые неудачные входы — заблокировать учётку. Правило:
   сессия в фоне **никогда не запускает плагин**. Механизм — уже существующий `execshim` (все
   плагины идут через него): `Wrap` получает путь «флага фона» сессии
   (`$SPK_OCULAR_HOME/run/bg-<случайное>`), `SetBackground(true)` создаёт файл, `false` и `Close`
   — удаляют; шим при существующем файле плагин **не запускает** и отвечает ошибкой «цель в
   фоне: вход не выполняется». Пока выданный плагином токен жив, фон работает как обычно
   (плагин не нужен); когда нужен новый — запрос получает класс `unauthorized`, сессия зовёт
   `lost()` один раз, `Service` закрывает её (точка «открыта» гаснет, вкладки логов этой цели
   заканчиваются словами «для продолжения нужен вход — выберите цель»; возврат — холодное
   открытие, вход — по действию пользователя). Так же — 401 от сервера в фоне (статический
   токен отозван): не повторять, `lost()`. Остаточного риска «relist после таймаута вызовет
   плагин» нет: плагин в фоне не запускается вообще. Вкладки логов, оставленные пользователем,
   не исключаются: у сессии один набор учётных данных, а повторный вход — одним выбором цели
   (сказано в причине конца вкладки). Агенты: вызов агента по не выбранной цели с истёкшим
   входом получает отказ `unauthorized` «вход в кластер выполняет человек: выберите цель в
   Ocular» — вместо сегодняшнего окна входа, которое открыл бы агент, а не пользователь
   (изменение поведения P14, записать в AGENTS.md). Compose и
   синтетика интерфейс не реализуют (их кэши — контейнеры одной цели, открываются быстро;
   сессия всё равно тёплая). Почему не «держать views открытыми из UI»: скрытые таблицы
   получали бы обновления строк в WebProcess (CPU, память JS) ради того, что сервер отдаёт из
   кэша за миллисекунды.
3. **Снимок страницы цели (UI).** Модульное `Map<targetKey, WorkspaceSnapshot>` в памяти (не в
   SQLite — живёт, пока открыто приложение): вид, scope (они и так в `target_state`), фильтр,
   сортировка **по видам** (`kindId → {col, dir}` — сейчас сортировка локальна в
   `ResourceTable` и сбрасывается сменой вида; поднимается в `Workspace`), строка курсора (id),
   открытые детали (`Ref` + вкладка деталей), состояние навигации. Снимок пишется при уходе
   со страницы (размонтирование) и при каждой смене вида. При возврате: снимок главнее
   `target_state`; строки курсора/деталей, которых нет в таблице, — без ошибки (курсор на
   первой, детали закрыты — как сейчас при исчезнувшей строке). Отметки (P17) **не**
   сохраняются: смена цели их сбрасывает (решение P17-1), действие не должно касаться
   невидимого. Снимок **не удаляется** никогда (ревью P3-1), а проверяется при возврате: вида
   нет в каталоге цели (удалённый CRD, другой кластер под тем же context) — вид из
   `target_state` или вид по умолчанию, как у исчезнувшей строки курсора; причина закрытия
   сессии UI не нужна. Возврат через час — тот же вид и фильтр, таблица загрузится заново.
4. **Логи другой цели.** `dock.keepLogsOf` убирается: вкладки логов любой цели остаются, идут
   дальше и помечены как чужие (как терминалы: `foreign`, в подписи вкладки — цель). Сессию с
   открытым потоком не закрывает ни выбор другой цели, ни простой (так уже в `reapIdleSessions`).
   Закрытие вкладки освобождает поток; конец сессии по смене конфигурации — вкладка
   заканчивается «gone», как сейчас.
5. **Список целей.** `TargetsView` получает у каждой цели `open: bool` (есть живая сессия) —
   событие `targets_changed` при открытии/закрытии сессии (уже есть канал событий). В списке
   целей у открытой — точка «открыта» (`aria-label`/title «Подключение открыто»), в контекстном
   меню цели — «Закрыть подключение» (`CloseTarget(provider, id)`: закрывает сессию, её views,
   потоки — вкладки логов этой цели заканчиваются «закрыто пользователем»; у текущей цели пункта
   нет). Почему: пользователь должен видеть и уметь прекратить фоновые watch-и к prod-кластеру.
   Агенты (ревью P3-2): вызов агента в полёте `CloseTarget` не обрывает; сессия закрывается,
   **как только кончатся её вызовы** (без 60 с `agentUntil`), и не считается недавней.
   Следующий вызов агента снова откроет её (точка загорится) — сказано в подсказке пункта:
   «Закрыть подключение: watch-и и логи этой цели прекратятся; агенты с выданным доступом могут
   открыть его снова».
6. **Замеры.** kind: 200 pod-ов + прочие виды фикстуры; время от щелчка по цели до строк
   таблицы — холодная цель и возврат к тёплой (цель: тёплая ≤ 150 мс до строк) — **и тёплый
   путь доказан отсутствием нового LIST** (ревью P3-3): Go-тест сессии со счётчиком list/watch
   фейкового клиента (возврат из фона, повторный OpenView — ни одного list), kind-тест — счётчик
   запросов транспорта сессии. Private_Dirty процесса приложения и WebProcess: одна цель, три
   открытые, после закрытия двух (память возвращается); **большой кэш** (ревью P3-4): в тестовом
   namespace 3000 ConfigMap-ов и открытые во всех namespace-ах Pods, ConfigMaps и Events у каждой
   из трёх целей. Записать в «Итоги».

## Задачи

### Task 1. Недавние сессии (Go, `internal/api`)
- [ ] Порядок выбора целей, `recentTargets = 2`, `recentIdle = 10 min`; `closeOtherSessions` →
  «закрыть сверх недавних, кроме занятых (потоки, агенты)»; жнец учитывает `recentIdle` для
  недавних. Тесты (`sessions_test.go`, фейковые часы): уход с цели сессию не закрывает; третья
  покинутая — закрыта; с открытым потоком — не закрыта никогда выбором; недавняя без views —
  через 10 мин, текущая — через 60 с; смена конфигурации закрывает недавнюю; возврат к недавней —
  та же сессия (тот же `seq`, без `Open`).
- [ ] `provider.Backgrounder`; вызовы для не выбранных целей и при выборе (тест: порядок
  вызовов, повторный выбор той же цели не зовёт, сессия, открытая агентом, — в фоне); `lost()` —
  закрытие сессии, причина конца потоков (тест).
- [ ] `TargetsView.open`, событие при открытии/закрытии сессии; `CloseTarget` (не текущая;
  вызов агента в полёте не оборван, сессия закрыта с концом последнего вызова — тест; потоки
  заканчиваются). Тесты API и транспорта (Wails + HTTP).

### Task 2. Фоновые кэши и фон без входа (Go, Kubernetes, execshim)
- [ ] `execshim`: флаг фона (`--hold <path>` в `Wrap`), при существующем файле плагин не
  запускается, ответ — ошибка со словами «цель в фоне». Тесты `execshim_test.go` (плагин-
  заглушка пишет след запуска: с флагом — не запущен; без — как раньше) и через client-go
  (`TestClientGoRequestWithHangingPluginFails` рядом: запрос в фоне — `unauthorized` без запуска).
- [ ] `session.SetBackground`: файл флага; `unauthorized` (плагин отказан, 401) у фонового
  watch/list/лога — без повтора, `lost()` один раз. Тест (фейк): фон, watch кончился с 401 —
  ни одного нового list/watch, `lost` вызван; не в фоне — повтор как сейчас.
- [ ] `session.SetBackground`; `cacheManager`: в фоне не вытеснять по `grace`, только сверх
  `maxIdle`; при возврате — отсчёт `grace` с момента возврата. Тесты (`cache_test.go`, фейковые
  часы): фоновый простаивающий кэш живёт дольше `grace`; сверх `maxIdle` — вытесняется самый
  старый; после возврата — вытеснение через `grace` от возврата.
