# P3 — exec в контейнер и port-forward

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`; каждая задача —
> отдельные коммиты `area: summary`, `make check` зелёный перед коммитом.

**Цель:** из таблицы или деталей pod-а / workload-а пользователь открывает терминал в контейнере
(вкладка нижней панели рядом с логами: xterm.js, TTY, resize, копирование/вставка, выход процесса
виден с кодом, «Подключиться заново») и пробрасывает порт pod-а / Service / workload-а на
локальный порт (список активных туннелей: адрес, цель, pod, число соединений, последняя ошибка,
«Остановить», «Открыть в браузере», «Скопировать адрес»). Все туннели и терминалы закрываются при
выходе. Ошибки (нет прав `pods/exec` / `pods/portforward`, нет shell в образе, контейнер не
запущен, порт занят, pod исчез) видны по-человечески.

**Архитектура:** две provider-агностичные возможности сессии — `Execer` и `PortForwarder`.
Терминал идёт к странице по **WebSocket** на существующем сервере потоков `internal/streams`
(loopback с токеном в desktop, `/streams/<token>/` в browser-режиме), двухшаговое открытие как у
логов. Туннели живут в Go (локальный listener + upstream к pod-у), UI видит их через API и
событие-инвалидацию. Kubernetes-адаптер: `remotecommand` (WebSocket с фолбэком на SPDY) для exec,
`portforward` tunneling-dialer (WebSocket, фолбэк SPDY) + свой обработчик соединений для туннелей.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` («Потоки», «Provider API»).

## Глобальные ограничения

- Всё из P0–P2 (AGENTS.md «Правила»).
- `internal/core`, `internal/streams`, общий UI терминала и туннелей не знают pod/container/
  namespace: «контейнер» — `Channel` провайдера (как у логов), цель туннеля — `Ref` + порт.
- Потоки к UI — только через `internal/streams`, никогда через `wails://`.
- Никаких опросов: туннель выбирает pod лениво — при старте и при первом соединении после сбоя
  upstream-а, одним GET/LIST (не таймером).
- У каждого запроса к кластеру — контекст; у открытия exec/port-forward — дедлайн на рукопожатие;
  у живого терминала/туннеля клиентского таймаута нет.
- Всё ограничено: число терминалов, туннелей, соединений на туннель, непрочитанный вывод
  терминала (окно потока, см. ниже), размер управляющих сообщений.
- xterm.js — только ленивый чанк (`check-bundle.mjs`).

## Решения P3 (агент, 2026-09-29; на ревью Codex)

**Время жизни (главное UX-решение).** Логи принадлежат инкарнации сессии (им нужны informer-ы),
а терминал и туннель — нет: им нужен только `rest.Config`/транспорт target-а. Поэтому терминалы
и туннели **не закрываются** при выборе другого context-а, reaper-е сессии или пересоздании
сессии из-за изменения kubeconfig — пользователь открыл shell или туннель к БД, переключился
посмотреть другой кластер, и они продолжают работать (как у Lens и как у запущенного
`kubectl port-forward`). Закрываются явно (закрыть вкладку / «Остановить»), при выходе процесса
в контейнере (терминал), при выходе из приложения (всё). Провайдер отдаёт объект, живущий
независимо от `Session.Close()`: сессия k8s при закрытии останавливает кэши, но транспорт
(`rest.Config`, execshim) остаётся рабочим у уже созданных терминалов/туннелей — это проверяется
тестом. Снимок конфигурации берётся при открытии (изменение kubeconfig не «переезжает» открытый
туннель на другой сервер — как у процесса kubectl). Вкладка терминала и строка туннеля
показывают context, чтобы после переключения было видно, куда они ведут.

**Терминал: транспорт (спайк Task 1 подтверждает для desktop).**
- Открытие в два шага: `OpenTerminal(ref, {channel, command})` проверяет запрос и регистрирует
  одноразовый id (TTL подключения 30 с, работа начинается только после подключения);
  страница открывает `WebSocket(<wsBase>/term/<id>)`, где `wsBase` — `StreamBase` со схемой
  `ws:`. Владелец id — не сессия, а приложение (см. «Время жизни»); лимит — ≤ 16 терминалов на
  приложение, отдельно от 8 лог-потоков.
- Проверки до потребления id: токен в пути (постоянное время), точный `Host` (loopback), метод
  GET + Upgrade; **Origin обязателен** (браузер всегда шлёт его в рукопожатии WS, CSWSH):
  desktop — ровно `wails://localhost` (или то, что покажет спайк), browser — свой origin.
- Библиотека WS на сервере — `github.com/coder/websocket` (уже в desktop-бинаре через Wails,
  контекстная, `AcceptOptions` с явной проверкой Origin — свою проверку делаем сами до Accept,
  `InsecureSkipVerify` только после неё). client-go приносит gorilla для своей стороны — это его
  дело.
- Кадры: **бинарные** — байты терминала (сервер→страница: вывод; страница→сервер: ввод);
  **текстовые** — JSON управления, лимит 4 КиБ:
  страница→сервер `{"k":"resize","cols":N,"rows":N}` (1..1000), `{"k":"ack","n":bytes}`;
  сервер→страница `{"k":"state","state":"connecting|running"}`, `{"k":"exit","code":N}`,
  `{"k":"end","reason":"done|error|gone","class":…,"message":…}` и затем закрытие 1000.
- **Управление потоком вывода:** WS в браузере не даёт обратного давления, xterm копит `write`
  в памяти. Сервер держит окно 1 МиБ непотверждённых байт: пока окно исчерпано, он не читает
  stdout из kube (обратное давление доходит до контейнера, `cat` большого файла не раздувает
  память, Ctrl+C остаётся отзывчивым). Страница шлёт `ack` после callback-а `term.write` пачками
  ≥ 128 КиБ (и по таймеру 100 мс, если есть неподтверждённое). Запись в WS — с дедлайном 60 с
  (не читающая страница отключается, как у логов).
- Коалесцирование вывода: чтение stdout буфером 32 КиБ, отправка сразу (интерактивная задержка
  важнее числа кадров); спайк проверит, не придерживает ли WebKitGTK хвост у WS так же, как у
  fetch (если да — тот же «толчок»).
- Resize: последняя величина побеждает (канал на 1 место), первая — до старта exec (размер
  xterm известен до подключения: передаётся в `OpenTerminal`), потом по `ResizeObserver` + fit
  с дебаунсом 50 мс.

**Терминал: Kubernetes.**
- `remotecommand.NewFallbackExecutor(websocket, spdy, httpstream.IsUpgradeFailure)` поверх
  `rest.Config` сессии (execshim уже внутри); `StreamWithContext` с TTY, stdin, stdout (stderr
  с TTY сливается), `TerminalSizeQueue`.
- Команда по умолчанию — поиск shell: `["sh", "-c", "if command -v bash >/dev/null 2>&1; then
  exec bash; elif command -v ash >/dev/null 2>&1; then exec ash; else exec sh; fi"]` (без `clear`,
  чтобы не терять вывод). Нет `sh` (distroless) → ошибка kube «executable file not found»
  переводится в понятное «в контейнере нет /bin/sh — укажите команду». Своя команда — поле в
  диалоге открытия, разбирается на argv по пробелам с кавычками (`'…'`, `"…"`, без подстановок).
- Контейнер: `ExecInfo(ref)` → каналы (контейнеры pod-а, для workload-а — выбор pod-а: самый
  новый готовый, как у логов; init/ephemeral — только запущенные), default — аннотация
  `kubectl.kubernetes.io/default-container`, иначе первый. Не запущенный контейнер —
  `bad_request` с состоянием контейнера. Для workload-а терминал открывается в конкретном pod-е
  (его имя — в заголовке вкладки), а не «в workload-е».
- Выход процесса: `exec.CodeExitError` → `exit{code}`, успех → `exit{0}`; затем `end{done}`.
  UI пишет в терминал `[процесс завершён, код N]` и показывает «Подключиться заново» (новый id,
  тот же канал/команда; экран не очищается — продолжение ниже разделителя).
- Закрытие вкладки / выход приложения → отмена контекста → соединение exec закрывается, runtime
  закрывает pty, shell получает SIGHUP. Проверяется на kind: после закрытия вкладки в контейнере
  не остаётся процесса shell.

**Туннели (port-forward).**
- Возможность `PortForwarder`: `ForwardInfo(ref)` → порты цели (имя, номер, протокол; только TCP —
  UDP Kubernetes не пробрасывает); `Forward(ctx, ref, remotePort) (Upstream, error)` — фабрика
  соединений: `Dial(ctx) (net.Conn-подобный поток, podLabel, error)`, провайдер сам выбирает и
  переизбирает pod. Ядро (`internal/forwards`) владеет listener-ами, счётчиками, состояниями и
  лимитами — это переиспользуемо, провайдер отвечает только за «дай поток к порту цели».
- Цели: Pod (порты контейнеров; любой порт вручную), Service (порты сервиса → `targetPort`,
  включая именованный, по контейнерам выбранного pod-а), Deployment/StatefulSet/DaemonSet/
  ReplicaSet (порты шаблона). Pod для Service — по selector-у, для workload-а — по UID контроллера
  (как в связях P1): предпочтительно Ready, затем Running, самый новый; для Pod-цели — сам pod
  с проверкой UID (одноимённая замена → ошибка «pod заменён», туннель не переезжает молча).
- Upstream к pod-у — одно соединение port-forward (tunneling WebSocket-dialer с фолбэком на SPDY,
  `portforward.NewFallbackDialer`), на каждое локальное TCP-соединение — пара потоков
  error/data с `requestID` (обработчик — порт `handleConnection` из client-go, Apache 2.0).
  Upstream умер (pod удалён, сеть) → текущие соединения закрываются, туннель в состоянии
  «ожидание», **следующее** локальное соединение переизбирает pod и открывает новый upstream
  (лениво, без таймеров); Service/workload переживает rollout. Ошибка из потока error
  kubelet-а (порт не слушает) — это ошибка соединения, а не туннеля: соединение закрывается,
  ошибка — в «последней ошибке».
- Локальный адрес: `127.0.0.1:<порт>` и best effort `[::1]:<тот же порт>` (браузеры резолвят
  `localhost` и в ::1). Порт по умолчанию — удалённый, если ≥ 1024 и свободен, иначе случайный;
  пользователь может ввести свой; занят → ошибка `conflict` сразу при старте (listener открывается
  синхронно в `StartForward`). Только loopback — наружу не слушаем никогда.
- Лимиты: ≤ 32 туннеля, ≤ 64 одновременных соединений на туннель (дальше — accept и сразу
  закрыть, счётчик отказов); дедлайн рукопожатия upstream-а 15 с.
- Состояния туннеля: `listening` (соединений нет), `active` (N соединений), `error` (последняя
  ошибка upstream-а/выбора pod-а; туннель продолжает слушать и пробует на следующем соединении),
  `stopped` (строка исчезает). Счётчики: соединений всего/сейчас, байт in/out, последняя ошибка с
  временем, текущий pod.
- API: `ListForwards()`, `ForwardInfo(ref)`, `StartForward(ref, remotePort, localPort)`,
  `StopForward(id)`; событие `forwards_changed` (ключ `forwards`, коалесцирование 250 мс — байты
  не спамят событиями) → UI перечитывает список. Туннели не сохраняются между запусками
  (бэклог).

**UI.**
- Нижняя панель обобщается: вкладки `logs` и `terminal` (иконка вида), тот же dock, та же
  высота. Вкладка терминала: заголовок `контейнер · pod`, подсказка с context-ом; неактивные
  вкладки остаются смонтированными (xterm не пересоздаётся).
- Точки входа: кнопка «Терминал» в деталях (kinds с `Exec`), горячая клавиша `S` (shell) в
  таблице, как `L` для логов; диалог выбора контейнера/команды — только если контейнеров > 1 или
  нужна своя команда (Shift+S / пункт «Терминал…»), иначе сразу default. `KindDescriptor`
  получает флаги `Exec` и `Forward`.
- Горячие клавиши приложения не срабатывают, пока фокус в терминале (`Ctrl+K`, `/`, `L`, `S`,
  Escape) — терминал получает всё; выход фокуса — клик вне. Копирование — выделение +
  `Ctrl+Shift+C`, вставка — `Ctrl+Shift+V` и нативная вставка; проверяется в desktop.
- Туннели: индикатор в строке состояния «⇄ N» (виден, если N > 0) открывает панель списка
  туннелей (в правом drawer-е или popover-е); в деталях объекта — секция «Порты» с кнопкой
  «Пробросить» на порт → маленький диалог (локальный порт, предзаполнен) → туннель в списке,
  адрес можно скопировать/открыть (`http://localhost:<порт>`, в desktop — внешний браузер через
  Wails `Browser.OpenURL`).
- xterm: `@xterm/xterm` + `@xterm/addon-fit` (без WebGL-аддона — DOM/canvas рендерер, память),
  scrollback 5000, тема из токенов Darcula, шрифт как у лог-вьюера.
