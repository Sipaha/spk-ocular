# P3 — exec в контейнер и port-forward

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`; каждая задача —
> отдельные коммиты `area: summary`, `make check` зелёный перед коммитом.

**Цель:** из таблицы или деталей pod-а / workload-а пользователь открывает терминал в контейнере
(вкладка нижней панели рядом с логами: xterm.js, TTY, resize, копирование/вставка, выход процесса
виден с кодом, «Подключиться заново») и пробрасывает порт pod-а / Service / workload-а на
локальный порт (список активных туннелей: адрес, цель, context, pod, соединения, последняя
ошибка, «Остановить», «Скопировать адрес», «Открыть» для HTTP-портов). Все туннели и терминалы
закрываются при выходе. Ошибки (нет прав `pods/exec` / `pods/portforward`, нет shell в образе,
контейнер не запущен, порт занят, pod исчез или заменён) видны по-человечески.

**Архитектура:** две provider-агностичные возможности сессии — `Execer` и `PortForwarder`, —
которые, пока сессия жива, выдают **независимые хэндлы** (снимок подключения + закреплённая
цель); хэндлом дальше владеет приложение, а не сессия. Терминал идёт к странице по
**WebSocket** на сервере потоков `internal/streams` (loopback с токеном в desktop,
`/streams/<token>/` в browser-режиме) с окнами подтверждений в обе стороны. Туннели —
provider-агностичный менеджер `internal/forwards` (локальные listener-ы, соединения, лимиты,
состояния) поверх фабрики upstream-ов провайдера. Kubernetes: `remotecommand` (WebSocket, фолбэк
SPDY) для exec; port-forward — свой обработчик потоков поверх соединения, открытого
контекст-зависимым согласованием (WebSocket-туннель, фолбэк SPDY).

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` («Потоки», «Provider API»).
**Спайк:** `docs/spikes/2026-09-29-terminal-websocket-desktop.md` (WS из desktop-окна работает,
хвост не придерживается, Origin `wails://localhost`).

## Глобальные ограничения

- Всё из P0–P2 (AGENTS.md «Правила»).
- `internal/core`, `internal/streams`, `internal/forwards`, общий UI терминала и туннелей не знают
  pod/container/namespace: «контейнер» — `Channel`, «pod» — `Instance` провайдера (ключ + подпись),
  цель туннеля — `Ref` + порт.
- Потоки к UI — только через `internal/streams`, никогда через `wails://`. Трафик туннелей — только
  на своих loopback-listener-ах, никогда не монтируется в маршрутизатор с токеном (произвольные
  TCP-клиенты не несут токен — это свойство port-forward; защита — только loopback).
- Никаких опросов инвентаря: туннель выбирает pod при старте и при первом новом соединении после
  смерти upstream-а (одним GET/LIST). Пинги транспорта (живость соединения) — не опрос.
- У каждого запроса к кластеру — контекст, отменяющий реальный ввод-вывод (не «бросить горутину
  по таймеру»).
- Всё ограничено: терминалы, туннели, соединения (на туннель и на приложение), непотверждённый
  вывод и ввод терминала, размеры сообщений, тело ошибки kubelet-а.
- xterm.js — только ленивый чанк (`check-bundle.mjs`).

## Решения P3 (агент, 2026-09-29; уточнены ревью Codex и спайком)

### Время жизни и владение

- Логи остаются привязаны к инкарнации сессии (им нужны informer-ы), терминалы и туннели — нет.
  Правило «один активный context» уточняется: **одна активная сессия просмотра** (кэши, виды,
  логи); терминалы и туннели — отдельно владеемые живые ресурсы, которые переживают выбор
  другого target-а, reaper и пересоздание сессии из-за изменения kubeconfig (как запущенный
  `kubectl port-forward`). Закрываются явно (вкладка / «Остановить»), при выходе процесса
  (терминал) и при выходе из приложения. Спецификация и тесты обновляются.
- Провайдер, пока сессия валидна, выдаёт **хэндл** (`ExecHandle`, `ForwardHandle`): неизменяемый
  снимок идентичности подключения (сервер, TLS, прокси, impersonation, способ аутентификации —
  собственный клиент из копии `rest.Config`), закреплённая цель (UID-ы) и собственный жизненный
  контекст + `Close`. Хэндл не держит ни ссылки на сессию, ни её контекста/кэшей
  (`Session.Close` отменяет свой ctx и кэши — хэндл это переживает; тест). Получение хэндла и
  передача его менеджеру сериализованы с закрытием приложения: после `Close` менеджера поздняя
  регистрация закрывает хэндл и отвечает `gone`.
- «Снимок» — это адрес и настройки, **не** замороженные учётные данные: token-файлы, сертификаты
  из файлов и exec-плагины (через execshim) обновляются как обычно. Если аутентификация перестала
  проходить — ошибка видна; на новую конфигурацию хэндл молча не переезжает. Секреты не
  логируются, не показываются, не попадают в SQLite.
- У живых ресурсов видно, куда они ведут: context + сервер (host) снимка; если target с тем же
  именем теперь указывает на другой сервер (хеш конфигурации сменился) — пометка «конфигурация
  context-а изменилась после открытия».
- «Подключиться заново» (терминал) использует **тот же снимок и тот же закреплённый pod/канал**;
  pod исчез или заменён → ошибка с предложением «Открыть новый терминал» (это уже новое открытие
  через текущую сессию, с текущей конфигурацией — отдельное явное действие). Своя команда
  автоматически не повторяется: «Подключиться заново» для неё открывает диалог с этой командой.

### Provider API (эскиз, уточняется в Task 2)

```go
type Execer interface {
    ExecInfo(ctx, ref) (core.ExecInfo, error) // каналы, экземпляры (pods) с default, состояния
    PrepareExec(ctx, ref, ExecRequest{Instance, Channel string; Command []string}) (ExecHandle, error)
}
type ExecHandle interface {
    Describe() core.LiveTarget            // target, endpoint, instance/channel подписи, argv
    Run(ctx, Terminal) (ExitStatus, error) // однократно; перед exec сверяет UID pod-а
    Again() (ExecHandle, error)            // тот же снимок и цель — для «Подключиться заново»
    Close()
}
type Terminal struct { Stdin io.Reader; Stdout io.Writer; Sizes TermSizes } // Sizes.Next → nil на отмене
type ExitStatus struct { Code int; Known bool } // Known=false: процесс мог остаться, статус не получен

type PortForwarder interface {
    ForwardInfo(ctx, ref) (core.ForwardInfo, error) // порты цели (имя, номер, протокол, appProtocol)
    PrepareForward(ctx, ref, ForwardPort) (ForwardHandle, error)
}
type ForwardHandle interface {
    Describe() core.LiveTarget
    Connect(ctx) (Upstream, error) // выбрать pod (закреплённый логический UID), разрешить порт, согласовать
    Close()
}
type Upstream interface {
    Label() string                 // выбранный pod и разрешённый порт
    Open(ctx) (Stream, error)      // пара потоков error/data с уникальным requestID
    Done() <-chan struct{}; Err() error
    Close()
}
type Stream interface {
    io.Reader; io.Writer
    CloseWrite() error // полузакрытие: запрос отправлен, ответ ещё читается
    Close() error      // сброс обоих потоков и удаление из соединения
    Result() error     // сообщение потока error (≤ 4 КиБ) после завершения; ошибка этого соединения
}
```

### Терминал: транспорт к странице

- Открытие в два шага: `OpenTerminal({ref, instance, channel, command, cols, rows})` — размер
  обязателен и проверяется (1..1000), — получает хэндл и регистрирует одноразовый id (TTL 30 с;
  истечение/отказ закрывают хэндл). Страница открывает `WebSocket(<wsBase>/term/<id>)`.
- Реестр потоков различает **виды** (`logs`, `term`): маршрут принимает только id своего вида,
  лимиты раздельные и считают и ожидающие id (logs ≤ 8, term ≤ 16), владелец `term` —
  приложение.
- Проверки **до** потребления id: токен (постоянное время), точный `Host`, GET, корректные
  заголовки Upgrade (`Upgrade: websocket`, `Connection: upgrade`, версия 13, ключ), **Origin
  обязателен** и точен (desktop `wails://localhost`, browser — свой origin). Затем резерв id →
  `Accept` (`coder/websocket`, собственная проверка Origin сделана, `InsecureSkipVerify` только
  после неё) → commit; ошибка `Accept` освобождает хэндл. Никакого exec в кластере до
  установленного WS.
- Кадры: бинарные — байты терминала (вывод / ввод, входящее сообщение ≤ 32 КиБ); текстовые —
  JSON ≤ 4 КиБ. Страница → сервер: `resize{cols,rows}`, `ack{n}` (n — **накопительное** число
  обработанных xterm байт вывода). Сервер → страница: `state{connecting|running}`, `iack{n}`
  (накопительное число байт ввода, записанных в stdin), `exit{code}` (только если статус реально
  получен), `end{reason: done|error|gone, class, message}`, затем закрытие 1000.
- **Потоки внутри сервера:** один читатель WS, который никогда не блокируется: ввод — в
  ограниченную очередь (256 КиБ), resize — в ящик «последнее значение» (старое заменяется), ack —
  атомарно в счётчик кредита; отдельный копировщик очереди в stdin (после записи — `iack`);
  отдельный читатель stdout, который резервирует кредит **до** отправки (ожидание кредита
  отменяемо); один упорядоченный писатель WS для байтов и управляющих кадров (порядок: весь
  вывод → `exit` → `end`). Никакая блокировка не удерживается во время ожидания кредита или
  записи в сеть.
- **Кредиты:** вывод — окно 1 МиБ непотверждённых байт (сырые `byteLength`, `binaryType =
  arraybuffer`, xterm получает `Uint8Array`); ввод — страница держит не больше 256 КиБ в полёте
  (по `iack`), вставка режется на куски ≤ 16 КиБ в клиентскую очередь ≤ 4 МиБ (больше — видимый
  отказ «вставка слишком большая», байты не теряются молча), очередь отменяется при закрытии/
  переподключении. Сервер проверяет `ack`/`iack`-инварианты: n — конечное целое, не убывает, не
  больше отправленного; нарушение или переполнение входной очереди — закрытие 4002 «нарушение
  протокола».
- **Живость:** WS-ping каждые 20 с с таймаутом 15 с (отдельный контекст, не жизнь ресурса);
  окно вывода исчерпано и нет `ack` 60 с → `end{error, "страница не читает вывод"}`; запись с
  дедлайном 60 с. Скрытая вкладка: xterm продолжает разбирать вывод (`display:none` не
  останавливает JS), значит `ack` идут; свёрнутое окно — проверяется в desktop.
- **Завершение:** `Run` вернулся → оставшийся вывод досылается в пределах кредита не дольше 10 с
  (иначе `end{error, "вывод не дочитан"}`), затем `exit` (если статус известен) и `end{done}`;
  ошибка транспорта ≠ `exit{0}`. Закрытие менеджера/приложения: явно отменяет все терминалы,
  закрывает их WS (`http.Server.Close` не закрывает hijacked-соединения), будит ожидания кредита
  и копировщики, закрывает хэндлы и дожидается всех горутин.
- Resize: начальный размер — из `OpenTerminal`; `Sizes.Next` отдаёт последний, `nil` на отмене.

### Терминал: Kubernetes

- `remotecommand.NewFallbackExecutor(websocket(GET), spdy(POST), pred)` поверх клиента снимка;
  `pred` — как у kubectl: `httpstream.IsUpgradeFailure(err) || httpstream.IsHTTPSProxyError(err)`
  (только ошибка согласования до запуска — команда не может выполниться дважды).
  `StreamWithContext`: TTY, stdin, stdout (stderr с TTY сливается), `TerminalSizeQueue`.
- Отдельного дедлайна рукопожатия у exec **нет** (executor не сообщает момент установки, а
  дедлайн на весь ctx убил бы живую сессию): состояние «подключение…» видно и отменяемо закрытием
  вкладки. У SPDY-пути есть таймауты dial/TLS транспорта client-go, а у WebSocket-пути **нет**:
  client-go v0.37 строит gorilla-`Dialer` с `HandshakeTimeout=0`, и пир, придерживающий TLS или
  заголовки upgrade, держит «подключение…» до отмены пользователем — это и есть политика
  (задокументирована). Сетевая часть отменяема сразу; дочерний процесс exec-плагина живёт по
  своим правилам execshim (≤ 90 с) — немедленное его завершение не обещаем.
- Экземпляр: `ExecInfo(ref)` для pod-а — он сам; для workload-а — его pods по UID контроллера
  (все страницы LIST, не усечённые «связи»), только неудаляемые и Running с выбранным
  контейнером, default — Ready, самый новый. `PrepareExec` закрепляет UID pod-а; `Run` сверяет
  UID (GET) непосредственно перед exec (узкая гонка имени до запроса exec в API не закрывается —
  задокументировано). Канал: контейнеры pod-а (init/ephemeral — только запущенные), default —
  аннотация `kubectl.kubernetes.io/default-container`, иначе первый; не запущен — `bad_request`
  с состоянием.
- Команда по умолчанию: `["sh", "-c", "if command -v bash >/dev/null 2>&1; then exec bash;
  elif command -v ash >/dev/null 2>&1; then exec ash; else exec sh; fi"]`. Ошибка «executable file
  not found» → «в PATH контейнера нет `sh` — укажите команду». Своя команда: argv без
  интерпретации shell; разбор — пробелы разделяют, `'…'` буквально, `"…"` с `\"` и `\\`,
  `\` вне кавычек экранирует следующий символ, `''` — пустой аргумент, незакрытая кавычка —
  ошибка разбора.
- Выход: `exec.CodeExitError` → `exit{code}`, `nil` → `exit{0}`; иначе ошибка без `exit`.
- Гарантия при закрытии: закрываем своё соединение exec и всё локальное; завершение процесса в
  контейнере — **best effort** (зависит от runtime: закрытие pty обычно даёт shell SIGHUP, но
  фоновые/отвязанные процессы и перехватчики HUP живут; см. kubectl#1076). Kind-тест проверяет
  интерактивный shell и shell с долгим foreground-процессом; никаких «уборок» чужих процессов
  дополнительным exec-ом.

### Туннели

- **Менеджер `internal/forwards`** (provider-агностичный): listener-ы, лимиты (≤ 32 туннеля,
  ≤ 64 соединения на туннель, ≤ 256 на приложение, буфер копирования 32 КиБ), состояния,
  счётчики, событие. Accept никогда не ждёт upstream (соединение ждёт в своей горутине со своим
  контекстом); сверх лимита — принять и сразу закрыть (+ счётчик отказов).
- **Поколения upstream-а:** на туннель — не больше одной попытки `Connect` одновременно
  (singleflight, отменяемая), остальные соединения ждут её со своими контекстами; установка
  нового upstream-а — только если туннель жив и поколение текущее; каждое соединение
  закрепляет своё поколение; очистка старого поколения никогда не трогает новое. Смерть
  upstream-а закрывает его соединения; **только новые** соединения выбирают pod заново.
  Повтор — лишь для этапа настройки (открытие потоков упало, из локального соединения ещё не
  прочитано ни байта), один раз; соединение, по которому шли байты, не переигрывается на другой
  pod.
- **Stop:** сначала пометить закрытым, закрыть listener-ы, отменить ожидаемый `Connect`, закрыть
  локальные соединения и upstream, затем дождаться горутин; без сети и ожиданий под блокировкой
  менеджера. Поздний успешный `Connect` после Stop закрывается.
- **Адреса:** порт по умолчанию — удалённый, если ≥ 1024: попытка bind атомарно, при занятости —
  `:0` (без проверки-потом-bind); явный порт — занят → `conflict` без подбора. Затем ::1 на **том
  же** порту best effort, результат — отдельный статус. Показывается фактический адрес
  `127.0.0.1:<порт>` (и `[::1]:<порт>`, если занят нами); `localhost` не рекламируется (он может
  резолвиться в ::1 чужого процесса). Сбой после bind (регистрация, гонка со Stop) откатывает
  все listener-ы.
- **«Открыть»** — только для HTTP-подобных портов (имя/`appProtocol` содержит `http`/`https`, или
  пользователь явно выбрал схему); иначе по умолчанию «Скопировать адрес». Desktop открывает
  через Wails `Browser.OpenURL`; в тестах — подменённый открыватель.
- **Событие** `forwards_changed`: смена состояния — сразу, счётчики байт/соединений — не чаще
  раза в секунду (последнее состояние, не сброс таймера на каждый байт).

### Туннели: Kubernetes

- **Согласование с контекстом:** штатные dialer-ы client-go не принимают контекст (tunneling —
  `context.Background()`, SPDY — `http.NewRequest`). Поэтому своя тонкая обёртка: запрос
  согласования строится с контекстом попытки (порт `negotiateSPDYOverWebsocket` для
  WebSocket-туннеля, `spdy.Negotiate` с запросом-с-контекстом для SPDY), фолбэк — как у kubectl
  (`IsUpgradeFailure || IsHTTPSProxyError`). Отмена рвёт реальный dial/TLS/рукопожатие; поздний
  результат закрывается. Дедлайн согласования 15 с; живость установленного соединения — пинги
  транспорта (WS-туннель: 10 с у client-go; SPDY: `PingPeriod` 10 с) — обнаружение мёртвого пира
  проверяется тестом, а не предполагается.
- **Потоки:** механика `handleConnection` client-go (Apache 2.0) — поток error (полузакрыт с нашей
  стороны), затем data с тем же портом и уникальным `requestID` (атомарный счётчик на
  соединение), — но с исправлениями: ошибка потока error или открытия data — ошибка **этого**
  соединения, общий upstream не закрывается; ожидание результата error ограничено (время и
  4 КиБ тела) и отменяемо; при любом исходе оба потока сбрасываются и удаляются. WebSocket-туннель
  несёт тот же SPDY-протокол — никаких «портовых» префиксов WS-протокола v4/v5 для port-forward.
- **Цели и выбор pod-а:** закрепляется логическая цель (UID Pod / Service / workload). Pod —
  сам (UID сверяется; замена → «pod заменён», не переезжаем). Service — GET при каждом выборе
  (UID сверяется; правки selector/targetPort того же UID учитываются со следующего соединения
  и видны в подписи); без selector и ExternalName → `unsupported`; headless с selector работает.
  Workload — pods по UID контроллера, все страницы LIST. Кандидаты — неудаляемые Running (не
  Succeeded/Failed) с разрешимым портом; Ready предпочтительнее, затем новее.
- **Порт Service:** выбор — `spec.ports[]` по номеру или имени, только TCP (UDP/SCTP → `unsupported`);
  `targetPort` пуст/0 → номер порта сервиса; числовой — как есть (объявленный containerPort не
  нужен); именованный — по TCP-портам контейнеров **выбранного** pod-а, заново при каждой смене
  pod-а; нет или неоднозначно → ошибка, без угадывания. Pod/workload — номер порта контейнера
  (или любой вручную для Pod).
- `pods/portforward` и `pods/exec` адресуются по имени: предварительная сверка UID сужает, но не
  закрывает гонку — тест показывает отказ при известной замене, гонка задокументирована.

## Находки реализации (Task 2–4, 2026-09-29)

- **Процессы exec не умирают при разрыве соединения** (kind/containerd, измерено): отмена exec
  оставляет в контейнере и shell, и его foreground-процесс; закрытие stdin до TTY как EOF не
  доходит. Поэтому мост терминала при закрытии вкладки / выходе приложения «вешает трубку»
  in-band: `^C`, через 100 мс `^D` (завершает shell на опустевшей строке), вывод при этом
  дочитывается и выбрасывается; только если команда не завершилась за 2 с — отмена. Измерено на
  kind: shell + `sleep` завершаются за ~25 мс, процессов не остаётся
  (`TestKindTerminalClosingTheTabEndsTheShellAndItsChild`; без моста —
  `TestKindExecCancelAloneLeavesTheShell`). Программы, игнорирующие `^C`/`^D` (vim), могут
  остаться — best effort, как и было обещано.
- **Фолбэк exec на SPDY не срабатывал бы никогда**: client-go v0.37 возвращает
  `UpgradeFailureError` из `k8s.io/streaming/pkg/httpstream`, а одноимённый предикат устаревшего
  `apimachinery/pkg/util/httpstream` его не узнаёт. Предикат — из `streaming`
  (`TestFallbackRecognisesClientGoUpgradeFailures`, тест SPDY-зависания).
- **Рукопожатие не отменялось контекстом ни на WS-, ни на SPDY-пути** (gorilla и SPDY round
  tripper читают ответ upgrade без контекста). Решение (`upgrade.go`): WS — httptrace-хук
  `GotConn` закрывает соединение по отмене; SPDY — свой upgrader (dial client-go, ожидание ответа
  под контекстом, после рукопожатия контекст его больше не держит). Тест: TLS-зависание,
  зависание заголовков WS, зависание SPDY после отказа WS — всё заканчивается отменой, горутин нет.
- **Начальный размер TTY приходит отдельным каналом**: команда, стартующая мгновенно
  (`sh -c 'stty size'`), может увидеть 0×0 — свойство протокола exec (как у kubectl); интерактивный
  shell успевает.
- «Подключиться заново»: API хранит подготовленный хэндл-прототип под `terminalId`
  (`ReopenTerminal` запускает копию с тем же снимком и pod-ом, `ForgetTerminal` при закрытии
  вкладки, ≤ 64 прототипа).
- Фикстуры kind: pod `noshell` (образ `pause`), в `kind-rbac.sh` проверка, что у `viewer` нет
  `pods/exec` и `pods/portforward`.

## Находки реализации (Task 5, 2026-09-30)

- **`StartForward` синхронно делает первый `Connect`**: туннель регистрируется (виден как
  `connecting`, считается в лимите), слушает и ждёт установки; неудача первого подключения
  (`forbidden`, pod не найден, нет кандидатов) откатывает туннель и становится ошибкой вызова —
  пользователь видит её в диалоге, а не «мёртвый» туннель в списке. Дальнейшие неудачи — состояние
  `error` с последней ошибкой; следующее соединение пробует снова.
- **Stop не ждёт `Connect`, игнорирующий отмену** (найдено тестом «поздний успех»): иначе
  несговорчивый провайдер вешал бы «Остановить» и выход из приложения. Stop отменяет контекст,
  ожидающие соединения сразу получают «остановлен», а закрытие хэндла (и позднего upstream-а)
  делает сама горутина `Connect`, когда вернётся; `Manager.Close` ждёт такие горутины ≤ 2 с.
- **Короткое удержание неудачи**: 1 с после неудачного `Connect` новые соединения получают ту же
  ошибку без нового подключения — клиент, переподключающийся в цикле (пул БД, браузер), не
  долбит кластер.
- **Контракт `Stream.Result`**: ждёт отчёт потока error ограниченно и сразу возвращается, если
  поток или upstream закрыты; у чистого соединения поток error закрывается пустым вместе с данными
  (иначе каждое соединение висело бы до таймаута и упиралось в лимит 64 — так фейк сначала и
  вёл себя: 2000 последовательных соединений шли 63 с вместо 0,7 с).
- Соединение освобождается, когда закончилась удалённая сторона (как у kubectl): закрытие клиентом
  — полузакрытие потока, ответ дочитывается. Поэтому быстрый цикл «открыть-закрыть» может
  кратковременно упереться в лимит 64 — это ожидаемо (сверх лимита — принять и закрыть, счётчик
  `rejected`).
- Порт: неверная схема/порт проверяются в API **до** `PrepareForward` (ничего не готовится);
  привилегированный явный порт → `forbidden` «нужен порт ≥ 1024»; авто-режим при удалённом
  порте < 1024 сразу берёт любой свободный.

## Ревью плана (Codex, 2026-09-29)

Два сообщения, 11 замечаний, и уточнение по исправленному плану (у WS-пути exec нет
таймаута рукопожатия вообще — только отмена; повторный накопительный `ack` не ошибка); все признаны по существу и внесены выше. Кратко и где
расходимся:
1. Штатные dialer-ы port-forward не отменяемы → своё согласование с контекстом (принято). Для
   exec отдельный дедлайн рукопожатия **не вводим** (executor не сообщает момент установки):
   честное «подключение…» с отменой и таймауты транспорта/execshim.
2. Независимый хэндл вместо смены строки-владельца; закрепление pod-а в тикете; dock над keyed
   `Workspace`; id вкладки с target-ом (принято).
3. Снимок = адрес/настройки, не учётные данные; видимость context-а и сервера; «Подключиться
   заново» — тот же снимок, новый target — явное новое открытие (принято).
4. Кредиты только на вывод давали взаимоблокировку с большой вставкой → неблокирующий читатель,
   очередь ввода, `iack`-окно, накопительные ack, упорядоченный писатель, таймаут прогресса
   (принято).
5. Завершение удалённого процесса — best effort, без «уборки» чужих процессов (принято).
6. `handleConnection` client-go закрывает весь upstream на ошибке одного соединения и может
   зависнуть → переносим механику с исправлениями (принято).
7. Поколения и singleflight upstream-а, не переигрывать соединения с байтами, пинги, общий
   лимит соединений, частота события (принято).
8. Разрешение портов Service, selectorless/ExternalName/UDP, закрепление логического UID,
   только живые кандидаты (принято).
9. `localhost` может указывать на чужой ::1 → показываем фактические адреса; «Открыть» только
   для HTTP-подобных; атомарный bind (принято).
10. Предикат фолбэка как у kubectl, резерв → Accept → commit, виды id в маршрутах, закрытие
    hijacked WS при выходе (принято).
11. Размер в DTO, геометрия скрытой вкладки, поколения на клиенте, вывод как недоверенные
    данные, разбор argv, своя команда не повторяется автоматически (принято). Сценарии
    насыщения из «спайка» перенесены в Task 10: транспорт спайк закрыл, остальное — свойства
    реализации.

## Вне P3 (бэклог)

- Ephemeral debug-контейнеры (`kubectl debug`), attach к процессу без exec.
- Восстановление туннелей и терминалов после перезапуска приложения.
- UDP-туннели (Kubernetes не умеет), проброс наружу (не loopback) — сознательно не делаем.
- Запись сессии терминала в файл.
