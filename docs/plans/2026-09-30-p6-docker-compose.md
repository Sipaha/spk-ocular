# P6 — Docker Compose provider: просмотр и логи

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`; каждая задача —
> отдельные коммиты `area: summary`, `make check` зелёный перед коммитом; каждое исправление и
> каждая возможность начинаются с теста, который падает без них.

**Цель:** в списке target-ов рядом с kube contexts — Docker contexts (Docker Engine endpoint-ы).
Открыв один, пользователь видит compose-проекты как scopes и в них — сервисы, контейнеры,
сети, тома, образы с живым состоянием и health (state + healthcheck), детали (факты, YAML
inspect, связи) и логи контейнера и сервиса целиком. Всё — через те же `core`/`provider`/общий
UI: второй провайдер доказывает абстракцию. Терминал, CPU/RAM и действия — следующий этап
P7 (решения по ним, принятые на ревью, — в конце документа), чтобы просмотр был готов раньше
и каждый этап проверялся целиком.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` — «Проверка абстракции на
Docker Compose» (таблица соответствий и уточнение после ревью), «Provider API», «Живые
таблицы» (контракт Watch), «Ключевые технические решения» (время без опроса, одна активная
сессия, действия, никаких фоновых опросов), бэклог (долг общего UI из ревью P5).

## Глобальные ограничения

- Всё из P0–P5 (AGENTS.md «Правила»). В `internal/core`, `internal/api` и общем UI не
  появляются container/compose/project; Kubernetes-знание, оставшееся в общем UI (вид `pods`
  по умолчанию, `defaultNamespace`, связанный вид `events`, подпись scope в диалоге), уходит
  в метаданные провайдера (Task 1).
- Никаких фоновых опросов демона и переподключений «для надёжности»: состояние — список +
  поток `/events` как подсказка + явное «Перечитать» пользователя (решение 2).
- Credentials (TLS-ключи context-а) не покидают Go: нет в БД, DTO, логах, событиях.
- Все запросы к демону — с контекстом и таймаутом; у потоков (events, logs, exec) — дедлайн
  только на заголовки, как у watch Kubernetes.
- Тесты с записью и нагрузкой — **только на изолированном тестовом демоне** (Task 0), никогда
  на демоне пользователя: там идут его контейнеры (compose-проект SPK_launcher и др.).
  Endpoint тестового демона проверяется до любой мутации, как kubeconfig kind.
- UX важнее экономии памяти; считается только Private_Dirty.
- Вне P6: терминал, статистика, действия — P7. Бэклог: чтение compose-файлов (желаемое число реплик, сервисы без контейнеров,
  scale/create/up/down), endpoint-ы `ssh://` (нужен `docker system dial-stdio`), Problems для
  Compose, Docker provider для контейнеров вне compose, Swarm, podman, build, push/pull образов,
  events как вид.

## Что уже есть (обзор 2026-09-30)

- Контракт `provider.Session` (Watch/Get/Scopes/ScopeKind), опциональные `LogSource`,
  `Execer`, `MetricsSource`, `Actioner`, `TargetWatcher`, `CommandAliaser`. Compose реализует
  в P6 — Session, `LogSource`, `TargetWatcher`, `CommandAliaser`; в P7 — `Execer`,
  `MetricsSource`, `Actioner`; `PortForwarder` — никогда (порты уже опубликованы).
- `internal/views` (hot-layer видов), `internal/streams` (логи и терминалы к UI), менеджер
  сессий API — provider-агностичны; синтетический провайдер показывает, что UI обходится без
  Kubernetes, но в `Workspace`/`ResourceDrawer`/`ActionDialog` остались вшитые `pods`,
  `events`, `defaultNamespace`, `action.namespace` (ревью P5).
- На машине: Docker 29.3.1 (API 1.54), Compose v5.1.1, текущий context `rootless`
  (`unix:///run/user/1000/docker.sock`), `default` — `unix:///var/run/docker.sock` (нет
  сокета). Образ `docker:29-dind` есть локально.

## Решения P6 (агент, 2026-09-30; пересмотрены по ревью Codex)

### 1. Клиент Docker Engine — свой, тонкий

Свой HTTP-клиент поверх `net/http` (`internal/providers/compose/engine`): P6 нужны `_ping`,
`/info`, containers list/inspect, networks, volumes, images, events, logs. Официальный клиент
не исключён навсегда, но тяжёлые обязанности — жизненный цикл соединения, ограничения тел,
версии, отсутствие повторов — наши при любом выборе; свой клиент делает их явными и
тестируемыми. Правила:
- Транспорт `unix://`, `tcp://`, `tcp://`+TLS (CA, cert/key context-а или `DOCKER_CERT_PATH`);
  неполная/битая TLS-пара — ошибка target-а, **никогда** тихий переход на plaintext.
  Редиректы запрещены (`CheckRedirect` → ошибка); прокси — как у docker CLI
  (`go-connections`): для `tcp://` — из окружения (`HTTPS_PROXY`/`NO_PROXY`), для `unix://`
  — нет.
- Версия — лениво, при первом запросе сессии (не в `Discover`, не в `Session.Open` — оба без
  сети): `_ping` → `Api-Version`; путь `/v<min(клиент, демон)>`; клиент: максимум 1.54,
  минимум 1.41; ниже — `unsupported` с версией демона.
- Дедлайны: запрос-ответ (list/inspect/ping) — общий дедлайн и лимит тела (list 64 МиБ,
  inspect 4 МиБ, ошибка 64 КиБ); потоки (events, logs) — дедлайн только на заголовки, тело —
  без дедлайна, но с лимитами кадров/строк.
- Ошибки: `{"message"}` + статус → классы (`404` not_found, `409` conflict, `401/403`
  forbidden, `400` bad_request, `5xx`/обрыв/таймаут — unavailable); тексты — в
  `core.Message` провайдера.

### 2. Наблюдение: эпоха, непрерывный читатель событий, сверка

Одна лента объектов на сессию и тип Engine-объекта (containers; networks/volumes/images —
лениво, по первому виду или детали, которому они нужны), с арендой и grace как кэши
Kubernetes. Жизнь ленты — **эпохи**: эпоха начинается подключением и кончается разрывом,
локальным переполнением или закрытием; вся работа (inspect, list) несёт номер эпохи, ответы
старой эпохи отбрасываются.

Начало эпохи:
1. `GET /info` → `SystemTime` демона (не часы клиента: перекос).
2. Подписка `/events?since=<SystemTime − 1 с>&filters=…` — отдельная горутина **непрерывно**
   читает поток в ограниченную коалесцирующую очередь «грязных» id (≤ 4096; переполнение →
   «грязно всё» → новая сверка) независимо от inspect-ов и UI. `since` в прошлом снимает
   перекос часов и перекрытие с историей; окно между ответом 200 и фактической подпиской
   (демон шлёт 200 до `SubscribeToEvents`) при > 256 событиях в нём **не закрывается ничем**:
   объект, созданный после list-а, чьё событие вытеснено из истории, не попадёт ни в снимок,
   ни в грязные id. Это часть явного ограничения ниже, а не то, что чинит шаг 4.
3. `GET /…/json` (list) → снимок; каждый объект — inspect в пуле (≤ 8), с поколением на id.
4. Сверка: id, ставшие грязными во время снимка, инспектируются заново **после** снимка.
   Событие — только подсказка, **никакое событие не применяется напрямую** (и `destroy`
   тоже): всё решает inspect после него (404 = удалён, есть — обновлён); так старое
   повторённое событие не может удалить новую инкарнацию. Ready — только когда эта сверка
   закончена **и** поток событий жив; list успешен, а events — 403/ошибка → вид error/stale,
   не пустой Ready; нерешённые inspect-ы (таймаут) → stale с объяснением.
5. Дальше: событие → id грязный → inspect (поколение; 404 = удаление). Обрыв потока →
   переподключение с backoff (0,5 → 8 с), вид stale через 5 с без восстановления; новая
   эпоха = шаги 1–4 и сравнение (пропавшие из нового снимка — удаления).
Фильтры событий: `type=container` и действия `create, start, restart, die, stop, kill,
pause, unpause, rename, update, destroy, health_status` (`exec_*` от healthcheck-ов шумят —
спайк); для сетей — `type=network` (`create, destroy, connect, disconnect`: `connect` грязнит
и сеть, и контейнер из `Actor.Attributes.container`), тома — `type=volume` (`create, destroy,
mount, unmount`), образы — `type=image` (`pull, tag, untag, delete, load, import`).

*Уточнено при реализации (Task 4, 2026-09-30):*
- Лента контейнеров подписана на `type=container` **и** `type=network` (`connect/disconnect`)
  одним потоком, **без** фильтра `label=com.docker.compose.project` на событиях: у Moby фильтры
  разных ключей складываются по И, и label-фильтр отбросил бы события сети (у них в атрибутах
  нет labels контейнера). События контейнеров без compose-label отбрасываются на месте (у
  событий контейнера labels — в `Actor.Attributes`); `connect/disconnect` грязнит контейнер
  «слабо» — inspect только если он уже известен ленте. List контейнеров — с label-фильтром;
  inspect без label-а проекта — «не наш» (удаляется, если был).
- Тома — только `create, destroy`: `mount/unmount` шумят на каждом старте контейнера, а
  «используется» считается из inspect-ов контейнеров.
- Образы: `pull/load/import` называют ссылку (`app:latest`), inspect разрешает её в id; ключ
  ленты — всегда id из ответа; 404 по ссылке ничего не удаляет.
- Фильтр `event=health_status` совпадает с `health_status: healthy` (Moby режет Action по `:`).
- Конец потока событий обрывает эпоху **сразу**, даже посреди снимка (зависший inspect старой
  эпохи отменяется, его поздний ответ не попадает в новую).
- Одна горутина на ленту делает всё (снимок, сверку, inspect-ы грязных id): ответы старой
  эпохи не могут попасть в новую по построению; id, ставший грязным во время своего inspect-а,
  читается ещё раз в следующем проходе. Неудачный (не 404) inspect оставляет последний
  известный объект, лента stale с объяснением, пока объект не прочитан (событие или
  «Перечитать»). Результат inspect-а заменяет объект, только если ответ другой (сравнение
  тела) — представления не пересчитываются зря.
- `Get` читает объект (контейнер/сеть/том/образ) **свежим** inspect-ом поверх снимка ленты
  («на момент чтения»); если ответ отличается от ленты — лента получает id как грязный и
  догоняет (таблица и детали сходятся без опроса).
- Вид пересчитывает свои строки из снимка лент при каждом (склеенном) изменении и отдаёт
  разницу с прошлым; статус — худший по лентам: error > loading > stale > ready (строк нет,
  пока у какой-то ленты нет первого снимка).

**Ограничение, которое не лечится без опроса:** события теряются (1) в окне старта подписки
при > 256 событиях истории (шаг 2) и (2) у медленного подписчика — Moby пропускает доставку
(буфер 1024, 100 мс) **без разрыва** потока. Непрерывный читатель делает это
маловероятным, но не невозможным — поэтому в общем UI появляется явное действие
«Перечитать», а в спецификации и AGENTS.md записано: наблюдение Docker — best effort, не
эквивалент watch Kubernetes. Периодический relist не делается (решение «без опросов»).

**Контракт «Перечитать».** API `ResyncView(viewID)` разрешает вид через его **владельца**
(сессию-инкарнацию, как `GetRows`), не через текущий выбор target-а: запрос для закрытого
вида или вида прежней инкарнации — `gone`, чужой target не трогается. Провайдер (опциональный
`provider.Resyncer`: `Resync(q Query) error`) начинает новую эпоху **лент, от которых
зависит вид** (таблица зависимостей ниже); одновременные запросы к одной ленте
склеиваются (идущая сверка не отменяется, повторная ставится после неё один раз). Строки не
удаляются до успешной сверки: провалившийся relist оставляет последние известные строки со
статусом stale; версии и надгробия вида сохраняются, поздние ответы старой эпохи
отбрасываются. Логи и детали той же сессии живут дальше (перестройка ленты не выглядит как
удаление членов сервиса). В UI — `F5` и кнопка в шапке вида, только если у сессии есть
`Resyncer` (признак в `KindDescriptor`/ответе `OpenView`); `F5` идёт через те же правила
реестра (терминал, модальные окна, обработанные клавиши); перезагрузка страницы браузера
ничего не перечитывает. Тесты: повторный F5, F5 во время переподключения, старый вид после
смены target-а, проваленный relist, два вида на одной ленте, активные логи сервиса во время
сверки.

**Таблица зависимостей (аренды лент и перекрёстная инвалидация).**
| Потребитель | Ленты | Что грязнит что |
|---|---|---|
| scopes (`projects`), выбор проекта | containers, networks, volumes | проект существует по любой из трёх |
| `services`, `containers`, детали контейнера/сервиса, логи сервиса | containers (+ networks для связей деталей) | `network connect/disconnect` → сеть и контейнер `Actor.Attributes.container` |
| `networks` | networks, containers | изменение контейнера (create/destroy/rename, connect/disconnect) → его сети пересчитываются (членство «используется») |
| `volumes` | volumes, containers | create/destroy контейнера → его тома (mounts) пересчитываются |
| `images` | images, containers | create/destroy контейнера → строка его образа добавляется/убирается без события образа |
Лента берёт аренду у каждого потребителя, отпускается с grace, как кэши Kubernetes; закрытие
одного потребителя не останавливает ленту, нужную другому.

### 3. Target-ы: Docker contexts, как docker CLI 29

Проверено на CLI 29 (2026-09-30): при `DOCKER_HOST` context `default` указывает на
`DOCKER_HOST` и он текущий, остальные contexts перечисляются как обычно; `DOCKER_CONTEXT`
при `DOCKER_HOST` не действует. Правила Ocular:
- Каталог конфигурации — `DOCKER_CONFIG`, иначе `~/.docker`.
- Target-ы — все contexts из `<cfg>/contexts/meta/*/meta.json` + встроенный `default`
  (`DOCKER_HOST` с `DOCKER_TLS_VERIFY`/`DOCKER_CERT_PATH`, иначе
  `unix:///var/run/docker.sock`). Текущий: `DOCKER_HOST` → `default`; иначе `DOCKER_CONTEXT`;
  иначе `currentContext` из `config.json`; иначе `default`.
- Id — `context:<имя>`; битый meta.json — `Problem`, остальные видны. TLS context-а —
  `<cfg>/contexts/tls/<id>/docker/{ca,cert,key}.pem`.
- `ConfigHash` — endpoint, `SkipTLSVerify`, содержимое TLS-файлов (HMAC, в UI — `configRev`).
  Логи принадлежат сессии-инкарнации (как в Kubernetes): поток пользуется неизменными
  данными соединения, пока живёт его сессия; смена конфигурации/TLS закрывает сессию, и её
  логи кончаются `gone` — без тихого переноса на новые credentials. «Перечитать» в той же
  сессии логи не трогает. (Независимый снимок соединения — только у терминала P7, как P3.)
  Тесты раздельно: ротация cert-а и «Перечитать».
- Наблюдение — inotify на `<cfg>`, `<cfg>/contexts/meta` и каждый `meta/<id>`,
  `<cfg>/contexts/tls/**`, `DOCKER_CERT_PATH`; новые каталоги добавляются в watch; атомарная
  замена файлов (rename) ловится; без опроса.
- `ssh://` и прочие схемы — target виден, сессия отвечает `unsupported` с объяснением.

### 4. Идентичность, Ref и Rev

- `Ref.Name` — **ключ** объекта, неизменный для него; для показа — новое поле `Ref.Title`
  (`core.Ref.Title`, UI показывает `title ?? name`). Контейнер: Name = полный id, UID = полный
  id, Title — имя (`/`-префикс снят). Переименование меняет Title, но не Name: открытые
  детали, логи и недавние продолжают следовать за тем же контейнером; повторно занятое имя —
  другой объект.
- Сервис: логическая идентичность `Name = <project>/<service>`, UID = тот же ключ (у Compose
  нет UID сервиса). Строка сервиса есть, пока есть хоть один его контейнер; исчез последний —
  строка удаляется; появился снова — та же логическая строка. Недавний Ref сервиса открывает
  текущий сервис с этим ключом или «больше нет». Набор контейнеров — отдельная, закреплённая
  вещь (для логов сервиса — живой набор, для действий P7 — набор из плана).
- Проект (scope): есть, пока есть контейнер **или** сеть/том с его label-ом.
- Сеть — Engine id; образ — id (`sha256:…`), теги — атрибуты (перенос тега меняет строки
  образов, не их id). Том — **без неизменного UID у Engine** (`CreatedAt` — до секунды, может
  отсутствовать): идентичность тома — единообразно best effort, UID = `<name>@<CreatedAt>`
  (без `CreatedAt` — `<name>@`), одинаковая при F5, разрыве и перезапуске приложения; локальных
  счётчиков нет. Пересоздание в ту же секунду не различается — ни через разрыв, ни на
  непрерывной ленте (destroy/create могут склеиться, inspect увидит только новый объект);
  детали тома это говорят. Тесты: неизменный том через F5 и разрыв; недавний Ref после
  перезапуска; пересоздание в другую секунду — «больше нет»; в ту же секунду — открывается
  текущий (задокументированное ограничение); старое `destroy` при пересозданном томе.
- `Rev` — хеш полей inspect-а, видимых в деталях, плюс производных связей (сети контейнера).
  `State.Health.Log` (меняется на каждой проверке) в `Rev` не входит: детали показывают вывод
  последней проверки **на момент чтения** с меткой времени и так подписаны; обновление — при
  смене статуса health (событие `health_status`) или при открытии; постоянное слежение за
  каждой проверкой не обещается. Дедлайны health — своей проекцией, как в Kubernetes.
- `Ref.Title` — только для показа: не входит в идентичность, `Expect`, ключи недавних;
  после переименования показ берётся из новых наблюдений; сохранённый `title` недавнего —
  подпись «как было», открытие — по ключу.
- Деталь следит за объектом через `Query.Name` = ключ (не отображаемое имя).

### 5. Модель: виды и связи

Scope — compose-проект (label `com.docker.compose.project`); виды провайдера (группы
навигации «Compose» и «Engine»):
- `projects` — scopes (`ScopeKind`): имя, сервисов, контейнеров, запущено, рабочий каталог и
  файлы (labels `…project.working_dir`/`…project.config_files` — только текст).
- `services` — наблюдаемые сервисы (решение 4): запущено/всего, health — по правилам 6;
  «желаемое» не показывается.
- `containers` — имя, сервис, номер реплики, state/status, health, `RestartCount`, образ,
  опубликованные порты, возраст. One-off (`…oneoff=True`, `compose run`) — тоже контейнеры
  проекта, но не члены сервиса.
- `networks`, `volumes` — проекта: с его label-ом **или** используемые его контейнерами
  (внешние сети/тома — many-to-many, связь «используется», не «принадлежит»; один объект —
  одна строка, по его id). В «все проекты» — всё, что связано с любым проектом.
- `images` — без scope (`Scoped: false`): образы, используемые compose-контейнерами, связь
  образ ← контейнеры.
- Связи: контейнер → сервис (owner), сервис → контейнеры, контейнер → сети/тома/образ,
  сеть/том → контейнеры.
- Не показываются: контейнеры без compose-labels (будущий Docker provider) —
  `KindDescriptor.NotCovered`.

### 6. Health

Контейнер (`State`):
| Состояние | Health |
|---|---|
| `running`, без healthcheck или `healthy` | ok |
| `running` + `starting` | progressing |
| `running` + `unhealthy` | error «Unhealthy»; сообщение — вывод последней неудачной проверки как свидетельство; `Since` пусто (начало неизвестно) |
| `restarting` | warning «Restarting» |
| `paused` (при `Running=true`) | warning «Paused» |
| `created` | progressing «Created» |
| `exited`, код 0 | ok «Completed» |
| `exited`, код ≠ 0 | error «Exited (N)», `Since` = `FinishedAt` |
| `dead` | error |
| `removing` | terminating |
Недавний рестарт — свидетельство **менеджера рестартов**: `RestartCount > 0` и
`StartedAt` в последние 10 мин → warning «RestartedByPolicy» с дедлайном (явный
start/restart пользователя сбрасывает счётчик — это не «все рестарты»); нулевое/будущее
время — как в P5; exited/dead/removing важнее.
Сервис (желаемое неизвестно — ничего не выдумываем) — по приоритету, первое сработавшее:
1. есть error у члена → error (причина худшего; «N из M» в сообщении);
2. есть warning → warning;
3. есть progressing (starting, created) → progressing;
4. все члены terminating → terminating;
5. все завершились с кодом 0 → ok «Completed» (остановленный и завершившийся без ошибки не
   различаются — отдельного «Stopped» нет);
6. иначе (running ok, в смеси с completed) → ok.
Тесты: один running-контейнер со `starting` healthcheck → сервис progressing; все created;
все removing; running + completed; running + exited ≠ 0.

### 7. Логи

- Контейнер: `logs?stdout=1&stderr=1&timestamps=1&tail&since&follow`; без TTY — stdcopy
  (8-байтовый заголовок; кадры — куски байтов, не строки: сборка строк, ограничение длины
  кадра и строки до выделения памяти, неполный заголовок на EOF — gap, поток 3 — ошибка
  демона); stdout и stderr — два источника одного канала в порядке прихода (без сортировки
  по времени во follow); с TTY — один поток (stderr не отделить — так и подписано).
- Курсор (устарело — см. «Уточнено при реализации» и повторное ревью) — на (полный id
  контейнера, поток): метка времени + счёт повторов с этой меткой;
  журнал Docker переживает рестарты, поэтому продолжение после рестарта — `since` = курсор с
  пропуском уже виденного, а не tail с начала; ротация/обрезка журнала → видимый gap, точный
  повтор не обещается.
- follow остановленного контейнера отдаёт историю и EOF — источник не «кончился»: он ждёт
  (`waiting`) в ленте контейнеров и переоткрывается при `start`; `destroy` → ended; драйвер
  без логов (`none`, некоторые удалённые) → error «логи не поддерживаются драйвером».
- Сервис: агрегат по живому набору контейнеров (не one-off) — подписка на ленту до снимка
  набора (без щели), новый контейнер подключается, удалённый — ended; лимиты и backpressure
  `streams`, как у Deployment.

*Уточнено при реализации (Task 5, 2026-09-30):*
- **Каналы логов = потоки.** У контейнера и сервиса каналы `stdout` и `stderr`, по умолчанию
  «все» (`*`: `stdout и stderr`; подпись выбора — «Поток», из метаданных провайдера); при обоих
  у члена два источника (`web-1` и `web-1 (stderr)`), при одном — один, и у Engine
  запрашивается только он. TTY-контейнер — один источник `name (tty)` (stderr не отделить),
  у сервиса только из TTY-членов — один канал. «Предыдущий» не предлагается (`Previous=false`;
  запрос — `unsupported`): журнал Docker один на все перезапуски.
- **Курсор** (пересмотрен повторным ревью, см. ниже) — последние прочитанные записи (≤ 512: метка, поток, длина и хэш текста) и якорь — последняя
  прочитанная строка с меткой; продолжение — `since=<метка якоря>` (позиционный `since` точно
  вернёт якорь) или раньше — с начала строки, чтение которой оборвалось; известные записи до
  якоря отбрасываются, незнакомая — доставляется с `gap` (старая строка вне окна tail, ротация);
  строка, продолжившая доставленную без `\n` (контейнер остановился посреди строки), — только
  новой частью; `tail=all`.
  Повтор лучше потери.
- **Жизнь члена** — по ленте контейнеров (без опроса): конец follow при `running` —
  переподключение с backoff (1 → 10 с, раньше по изменению ленты); остановлен —
  `waiting` («exited (code N); продолжится при старте») до изменения ленты; удалён — `ended`;
  драйвер `none` — `error unsupported`. Один контейнер: поток кончается с ним; сервис ждёт
  новых членов.
- **Backlog** — как у Kubernetes: параллельно (4), бюджет 16 МиБ на вкладку (≥ 512 КиБ на
  члена, обрезка — `truncated`), слияние по времени, последние N; член, найденный позже, —
  с начала (`tail` 10 000). Не больше 20 членов на вкладку (`limited`), не больше 64
  запросов логов в приложении.

## P7 — терминал, статистика, действия (решения, принятые на ревью; свой план позже)

- **Терминал.** Экземпляры — контейнеры сервиса (явный экземпляр сверяется с label-ами
  сервиса и полным id), канал один, команда по умолчанию `sh`. Новый exec id на каждый
  `Run`/`Again` (прототип не делит exec). Hijack: отмена/`Close` привязаны к самому
  соединению на всех шагах (dial, TLS, запись запроса, заголовки, IO); дедлайн рукопожатия
  снимается после 101; байты, прочитанные сверх заголовков, сохраняются. 101 — только
  «подключено»: ошибка старта может прийти в потоке; код выхода — только из `exec inspect`
  (иначе «неизвестно»), EOF ≠ 0. После неоднозначного ответа `start` — ни повтора, ни нового
  exec. Снимок соединения (с TLS) принадлежит приложению; `Close` провайдера — не под
  блокировками API. Тесты: нет shell, остановлен/на паузе/перезапущен, вывод в чтении
  заголовков, зависший 101/отказ/TLS, одновременная отмена и заблокированный stdin/stdout,
  поздний resize, смена target/TLS.
- **Статистика.** Контракт меняется: `GetMetrics(viewID, rowIDs)` — UI передаёт видимые
  строки (≤ 60), сервер проверяет, что они в виде; общий дедлайн и отмена (контекст
  страницы, не `Background`); сервис — сумма по ограниченному числу членов, частичный
  результат помечается. CPU — ядра: (Δ cpu контейнера / Δ system) × online CPUs, дельты
  неотрицательны, знаменатель > 0, иначе «неизвестно»; память — `usage − inactive_file`
  (cgroup v2) / `usage − total_inactive_file` (v1), вне диапазона — «неизвестно»; время
  замера и инкарнация; только Linux-демоны (`/info OSType`).
- **Действия.** Контейнер: restart, stop, start, remove (`force=false`, `v=false`; отказ
  демона для запущенного — показывается). Сервис: restart/stop/start по **закреплённому в
  плане** набору полных id (отсортирован, в `Expect`), без добавления новых членов во время
  выполнения; по одному запросу на член, последовательно; первый отказ или «неизвестно»
  останавливает остальные; итог — по членам (выполнено / отказано / неизвестно / не
  выполнялось) в `core.ActionResult.Parts` (новое поле, общий UI его показывает). `Expect` —
  **локальная предпроверка** (id, `StartedAt`, статус, параметры stop: таймаут, сигнал,
  `AutoRemove`), а не условие записи Engine: гонка «кто-то перезапустил тот же контейнер
  между проверкой и записью» остаётся и описана в диалоге и документах. Таймаут grace stop
  передаётся явно (`t=`), дедлайн запроса больше него; 304 (уже запущен/остановлен) —
  «ничего не изменилось»; сбой до отправки — failed, после возможной отправки — unknown,
  без повторов; stop может завершить процесс принудительно после grace — сказано в
  последствиях. Права — «неизвестно» (у Docker нет SSAR: доступ к сокету = всё).
