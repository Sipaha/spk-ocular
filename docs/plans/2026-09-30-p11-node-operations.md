# P11 — узлы: cordon, uncordon, drain

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`. Каждая задача — отдельные
> коммиты `area: summary`, `make check` зелёный перед коммитом. Каждое исправление и каждая
> возможность начинаются с теста, который падает без них.

**Цель:** у узла Kubernetes появляются действия **Cordon** (планировщик больше не назначает
на узел новые pod-ы), **Uncordon** (назначает снова) и **Drain** (cordon + запросить выселение
pod-ов через Eviction API, который соблюдает PodDisruptionBudget) — по смыслу как
`kubectl cordon/uncordon/drain` и те же пункты Lens, с отличиями, названными в решениях
(пропуск завершённых и удаляемых, без `--force`, без ожидания). Сейчас у
узлов нет ни одного действия (P4 сознательно не дал им delete: «узел выводят, а не удаляют»).

**Архитектура:** существующий контракт действий P4 (`PrepareAction` → просмотр → один
`RunAction`), без новых методов API; DTO плана расширяется общим необязательным полем списков
(решение 9). Drain — первое действие Kubernetes с частями (`ActionResult.Parts`,
как у Compose P7): cordon и выселение каждого pod-а — отдельные записи, итог по частям. Общий UI
и `internal/core` не знают слов «узел» и «drain» (подписи — ключи сообщений провайдера).

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md`; пункт — из `docs/backlog.md`
(«Действия (из P4): … cordon/drain узла»). Принципы: Read-first, destructive — с подтверждением,
все contexts RW без read-only-пометок.

## Глобальные ограничения

- Всё из P0–P10 (AGENTS.md «Правила»), особенно правила действий: `RunAction` читает строго по
  UID, `Expect` связывает всё, что прочитали эффекты плана, несовпадение — `conflict` без
  записи; каждая запись — один HTTP-запрос (`restWriter`, `MaxRetries(0)`), неоднозначный ответ
  (5xx, таймаут) — `unknown`, без повторов; повтор — только при провале предусловия, когда
  перечтение доказывает, что записи не было (≤ 3).
- Никаких опросов: drain **не ждёт** завершения выселенных pod-ов (это делает kubelet по их grace
  period); таблица pod-ов показывает это вживую. Итог говорит «выселение запрошено».
- Все contexts RW. Тесты записи — только kind `ocular-dev`, и только на отдельном узле для
  drain-тестов (Task 1), чтобы не выселять системные pod-ы и фикстуры других тестов.

## Решения P11 (агент, 2026-09-30; ревизия 2 по ревью плана Codex)

1. **Объём.** Узел: `cordon`, `uncordon`, `drain`. Без параметров: grace period — собственный у
   каждого pod-а (как `kubectl drain` по умолчанию), без `--force`, без `--disable-eviction`,
   без ожидания ухода pod-ов, без запасного DELETE. В бэклог: grace period/таймаут, drain
   нескольких узлов, ожидание с прогрессом, CronJob (обнаруженный вид — отдельный этап).
   Итог drain значит «выселение запрошено и принято сервером», **не** «узел можно выключать».
2. **Cordon / Uncordon.** Merge patch `spec.unschedulable: true|false` с `metadata.uid` и
   `metadata.resourceVersion` (как restart/scale P4, повтор по 409 — по общему правилу).
   Недоступно, если узел уже в нужном состоянии. Оба не опасные. Слова эффекта: «планировщик не
   будет назначать на узел новые pod-ы; работающие остаются» — cordon не мешает pod-ам с
   `nodeName` или с toleration-ом `unschedulable` (сказано в эффекте). Права — SSAR `patch
   nodes` с именем узла. `effectState` — `spec.unschedulable`. В меню оба пункта есть всегда
   (применимость по строке не вычисляется, общий UI не разбирает состояние узла): неприменимое
   — `Unavailable` в свежем плане.
3. **Drain: разбор pod-ов.** Pod-ы узла — list по `spec.nodeName=<узел>` во всех namespace-ах,
   `limit = maxDrainPods + 1` (`maxDrainPods` = 500; kubelet по умолчанию держит ≤ 110).
   Больше, есть `continue`, нет права или ошибка — план `Unavailable` («не удалось узнать все
   pod-ы узла» / «pod-ов больше 500»), без записи; тот же предел и то же правило в `RunAction`.
   Классы:
   - **пропускаемые** (в плане свёрнутым списком, без записи): pod-ы с контроллером-DaemonSet,
     mirror/static (`kubernetes.io/config.mirror`), завершённые (`Succeeded`/`Failed`),
     удаляемые (`deletionTimestamp`);
   - **без контроллера** (нет `ownerReferences` с `controller: true`) — не выселяются и названы:
     «после выселения их никто не пересоздаст; удалите сами, если они не нужны» (kubectl без
     `--force` отказывается от всего drain — мы выселяем остальные);
   - **выселяемые** — остальные; у каждого в плане владелец (вид/имя). Pod-ы с `emptyDir`
     названы отдельно: данные `emptyDir` пропадут (как `--delete-emptydir-data`).
   Drain всегда опасный. Слова: «выселение запрошено; контроллер может пересоздать pod
   (где — решает планировщик)», не «pod-ы перезапустятся в другом месте» — наличие
   контроллера не гарантирует ни его работу, ни место.
4. **Drain: отпечаток pod-а и `Expect`.** У каждого pod-а, который пишется или назван, —
   семантический отпечаток: namespace, имя, UID, `nodeName`, класс, ссылка на контроллер
   (apiVersion, kind, имя, UID), имена томов `emptyDir`. `Expect` = маршрут + узел (UID,
   `spec.unschedulable`) + отсортированный список отпечатков выселяемых и названных. Переход
   pod-а между классами (в том числе из пропускаемых в выселяемые или названные и обратно)
   меняет этот список. Изменения только статуса (`resourceVersion`, conditions) в `Expect` не
   входят. PDB в `Expect` не входят: сервер решает при каждом выселении, прогноз плана —
   только прогноз.
   `RunAction`: узел по UID, pod-ы тем же list-ом (решение 3); другой `Expect` — `conflict`,
   ни одной записи («pod-ы узла изменились — посмотрите снова»).
5. **Drain: выселение pod-а.** `POST pods/<pod>/eviction` (`policy/v1` Eviction) через
   `restWriter` (`MaxRetries(0)`, один HTTP-запрос на попытку) с
   `deleteOptions.preconditions = {uid, resourceVersion}` из **свежего** списка `RunAction`
   (не из плана). Ответ:
   - 201/200 — `done` («выселение запрошено»);
   - 429 с cause `DisruptionBudget` — `refused`: «не позволяет PodDisruptionBudget,
     повторите позже»; 429 без него — `refused`: «сервер временно отказал (ограничение
     частоты)»; `Retry-After` не выполняется, повторов нет (повторный drain безопасен);
   - 409 или 404 — ничего не доказывают сами (409 — и конфликт версии, и конфликт хранилища;
     404 — и нет pod-а, и нет маршрута eviction), поэтому **одно** ограниченное чтение pod-а
     по имени: нет — `skipped` «pod уже удалён»; другой UID — `skipped` «pod заменён, новый не
     выселялся»; тот же UID и тот же `resourceVersion` — `refused` с классом ответа; тот же UID,
     новый `resourceVersion` (только при 409) и тот же отпечаток — повтор выселения с новым
     `resourceVersion` (≤ 3 попыток на pod, общее правило «повтор — только когда чтение
     доказало, что записи не было»); отпечаток другой — `refused` «pod изменился после
     просмотра»; чтение не удалось — `refused` с классом исходного ответа (при 404/409 записи
     не было). Новый UID не выселяется никогда; DELETE вместо выселения — никогда;
   - 403 — `refused` (права), 400/422 — `refused` (отказ), 5xx/таймаут/обрыв/нет статуса —
     `unknown` без повторов (в том числе 500 «у pod-а больше одного PDB» — план заранее
     предупреждает о таком pod-е, решение 7).
   Своя классификация выселения, отдельно от `failedWrite` (он про объект действия).
6. **Drain: части, порядок, сроки, итог.**
   - Части: `cordon` (если узел открыт), затем по одной на выселяемый pod (namespace/имя),
     затем `skipped` на каждый названный без контроллера («оставлен: без контроллера»).
   - Cordon первым. Его `refused`/`unknown` — все остальные части `skipped` («не начато:
     узел не закрыт»). Повтор cordon по 409 — только до выселений и с перепроверкой всего
     `Expect` drain (узел и pod-ы).
   - Выселения независимы: `refused`/`unknown` одного не останавливает следующие.
   - Срок: `drainRunTimeout` = 45 с на весь прогон (чтения, cordon, выселения; запас 15 с до
     60-секундного таймаута диалога), у каждой записи — свой срок 10 с (не дольше остатка).
     Перед каждой следующей частью проверяются остаток срока и отмена; исчерпан/отменён — ни
     одной новой отправки, оставшиеся — `skipped` («не начато: истёк срок» / «отменено»).
     Запись, чей срок истёк, — `unknown`.
   - Итог (`ActionResult.Outcome`) по старшинству: есть `unknown` — `unknown`; иначе есть
     `refused` — `refused`; иначе есть `skipped` — `skipped` (не завершено: названные, не
     начатые); иначе `done`. Поздний `done`/`refused` не стирает более ранний `unknown`.
   - После первой отправленной записи `RunAction` **всегда** возвращает результат с частями
     (сделанные, текущая `unknown`, не начатые `skipped`), не ошибку — и при отмене, и по
     сроку; ошибка — только до первой записи (`conflict`, `gone`, `unavailable`).
   - Особые случаи: узел открыт и выселять нечего — прогон = cordon (+ названные); узел уже
     закрыт и выселять нечего — план `Unavailable` («нечего выселять», названные перечислены).
   - Весь drain не повторяется никогда.
7. **Drain: прогноз PDB.** PDB в namespace-ах выселяемых pod-ов (list, ≤ 50 namespace-ов, ≤
   200 PDB на namespace, параллельно ≤ 8, под `prepareExtrasTimeout`); по selector-у PDB —
   предупреждения: «сейчас не позволяет выселить (`disruptionsAllowed` = 0)» — с оговоркой по
   `observedGeneration`/`unhealthyPodEvictionPolicy` (прогноз, сервер решает сам), «у pod-а
   больше одного PDB — сервер откажет». Не удалось прочитать, предел, не успели —
   «PDB не проверены» (не «PDB нет»).
8. **Права — только записей этого плана.** Cordon/uncordon: SSAR `patch nodes/<имя>`. Drain:
   `patch nodes/<имя>` — только если в плане есть часть cordon; выселение — SSAR на каждый
   выселяемый pod по имени (группа `""`, ресурс `pods`, субресурс `eviction`, `create`,
   namespace, имя): RBAC позволяет `resourceNames` у субресурса, поэтому отказ широкого
   вопроса по namespace-у — не доказательство отказа по имени. Оптимизация: широкий SSAR по
   namespace-у, ответ `allowed` покрывает его pod-ы; `denied`/`unknown` — вопросы по именам.
   Параллельно ≤ 8, под `prepareExtrasTimeout`; не успели — «unknown», не «allowed». Итог:
   любой `denied` — план `denied` с перечнем (namespace/имя).
9. **Общий DTO и UI.** `core.ActionPlan` получает необязательное поле `Lists []ActionList`:
   `ActionList{Title Message, Destructive bool, Collapsed bool, Items []ActionItem}`,
   `ActionItem{Name string, Note *Message}` — общее, без слов «узел»/«pod» (подписи — ключи
   провайдера). Списки плана полные (≤ `maxDrainPods`), никогда не усечённые; UI показывает
   их порциями по 50 («показать ещё»), свёрнутые — по щелчку. Части результата тоже
   порциями по 50, каждый не `done` доступен с причиной. Диалог не закрывается сам, если итог
   не `done` (так уже для `refused`/`unknown`; `skipped` — туда же). В общем UI нет ветвлений
   по `kubernetes`/`nodes`/`drain` и разбора «SchedulingDisabled».
10. **Тестовый узел.** kind `ocular-dev` (одноразовый тестовый кластер этой сессии; других
    пользователей у него нет) пересоздаётся по `scripts/kind-config.yaml`: control-plane + один
    worker с taint-ом `ocular.dev/drain=only:NoSchedule` и меткой `ocular.dev/drain=only`.
    Taint — не изоляция: системные DaemonSet-ы (kindnet, kube-proxy) его терпят и остаются —
    это проверяемые «пропускаемые». Перед любой записью kind-тест проверяет, что каждый
    выселяемый pod узла — фикстура drain (метка), иначе отказ теста без записи. Фикстуры с
    `nodeSelector` на worker-е после выселения остаются `Pending`, пока узел закрыт, — тест
    ждёт именно этого (старый UID ушёл, новый pod `Pending`), а не «переезда»; очистка —
    uncordon и удаление фикстур. Тесты, считающие узлы (`kind_test.go`), и `kind-churn.sh` —
    на два узла.

## Ревью плана

Ревью Codex ревизии 1 (`a359621`): объём и основные выборы приняты (без нового метода, названные
без контроллера вместо отказа от всего drain, `emptyDir` только в опасном плане, drain вслепую —
недоступен, cordon первым, независимые выселения, без опроса и DELETE, PDB вне `Expect`).
Замечания, все приняты (ревизия 2):
- P2 — класс pod-а меняется при том же UID (снят владелец, владелец A→B): одного набора UID
  мало → отпечаток pod-а в `Expect`, предусловия выселения uid + `resourceVersion` из свежего
  списка, 409 — чтение и сверка отпечатка (решения 4, 5).
- P2 — ответ не доказывает причину (429 — не только PDB, 409/404 — не только «pod ушёл») →
  cause `DisruptionBudget`, одно чтение pod-а при 404/409, консервативный `refused`, без DELETE
  (решение 5).
- P2 — права могли запретить разрешённый drain (patch узла без части cordon; широкий SSAR при
  `resourceNames`) → только записи плана, SSAR по имени pod-а (решение 8).
- P2 — итог частей не был определён (drain не останавливается, в отличие от Compose) →
  старшинство итога, результат с частями после первой записи, сроки прогона и записи, особые
  случаи (решение 6).
- P2 — UI обещал группы и порции без контракта, пределы не заданы → `ActionPlan.Lists`, порции
  в UI без усечения семантики, пределы list/PDB/SSAR (решения 3, 7, 8, 9).
