# P17 — Действия над несколькими объектами и принудительное удаление pod-а

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`. Каждая задача — отдельные
> коммиты `area: summary`, `make check` зелёный перед коммитом (коммит — только по его коду
> выхода). Каждое исправление и каждая возможность начинаются с теста, который падает без них
> (проверка мутацией на старом коде).

**Цель:** в таблице можно **отметить несколько строк** (флажки, Ctrl/Shift+щелчок, Space,
Shift+стрелки, Ctrl+A) и выполнить над ними одно действие — удалить 30 упавших pod-ов,
перезапустить пять Deployment-ов, остановить три контейнера Compose — с одним просмотром, где
видно, что будет с каждым, и итогом по каждому. У pod-а появляется **«Удалить принудительно»**
(`kubectl delete --force --grace-period=0`) — для pod-ов, зависших в Terminating (сейчас у
удаляемого pod-а все действия недоступны, и чинить приходится kubectl-ом).

**Почему этот этап (выбор агента, 2026-10-01; пользователь просил не ждать его выбора):** на живых
кластерах ежедневная уборка — это пачки: Evicted/Error/Completed pod-ы после инцидента, рестарт
нескольких сервисов после смены Secret, зависшие в Terminating pod-ы на ушедшем узле. Сейчас в
Ocular каждое — отдельный диалог на каждую строку. Прочее из бэклога реже (удаление namespace по
имени, undo StatefulSet) или крупнее без такой же ежедневной отдачи (несколько кластеров,
compose-файлы). Удаление namespace с вводом имени — остаётся в бэклоге: редкое и с огромным
радиусом, отдельный этап.

**Архитектура:** массовое действие — **композиция в UI** существующего контракта P4: для каждого
отмеченного объекта свой `PrepareAction` (свой план, свой `Expect`, свои права), один общий
просмотр, затем для каждого готового — свой `RunAction`. Сервер и `core` не меняются (кроме
нового действия pod-а); гарантии P4 (чтение по UID, `conflict` без записи, `unknown` без
повторов) действуют для каждого объекта как есть. Агенты (P14) не затронуты: они и так действуют
по одному объекту; `forceDelete` получают как любое новое действие — только явным грантом.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md`; пункт — `docs/backlog.md`
(«Действия (из P4): … force delete (grace 0), массовые действия над выделенными строками»).
Принципы: Read-first, destructive — с подтверждением, все contexts RW без read-only-пометок.

## Глобальные ограничения

- Всё из P0–P16 (AGENTS.md «Правила»), особенно правила действий: `RunAction` читает строго по
  UID, `Expect` связывает всё, что прочитали эффекты плана, несовпадение — `conflict` без
  записи; каждая запись — один HTTP-запрос, неоднозначный ответ — `unknown` без повторов;
  повтор — только когда перечтение доказывает, что записи не было (≤ 3).
- Никаких опросов: ход удаления/перезапуска виден вживую в таблице.
- Все contexts RW. Тесты записи — только kind `ocular-dev`, в собственном namespace теста
  (удаляется); образы — только уже загруженные на узлы (`busybox:1.36`).
- Ручные запуски — изолированные HOME/DOCKER_CONFIG/SPK_OCULAR_HOME, цель по точному имени.
- UX важнее памяти; меряется только Private_Dirty.

## Решения P17 (агент, 2026-10-01)

1. **Отметка ≠ курсор.** У таблицы остаётся курсор (выбранная строка: детали, L, S, Enter) и
   появляется набор **отмеченных** строк (`marked: Set<rowId>` в странице `Workspace`).
   - Мышь: колонка флажков слева (32 px; в заголовке — «все/никто», промежуточное состояние);
     Ctrl(⌘)+щелчок — переключить отметку строки **без** открытия деталей; Shift+щелчок —
     отметить диапазон от последней переключённой строки (якорь) до этой в текущем порядке
     сортировки.
   - Клавиатура (таблица в фокусе): Space — переключить отметку строки курсора; Shift+↑/↓ —
     сдвинуть курсор и отметить строку, на которую он пришёл; Ctrl+A — отметить все строки,
     прошедшие фильтр; Esc при отметках — снять все (одна клавиша — одно действие: детали
     этим Esc не закрываются). Порядок Esc: открытое меню → отметки → детали. Space, Ctrl+A,
     Shift+стрелки — только когда фокус в таблице (в поле фильтра Ctrl+A выделяет текст, в
     диалоге — его поля; ревью P3-5).
   - Отмеченные ⊆ показанные строки: строка, ушедшая из таблицы (удалена, не проходит новый
     фильтр), из набора выпадает; смена вида/scope/цели набор очищает. Почему: действие не
     должно касаться невидимого — «скрытые отмеченные» при снятом фильтре были бы сюрпризом.
   - Отмеченные строки подсвечены (`bg-marked`, отличимо от курсора `bg-active`).
     `aria-selected` остаётся у курсора (на нём держатся тесты и навигация); отметка —
     `aria-checked` у флажка строки и `data-marked` у строки.
2. **Полоса отметок.** При ≥ 1 отмеченной в шапке страницы (вместо счётчика рядом с
   заголовком) — «Отмечено: N» + кнопка «Действия ▾» (меню массовых действий) + «Снять
   отметку». Контекстное меню отмеченной строки при N ≥ 2 — массовое меню (те же действия +
   «Снять отметку»); у неотмеченной — прежнее меню строки (набор не меняется).
   Delete при N ≥ 2 — массовое удаление; при N ≤ 1 — как сейчас (строка курсора).
   N = 1 — всегда обычный диалог одного объекта (он богаче).
3. **Какие действия массовые.** Пересечение действий видов отмеченных строк (строка Problems —
   свой вид) по `id`, у которых нет `text`, нет параметра `choice`, не `noAgents` и не `single`
   (debug, undo — только поштучно: выбор/образ у каждого свой). **Новый флаг дескриптора
   `ActionDescriptor.Single`** («только по одному объекту») — у `drain` (ревью P2-2: четыре drain
   одновременно выселяют всё сразу, замены не находят узла — остальные уже cordon, PDB
   проверяется по выселению, не по суммарной потере; kubectl drain нескольких узлов идёт по
   одному). Флаг в `core` провайдер-агностичен; агентов не касается (они и так по одному). Параметр `count` — общий (scale пяти
   Deployment-ов до 0). Подпись — `actionLabel` действия; `destructive` — если у любого вида.
   Пусто — меню говорит «Нет общих действий для отмеченных».
4. **Просмотр (`BulkActionDialog`).** Один диалог на весь набор (снимок refs на момент
   открытия — дальнейшие изменения отметок его не трогают).
   - Шапка: действие, цель (контекст/сервер один — таблица одной цели), число объектов по
     видам и namespace-ам («12 pods в 3 namespace-ах»).
   - Count (если есть) вводится первым, как в `ActionDialog`; планы готовятся после ввода.
     Смена count после готовых планов пересобирает **все** планы (ревью P3-2); запуск
     недоступен, пока не вернутся все планы для нового count (как в одиночном: запуск — только
     по планам, просмотренным для этого значения).
   - Планы готовятся параллельно, **не больше 6 одновременно** (у каждого PrepareAction до
     5 с дополнительных чтений и SSAR), прогресс «Проверено 7 из 12».
   - Список объектов (порциями по 100, `Portions`): имя, namespace, состояние плана —
     *готов*, *готов с предупреждениями (N)*, *недоступен: причина*, *нет прав: причина*,
     *проверка не удалась: ошибка*. Строка раскрывается — эффекты, предупреждения, `Changes`,
     `Lists` этого плана (переиспользуется разметка `ActionDialog` — вынести в
     `PlanDetails.tsx`). Права `unknown` — готов (как в одиночном диалоге: действие может
     пройти).
   - Сводка над списком: «Будет выполнено: 10; пропущено: 2 (недоступно или нет прав)»;
     предупреждения, повторяющиеся по ключу сообщения, сведены в одну строку «… — у N
     объектов» (первые 3 имени).
   - Кнопка «Удалить 10» / «Перезапустить 5» (опасная — при destructive любого плана);
     выключена, пока готовятся планы или готовых нет. «Проверить заново» — пересобрать все
     планы. У опасного просмотра начальный фокус — «Отмена» (как у одиночного, ревью P3-3;
     тест).
5. **Выполнение.** Только готовые планы; по каждому свой `RunAction` (`ref` с UID из плана,
   его `Expect`, его `configRev`), **не больше 4 одновременно**, таймаут 60 с на запуск (как у
   одиночного: дольше — «итог неизвестен»). Итог появляется в строке объекта: сделано /
   отказано / конфликт (объект изменился — свой текст провайдера) / итог неизвестен /
   частично (`Parts`, как у одиночного). «Остановить» — не начинать новые (идущие
   досчитываются), не начатые — «не выполнено». Диалог не закрывается, пока идут запуски
   (как одиночный). По окончании — сводка «Сделано 9 из 10; 1 конфликт» и уведомление в
   строке состояния; ошибочные строки остаются видимыми. Повторный запуск того же просмотра
   невозможен (как одиночный: новый просмотр — новые планы). План, устаревший за время
   чтения просмотра (например, грант «Запустить сейчас» у CronJob живёт 10 мин), заканчивается
   строкой «конфликт» со словами провайдера; молча планы при запуске не пересобираются —
   «Проверить заново» (ревью P3-4). Сделанные строки из отметки
   снимаются, несделанные остаются отмеченными — можно «Проверить заново».
   Почему по одному RunAction, а не новый серверный «batch»: каждый объект уже со своим
   `Expect` и классификацией итогов; batch дублировал бы их, не давая ничего, кроме меньшего
   числа запросов по localhost.
6. **Без предела на размер набора.** 300 Evicted pod-ов — реальный случай. Планы готовятся
   по 6, список порциями; память — только планы набора (с `Lists` у Deployment-ов — pod-ы;
   ограничено тем, что уже в кэше таблицы). Проверить на kind: 200 pod-ов, время подготовки и
   Private_Dirty WebProcess до/после — записать в «Итоги».
7. **`forceDelete` у pod-а.** Дескриптор `{ID: "forceDelete", Title: "Force delete",
   Destructive: true}` у `podsKind` после `delete`. Запись — `DELETE` с
   `GracePeriodSeconds: 0`, `Preconditions{UID}` (без resourceVersion: у удаляемого pod-а
   версия меняется, пока kubelet его гасит; принудительное удаление должно пройти и тогда —
   объект тот же по UID; `Expect` — UID, deleting, узел, владелец-контроллер, **список
   `metadata.finalizers`**), propagation background. Предупреждение о неготовом узле —
   **совет, в `Expect` не входит** (как проверка прав): узел, мигающий Ready/NotReady, не
   должен превращать запуски в конфликты; это сказано в коде рядом с `Expect` (ревью P3-1). Доступно **и у удаляемого** pod-а — это его главный случай (исключение из
   общего `unavailable.deleting` для этого действия). Unavailable: mirror (статический) pod —
   «управляется kubelet-ом узла: удаление ничего не даст» (как у `delete`, если там уже есть;
   иначе — для обоих).
   **Финализаторы (ревью P2-1).** `DELETE` с grace 0 убирает pod сразу, только если у него нет
   `metadata.finalizers`; с ними он остаётся Terminating, пока контроллеры их не снимут — это
   частая причина «застрявших» pod-ов. Тогда эффект другой: «pod останется, пока контроллеры не
   снимут финализаторы: X, Y — принудительное удаление этого не обходит», и он же —
   предупреждение (видно в сводке массового просмотра). Снятие финализаторов — отдельная, более
   опасная правка: бэклог, не P17.
   Эффекты (без финализаторов): «pod исчезнет из API сразу, не дожидаясь, пока kubelet
   остановит контейнеры»;
   контроллер (как у `delete`: «контроллер X создаст замену»). Предупреждения: узел не Ready
   или неизвестен — «контейнеры на узле N могут продолжать работать»; владелец — StatefulSet —
   «замена с тем же именем может запуститься, пока старый pod ещё работает (две копии одной
   идентичности)»; pod не удаляется — «обычное удаление даст контейнерам завершиться;
   принудительное — для зависших». Права — `delete pods` (как `delete`). Done — «pod X удалён
   принудительно». Меню: подпись `act.forceDelete` «Удалить принудительно», без горячей
   клавиши. Массовое — да (зависшие пачкой на ушедшем узле).
   Агенты: новый глагол `action:forceDelete` появляется сам, только явным грантом; в
   редакторе грантов предупреждение `agents.warn.forceDelete` («обходит ожидание kubelet-а:
   у StatefulSet — риск двух копий»).
8. **Синтетика.** Синтетические Workloads/Pods: `forceDelete` (строка «Terminating» у
   синтетического pod-а, который «застревает» при обычном delete); отказ одного из объектов
   при массовом запуске (для e2e итогов «частично») — через существующие
   `/api/_test/synthetic/controls`.
