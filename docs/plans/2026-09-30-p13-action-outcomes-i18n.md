# P13 — итоги и отказы действий на языке интерфейса

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`. Каждая задача — отдельные
> коммиты `area: summary`, `make check` зелёный перед коммитом. Каждое исправление и каждая
> возможность начинаются с теста, который падает без них.

**Цель:** в русском интерфейсе итог действия и причина отказа — по-русски. Сейчас последствия
в просмотре переведены (ключи сообщений провайдера, P4), а уведомление об успехе («node x:
cordon requested», «Job … created from cronjob …») и текст отказа/конфликта в диалоге («…
changed since the action was reviewed; review it again», «the review of this run has expired»)
— английский текст провайдера внутри русской рамки («Конфликт: …»). Пункт бэклога P12
(решение 164) расширен на отказы: они видны в том же диалоге и строятся тем же провайдером.

**Архитектура:** тот же механизм, что у последствий: `core.Message` (ключ провайдера,
параметры, английский текст) и `messageText` в UI. Итог действия становится `core.Message`;
классифицированная ошибка провайдера получает необязательную причину-сообщение, которая
проходит через `CodedError` к UI по HTTP (поле JSON) и по Wails (`cause` ошибки вызова — туда
Wails кладёт JSON самой ошибки). UI показывает причину на своём языке, иначе — `detail` как
сейчас. Новых методов API нет.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md`; пункт — `docs/backlog.md`
(«Уведомление об успехе простого действия — английский текст провайдера … перевести ключом
сообщения, как последствия»).

## Глобальные ограничения

- Всё из P0–P12 (AGENTS.md «Правила»). Поведение действий не меняется: те же записи, те же
  классы ошибок, те же английские предложения (`Text` итога, `Error()`/`detail` ошибки —
  дословно прежние; e2e на английском остаются как есть). Форма JSON итога меняется
  осознанно (решение 1).
- Текст сервера (сообщение apiserver-а, Docker Engine, ошибка сети) не переводится: он —
  параметр `{detail}` нашего предложения или, если нашего предложения нет, `detail` как есть.
- Ключи — в словаре провайдера (`messageTexts`), русский — в `providerTexts` UI; тест покрытия
  переводов (есть у kubernetes и compose) держит равенство ключей и параметров.

## Решения P13 (агент, 2026-09-30)

1. **Итог — сообщение; смена контракта осознанная.** `core.ActionResult.Message` становится
   `core.Message` (было `string`; JSON `message` — объект `{key, params, text}`). Все провайдеры
   заполняют его ключом там, где есть словарь (kubernetes, compose); синтетический провайдер —
   только `Text`. Английский `Text` дословно прежний. UI: уведомление об успехе —
   `messageText(res.message)` и в обычном, и в позднем (после таймаута) пути; у итога с частями
   — как сейчас, сводка частей на языке UI. **Совместимость не держим, и это решение, а не
   упущение:** API — внутренний контракт одного бинарника; его потребители — встроенный UI
   (страница отдаётся тем же процессом и в Wails, и в HTTP-режиме), Go-тесты, e2e. Рассинхрона
   версий нет: токен HTTP случайный на процесс (`newAuthToken`), страница прежнего процесса
   получает 401 и не может получить (и отрисовать) новый ответ API — остаётся прежний экран или
   ошибка; Wails-страница живёт в процессе. Потребители в репозитории
   обновляются все (Go: `api`, провайдеры, тесты; UI: типы, `ActionDialog`, тесты; e2e —
   проверка текста уведомления). Тест контракта — форма JSON итога через HTTP-транспорт
   (`message` — объект с `text`, без `parts[].message`), не только равенство `Text`.
2. **Части — только причина.** `core.ActionPart.Message` удаляется: у выполненной части текста
   UI не показывает (и не показывал), у невыполненной показывает `Why`. Правило: у части
   `refused` и `unknown` всегда есть `Why` (у compose — из ошибки записи: её причина-сообщение,
   иначе `{Text: detail}`); у `skipped` — по возможности (drain даёт, compose — нет: сводка
   говорит «не выполнено»). Английский текст невыполненной части compose меняется осознанно: был
   `err.Error()` с префиксом класса (`invalid: the Docker Engine refused: …`), становится
   причиной без префикса — исход части UI и так говорит своей меткой («отказано»).
3. **Причина ошибки.** `provider.Error` получает `Why *core.Message`; конструктор
   `provider.Said(class, m)` ставит `Message = m.Text` и `Why = &m` (так `Error()` и `detail`
   не меняются). `api.CodedError` получает `Why *core.Message` (`json:"why,omitempty"`),
   `fromProvider` переносит её. HTTP `writeErr` кодирует `why`. Wails: `defaultMarshalError`
   делает `json.Marshal(&err)` — у `*CodedError` это его JSON-поля, и они приходят в
   `error.cause` отклонённого вызова (тест на Go повторяет этот маршалинг; тест UI — разбор
   `cause`). Сообщение `CallError` (`"code: detail"`) не меняется — `parseWailsError` читает
   код оттуда, как сейчас.
4. **Что получает ключи.** Каждое наше предложение на пути `PrepareAction`/`RunAction`, которое
   UI может показать, **включая общие помощники, через которые этот путь проходит** (перечень
   по вызовам, не по файлам):
   - kubernetes: успех всех действий (`restart`, `scale` с «было → стало», `cordon`,
     `uncordon`, `suspend`, `resume`, `delete`, `run` с именем Job, `drain` — сводка); отказы и
     конфликты в `actions.go`, `drain.go`, `cronjob_run.go` (объект изменился/удалён/заменён,
     изменился API-ресурс, «продолжает меняться», итог неизвестен — `{detail}`, «ничего не
     записано» — `{detail}`, срок/повтор/предел/прежнее подключение гранта run, «Job с таким
     именем уже есть», неизвестный вид/действие). Уже ключевые причины (`why` недоступности,
     `drain.why.*`) передаются как `Why`, а не как `.Text`. Общие помощники на этом пути:
     `readObject` (`logs.go`: «объект удалён, его имя занял новый» — через `getObjectOf` в
     `getConfirmed`; ключ получает сам помощник, поэтому и логи/правка, которые его зовут,
     видят причину), `invalid(...)` из `exec.go` там, где его зовут действия (`getConfirmed`
     без UID, `readRunGrant` «просмотр запуска недействителен») — эти места строят
     `provider.Said` сами, `invalid` для exec/forward не трогается.
   - compose: успех действий контейнера (`writeAction`), отказы в `actions.go` (изменился,
     удалён, «Docker Engine отказал: {detail}», не ключ сервиса, нет контейнеров, `act.*`
     недоступности) и уже ключевые ошибки `resource.go` (`error.*` — сейчас ключ теряется).
   - слой API (`internal/api`): свои предложения на пути действия — «объекты этой цели нельзя
     менять», «сессия закрылась — попробуйте снова», «конфигурация цели изменилась после
     просмотра», «у вида больше нет этого действия» (`core.FindAction` не нашёл: каталог
     сменился между меню и кликом; класс `unsupported` прежний) — ключи `api.*`, свой словарь
     и свой тест покрытия переводов.
   Остаются английскими осознанно: ответы сервера без нашего предложения (`statusMessage(err)`:
   403, 400/422, 409 не про версию; ошибки сети через `classify`) — UI показывает класс
   по-русски и текст сервера; проверки, до которых UI не доходит (`checkRun`: пустые поля,
   `CheckParams`: UI сам проверяет диапазон числа до запроса). Ошибки со скрытым текстом
   сервера (Secret, P10) не меняются: в `Why.Params` не попадает ничего, чего нет в `detail`.
5. **Одно место разбора в UI.** Копии `detailOf`/`errDetail` (ActionDialog, EditDialog,
   ValueDialog, ValuesSection, ResourceDrawer, useLogStream, useMetrics) и `errText` (Ports,
   TerminalView) сводятся к одной функции `errorDetail(e)` — **только текст**: у `ApiError` —
   причина `why` на языке UI, иначе `detail`, иначе код; у обычного `Error` — `message`; иначе
   `String(e)`. Класс по-прежнему добавляет вызывающий там, где добавлял (`errText` =
   `classLabel(code) + ': ' + errorDetail(e)` в Ports/TerminalView; ActionDialog — в своих
   рамках «Конфликт: …»/«Отказ (класс): …»), так что меток не становится ни меньше, ни больше.
   `ApiError` сохраняет `code` и `transport`: исход «неизвестно» (обрыв связи) по-прежнему
   решается по ним, перевод причины на классификацию не влияет. Причина проверяется по форме
   (`key`/`text` — строки, `params` — объект строк); иная — игнорируется (показывается
   `detail`; `key` и `params` необязательны, причина только с `text` — допустима). В UI
   подстановка — функцией-обработчиком, так что `$&`, `$1`, `` $` ``, `$'` в значениях — тоже
   данные. Так причины, которые уже есть у compose (`error.*`), видны везде, где UI
   показывает ошибку. Переводить ошибки правки YAML/значений/логов ключами — не в P13 (бэклог).
6. **Страж — дополнение, не доказательство.** Покрытие доказывают поведенческие тесты через
   публичные `PrepareAction`/`RunAction` и API (решение 4, Task 2–3): замена объекта под тем же
   именем, запуск без UID, испорченный грант run, вид/действие, исчезнувшие из каталога, — у
   каждого `Why.Key`, класс и `detail` прежние. Дополнительно тест исходников: в файлах действий
   (`kubernetes/actions.go`, `drain.go`, `cronjob.go`, `cronjob_run.go`, `compose/actions.go`)
   нет `provider.Error{` с `Message: fmt.Sprintf(`/строковым литералом/`….Text` (потерянный
   ключ), нет вызовов `invalid(` со строкой; текст сервера (`statusMessage(err)`, `msg`
   классификатора) допустим. Проверяется мутацией: вернуть одну старую строку — тест падает.
7. **Подстановка параметров — один проход.** Сейчас и `msg` в Go (kubernetes, compose), и
   `messageText` в UI подставляют параметры повторными `ReplaceAll` по уже подставленному
   тексту: текст сервера в `{detail}`, содержащий `{name}`, переписывается (ревью Codex
   воспроизвело: `server says {name} was rejected` → `server says nightly …`; нужен шаблон с
   несколькими параметрами — один `ReplaceAll` свою вставку не пересканирует, поэтому
   однопараметрические `drain.why.*` сейчас не задеты). Новая подстановка — один проход по плейсхолдерам
   **исходного шаблона** (`\{(\w+)\}`): известный параметр заменяется значением, неизвестный
   плейсхолдер остаётся как есть, значения не сканируются. Одинаково в Go (общая функция в
   `core`, её зовут `msg` обоих провайдеров и `api`) и в UI (`messageText`). Тесты (Go и UI):
   значение с `{name}`/`{detail}`/токеном другого параметра, JSON-скобки, повторённый
   плейсхолдер, кавычки/перевод строки/`%` — текст сервера сохраняется дословно и в английском,
   и в русском.
