# P5 — Problems, палитра, клавиатура, полировка, soak

> Для агентов: задачи выполняются по порядку, шаги отмечаются `- [x]`; каждая задача —
> отдельные коммиты `area: summary`, `make check` зелёный перед коммитом; каждое исправление и
> каждая возможность начинаются с теста, который падает без них.

**Цель:** открыв context, пользователь одним видом **Problems** видит, что сломано в выбранной
области (namespace или все) сейчас — pods, workloads, сервисы/ingress-ы, узлы — и недавние
Warning events как отдельные свидетельства, с честным покрытием по каждому источнику («узлы:
нет права list», «events: загружаются»). `Ctrl+K` открывает палитру: переход к виду, target-у,
namespace-у, строке текущей таблицы или недавнему объекту; команды в стиле k9s (`:po`,
`:deploy web`, `:ns demo`, `:ctx prod`). Приложение проходится с клавиатуры, в том числе в
русской раскладке, не отнимая клавиши у терминала и редактора. Память не растёт за час работы
под «шумящим» кластером.

**Спецификация:** `docs/specs/2026-09-29-spk-ocular-design.md` — «Kubernetes MVP — функции»
(Problems, навигация), «Ключевые технические решения» п. 3–6 (health, время без опроса,
рестарты, Problems — «проблемы в наблюдаемой области»), «Состояние (SQLite)» (недавние
переходы), «Критерии успеха» (без роста памяти за час, `scripts/pss.sh`). Решение 5 меняется
(см. «Рестарты») — спецификация правится в Task 1.

## Глобальные ограничения

- Всё из P0–P4 (AGENTS.md «Правила»). `internal/core`, `internal/api`, общий UI не знают
  pod/deployment/namespace: Problems — вид провайдера с обычными строками, палитра — поверх
  `KindDescriptor`, `Target`, `ScopesView`, строк видов и метаданных провайдера.
- Никаких фоновых опросов кластера и глобальных LIST ради поиска: Problems — watch-и тех же
  кэшей (аренды), время — только локальные дедлайны.
- UX важнее экономии памяти; считается только Private_Dirty.
- Тесты с записью и нагрузкой — только на kind `ocular-dev` (kubeconfig и context проверяются
  до любой мутации).
- Вне P5 (бэклог): Jobs/CronJobs/CRD как источники Problems, скорость рестартов по истории
  наблюдений, глобальный поиск объектов, настраиваемые правила, оповещения, хранение истории
  проблем, интеграции мониторинга, общий фреймворк команд.

## Что уже есть (обзор 2026-09-30)

- Health считает провайдер в `project(u, now) → (cells, Health, next)`; `next` — момент, когда
  правило времени поменяет вердикт; `viewWatch` (`view_watch.go`) — один вид поверх одного
  кэша: сериализация обработчиков и таймеров (`order`), дедлайны по UID-инкарнации, поколения
  таймера, статус источника loading/ready/stale/error, тесты на фейковых часах. Правила
  времени: Pending ≥ 5 мин, NotReady ≥ 2 мин, OOMKilled за 10 мин, адрес LoadBalancer/Ingress.
- Кэши — по ключу (gvr, namespace, selector): таблица namespace X, «все namespaces» и детали
  одного объекта — разные informer-ы; аренды с grace 60 с, не больше `maxIdleCaches` простаивающих.
- Колонка Restarts — сумма `restartCount`; Warning events — строки вида Events; у Event
  whitelist слим-кэша не хранит `involvedObject.apiVersion` и `series`.
- Аудит health (ревью Codex, подтверждено кодом `kind_workloads.go`): StatefulSet с разными
  ревизиями — Progressing без дедлайна, даже при 0 ready (сбой маскируется навсегда);
  OnDelete/partition держат ревизии разными намеренно — тоже «RollingOut» навсегда; DaemonSet
  OnDelete — так же; приостановленный Deployment — Warning, даже здоровый.
- Клавиатура: `/`, стрелки/Enter в списке target-ов и таблице, `L`, `S`, `Delete`,
  `Shift+F10`, Esc в панелях (`inTerminal` не отдаёт Esc терминала панели); единого реестра нет.
- SQLite: `ui_prefs`, `target_state` (4 КБ на значение).
- Замеры: `scripts/pss.sh`, `kind-load.sh`, `measure-kind.mjs` (один проход). `/api/_test/*`
  монтируется только в browser-режиме (`browser.go`), desktop статистики не отдаёт.

## Решения P5 (агент, 2026-09-30; пересмотрены по ревью Codex)

### Состояние против свидетельств

Problems показывает два рода строк, и UI их различает:
- **Текущая проблема** — health объекта сейчас (`error`, `warning`, `unknown`), посчитанный
  **той же проекцией**, что и строка его таблицы (один источник правды: таблица и Problems
  согласованы по построению).
- **Недавнее свидетельство** — Warning event, последнее наблюдение которого в пределах 15 мин.
  Это не «объект сломан сейчас»: восстановившийся pod может ещё иметь свежие события. Колонка
  Kind у таких строк — «Event», severity — отдельное значение «recent» (стиль приглушённый).

### Аудит health (Task 0, до Problems)

Таблицы тестов на проекции, общие для таблиц и Problems:
- Доступность важнее «идёт rollout», когда нечему работать: StatefulSet с `desired > 0` и
  `ready == 0` — `error` «0 of N ready» даже при разных ревизиях. Deployment при rollout
  остаётся Progressing — его ограничивает `ProgressDeadlineExceeded` (API сам ставит дедлайн).
- Намеренное ≠ сбой: StatefulSet/DaemonSet `OnDelete` с разными ревизиями — не RollingOut
  (ok + reason «UpdatePending», доступность проверяется как обычно); StatefulSet с `partition`
  — rollout завершён, когда `updatedReplicas ≥ replicas − partition`; приостановленный
  Deployment — не Warning сам по себе (reason «Paused»), доступность проверяется.
- ReplicaSet — не источник Problems (его сбой виден через Deployment и pod-ы); Jobs — вне
  покрытия, так и написано в покрытии.

### Рестарты (решение 5 спецификации меняется)

- **Было:** сессионная история наблюдений `restartCount` (база, дельты, кольцо, разрывы).
  **Ревью Codex:** разрывы watch/relist при живом кэше, пересекающиеся кэши (namespace / все /
  имя) с разным порядком доставки, повторные списки и выселение делают «N рестартов за 10 мин»
  выдуманным без единой ленты наблюдений на pod — это отдельная сложная подсистема.
- **Стало:** правило из того, что говорит сам API, без локального состояния:
  `lastState.terminated.finishedAt` контейнера (обычного, init, sidecar) в пределах 10 мин →
  warning **RecentRestart** «перезапущен N мин назад (причина/код выхода), всего рестартов R»,
  дедлайн — `finishedAt + 10 мин` (существующий планировщик вида). Время — серверное; если
  `finishedAt` в будущем больше чем на 1 мин (перекос часов), правило молчит (не утверждаем
  «недавно»); меньший перекос — «только что». CrashLoopBackOff остаётся `error` по
  `state.waiting.reason`. Одна проекция — строка pods и Problems совпадают.
- Скорость рестартов по истории наблюдений — бэклог (с условиями Codex: одна авторитетная
  лента на pod, эпохи покрытия, ограничения и очистка).

### Warning events

- Строка — **один объект Event** (ключ — UID события): Kubernetes сам сворачивает повторы в
  один Event со счётчиком; мы не складываем события и не суммируем `count` с `series.count`.
- Время последнего наблюдения: `series.lastObservedTime` → `lastTimestamp` → `eventTime` →
  `metadata.creationTimestamp` (последний — с пометкой «время создания»). В Problems — если
  оно в пределах 15 мин; дедлайн — `+15 мин`; время в будущем больше 1 мин — не «недавнее»
  (перекос), не держится вечно; отрицательный возраст не показывается.
- Счётчик — накопительный за серию: подпись «всего N, последнее M назад», не «N за 15 мин».
  Одиночные Warning events включаются (свидетельство, не «повторяющееся»).
- `Row.Ref` строки события — **сам Event** (вид Events уже открывается в деталях, связь
  «involved object» ведёт к объекту по UID). Никакого разрешения по имени в «живой» объект:
  событие об удалённом старом UID не превращается в действия над новым одноимённым объектом;
  у события без UID объекта связь помечается «не проверено». Действий у строк событий нет.
- Whitelist Event расширяется: `involvedObject.apiVersion`, `series.count`,
  `series.lastObservedTime` (для группы+kind объекта и времени).
- Источник — отдельный кэш событий области с `fieldSelector=type=Warning` (меньше памяти, чем
  все события; при открытой таблице Events это второй informer — принято).

### Вид Problems: сборка без обобщения планировщика

- Kubernetes отдаёт kind `problems` (первым в группе, заголовок «Problems»), scoped как pods.
- **Сборка:** открытый вид Problems берёт аренды источников — pods, deployments, statefulsets,
  daemonsets, services, ingresses (правила адреса LB/Ingress), nodes (кластерные), Warning
  events — и на каждый ставит **обычный `viewWatch`** с его проекцией, дедлайнами, порядком и
  статусом, но с **фильтрующим адаптером `Sink`**: строка источника с проблемой → upsert
  строки проблемы; без проблемы или удалена → delete; `Reset` источника заменяет только строки
  этого источника (адаптер помнит их ID). Планировщик не обобщается — у строк разных
  источников нет общих зависимостей (рестарты — чистая проекция). Аренда — одна на
  потребителя: таблица pods и Problems делят informer, но освобождают его независимо.
- **ID строки:** `<kindID>#<uid>` (UID не содержит `#`; у событий — UID события); стабилен при
  обновлениях. `Row.Ref` — объект с UID (UI берёт возможности — детали, логи, терминал,
  действия — по `Ref.Kind`, не по виду таблицы).
- **Колонки:** Severity (status), Kind (вид объекта или «Event»), Namespace, Name, Reason,
  Message, Since. Сортировка — severity (error, warning, unknown, recent), затем Since.
- **Since** — только время, известное провайдеру: `lastTransitionTime` условия
  (Ready/Available/PodScheduled/узел Ready), время состояния контейнера (`finishedAt`),
  время наблюдения события; иначе пусто. Не время создания объекта и не «последнее
  обновление». Для этого у `core.Issue` необязательное поле `Since` (провайдер-агностично).
- **Узлы** при выбранном namespace — кластерные строки: Namespace пуст, покрытие говорит
  «узлы: весь кластер». Не приписываются namespace-у.

### Покрытие

- `ViewStatus.Coverage []SourceCoverage{Source, State, Class, Message}` — по источнику,
  фиксированный порядок (порядок источников вида); `State` — loading/ready/stale/denied/error.
  Статус вида: `loading`, пока хоть один источник грузится; `ready`, когда все осели и хотя бы
  один ready; `stale`, если все живые источники stale (строки — последние известные, не
  выбрасываются); `error` — все отказали. «0 проблем» при неполном покрытии UI показывает с
  перечнем непокрытого, не как «всё здорово».
- Сравнение статусов в `internal/views/view.go` (`*d.Status != v.status`) заменяется явным
  `Equal` с глубоким сравнением `Coverage` (и копией при сохранении) — иначе слайс ломает
  компиляцию/даёт ложные инвалидации. Тест: одинаковое покрытие — без события; изменение
  одного источника — одно событие.
- Не покрыто в P5 и так и сказано в покрытии: Jobs, CronJobs, PVC, CRD.

### Палитра (`Ctrl+K`)

- Модальная палитра: поле + список (показ ≤ 200 после ранжирования; выделение сохраняется при
  живом обновлении списка по ключу элемента). Источники: виды текущего target-а, target-ы
  (все провайдеры; у одинаковых заголовков — файл/провайдер в подписи; выбор по
  непрозрачному `Target.ID`), scopes (живой список или ручной ввод, если список запрещён),
  строки **текущей** таблицы (дубли одного `Ref` — один пункт), недавние объекты текущего
  target-а. Подпись покрытия: «объекты: текущая таблица и недавние». Никаких LIST ради поиска.
- Fuzzy — свой скорер (подпоследовательность, бонусы за начало слова/точное совпадение;
  латиница и кириллица как есть). Без зависимостей.
- **Грамматика** (ввод с `:`), приоритет сверху вниз:
  1. `:<scope-алиас> <имя>` — сменить scope (k8s: `ns`); `:<scope-алиас> *` — все;
     `:<target-алиас> <текст>` — target (k8s: `ctx`). Алиасы scope/target — метаданные
     провайдера (`ProviderInfo.ScopeAliases/TargetAliases`), общий UI их не знает.
  2. `:<kind-алиас>` — открыть вид; `:<kind-алиас> <текст>` — открыть вид с фильтром таблицы
     `<текст>` (не «открыть объект по имени»). Алиасы — `KindDescriptor.Aliases`.
  3. Иначе — fuzzy по источникам.
  Точное совпадение (id/заголовок) выбирается Enter-ом сразу; несколько совпадений — список,
  **никогда** не молчаливый первый fuzzy-кандидат. `:ns` без аргумента — вид Namespaces
  (правило 2), `:ns all` — namespace с именем `all` (все — только `*`).
- **Недавние:** таблица SQLite `recent_objects` (provider, target, kind, scope, name, uid,
  title, opened_at); запись — при **успешном** открытии деталей; идентичность включает UID
  (одноимённая замена — новая запись, старая открывается с «Этого объекта больше нет»); ≤ 50
  на target, ≤ 500 всего (вытеснение по времени). API `RecentObjects`/`TouchRecent` с
  (provider, target) в запросе; ответ для уже не текущего target-а UI отбрасывает.

### Клавиатура

- **Маршрутизация** (сверху вниз): открытые модальное окно/меню → локальные обработчики
  терминала и CodeMirror (терминал получает **все** клавиши, включая `Ctrl+K`, Esc, `F6`;
  CodeMirror — Esc при открытых поиске/подсказках) → глобальные клавиши приложения. Реестр
  `web/src/shortcuts.ts`: одно место, `KeyboardEvent.code`, признак «работает в полях ввода»
  (только `Ctrl+K` и Esc), игнор при `isComposing` и AltGraph, повторы (`repeat`) — только для
  навигационных клавиш. Слушатели в фазе capture уважают `inTerminal`.
- Глобальные: `Ctrl+K` — палитра (кроме терминала: там это kill-line; в панели терминала есть
  кнопка палитры), `?` — справка (физически Shift+Slash, не в полях ввода), `F6`/`Shift+F6` —
  по кругу видимых областей (список target-ов → навигация видов → таблица → детали → нижняя
  панель; скрытые пропускаются; внутри модального окна не действует; в терминале не действует).
- Навигация видов: стрелки/Home/End/Enter (roving tabindex). Таблица: + PageUp/PageDown,
  Home/End. Детали: `Alt+←` — назад по связям (вне полей ввода; `Backspace` не используется —
  он редактирует текст и в WebKit может означать «назад» в истории); хлебные крошки
  (исходный › связанный › …) кликабельны.
- Фокус возвращается туда, откуда открывали; если элемента больше нет (строка удалена или
  вне виртуального окна) — в тело таблицы / контейнер области.
- Русская раскладка проверяется в настоящем WebKitGTK (Xvfb, `xinput.py`), не только
  синтетическими событиями.

### Полировка (только найденное, без новых возможностей)

- Бэклог P4: единственное число вида в диалоге (`KindDescriptor.Singular`), тексты последствий
  на ключах + параметрах (ru/en). Бэклог P3: названия уровней «Pod/Container» в диалоге
  терминала от провайдера.
- **Поздний ответ действия** (пришёл после клиентского таймаута): у прогона — свой номер
  операции, отдельный от поколения диалога; поздний ответ обновляет **свой** ещё открытый
  диалог в состоянии «неизвестно» или показывает уведомление с целью; никогда не закрывает и
  не меняет более новое подтверждение, не сбрасывает его ошибки, ничего не отправляет заново.
  Тесты: таймаут→успех, таймаут→отказ, диалог закрыт, открыт другой диалог, сменён target.
  Отдельный коммит, не смешивается с клавиатурой.

### Soak

- **Стенд:** kind + `scripts/kind-churn.sh` (реальные watch/relist/bookmark-и): свой namespace
  `ocular-churn`, до мутаций проверяет kubeconfig/context kind-ocular-dev; фиксированный
  потолок живых объектов; `trap` очистки. Каждые ~2 с: создание/удаление pods (в т.ч.
  одноимённых с новым UID), scale 1↔5, patch ConfigMap-ов, Warning events, crashloop-pod,
  pod с потоком логов; фазы: обрыв API (пауза control-plane контейнера kind на 20 с →
  relist) и свёрнутое окно. `up`/`down`, темп — параметры.
- **Статистика desktop:** флаг разработки `--test-api` у desktop-сборки поднимает
  `testRoutes` на отдельном loopback-порту с токеном (не в релизной сборке по умолчанию);
  `/api/_test/stats` — виды, аренды, кэши (активные/простаивающие), потоки, терминалы,
  туннели, горутины, дедлайны. Замер того же дерева процессов (Go + WebKit) — `pss.sh`.
- **Сценарий:** скрипт по кругу (через test API или `xinput.py`): Problems (все / namespace) ↔
  pods (все / namespace) ↔ детали с events ↔ follow логов deployment-а ↔ терминал ↔ туннель,
  смена target-а туда и обратно; > 8 простаивающих ключей кэша; сознательные
  дополнительные аренды — перечислены в отчёте.
- **Прогон:** 15 мин разогрева (за окнами рестартов/событий и заполнения буферов), затем
  60 мин; каждые 60 с — `pss.sh` + stats + фаза сценария + PID-ы (перезапуск процесса =
  провал) + фактический темп churn → CSV. Итог: наклон Private_Dirty за последние 30 мин,
  разброс, пик, значение через 5 мин после закрытия видов. Критерий: < 1 МБ/10 мин и
  ограниченные счётчики stats. Шумно — продлить/повторить и показать CSV, критерий не
  двигать. Принудительный GC не используется.
- Короткий диагностический прогон (15 мин) — сразу после Problems (Task 3), приёмочный час —
  на финальной сборке (Task 8).
